# pi 源码教程的写作与绘图经验

适用基线为 56cae782341c339d3bb820081f0f9425d8c5b1ec。用户已认可第一章第二次重做后的内容与视觉方向。后续章节依照本规范交稿。

## 读者需要能自己推出结果

读者没读过源码。先给一个有编号的输入，要求预测输出，再介绍这次推演需要的对象。沿调用入口解释状态如何改变，最后只改一个条件，让读者重新计算。设计收益必须从例子中推出，涉及作者动机时注明来源，源码推导使用“由此可以看出”。

用 A.json 的 30 秒、B.json 的 60 秒贯穿普通 harness；独立演算要明确另起教学例。真实执行、可控 provider、源码推演三者都写清楚。每个非平凡结论应连到固定提交的文件与符号，定位行号在修改后复查。

## 把关系画出来

失败的首版用了五张表重复一次读取过程，丢失了结构信息。用户认可的修订版展示包的边界、消息归属、历史树、投影规则、任务所有权及执行归序。选图形时先确定问题需要哪种关系，再安排空间。

架构用嵌套框标所有权，时序用生命线，历史用树，调度用时间带。箭头逐条写起点、终点、动词和前提。不同视图的边不能混用。字段列表适合表格，表格不能代替调用关系。主体占画布约 85%，正文保持清晰，少量解释贴近决定行为的节点。

蓝表示调用，青表示返回，紫表示状态。横向 3:2 或 16:10，奶白或浅灰背景、墨蓝标题、细线和克制留白。提示词给出精确文字，禁止模型自行补充伪字段、模块、保证或因果关系。每张图保持一个主要问题。

## 必须防止的技术错误

- read 属于 coding-agent，执行循环属于 pi-agent-core。执行箭头应落到工具。
- context_edit 是会话条目类型。不得凭空添加 role=edit、content 等字段。
- SessionEntry.parentId 选历史路径，toolCallId 配对调用结果。树边和调用边分别解释。
- 模型声明工具时给出名称、说明、参数定义，具体路径在 toolCall 参数里。
- 工具结束事件与结果消息的顺序可能不同。并行图必须标前置条件。
- 截断保护也发执行事件，事件存在不足以证明工具体运行过。
- Durable 的 Entry、Document、Task 各有职责，不能画成依次转换的三个阶段。
- 持久检查点提供恢复依据；外部副作用还要检查重放和幂等边界。

## Q&A 的交付要求

问题单列标题，紧接可见的“答案”段落，再给字段级推导、条件变式和源码依据。至少覆盖结果预测、设计必要性、异常边界三类。检验题应能区分“看懂了一段话”和“能独立判断”。

## 生成和验收

技术底稿先写对象归属、固定输入、预期输出和源码依据，再提交 imagegen。内置接口未返回具体模型型号。每张都查看实际成图，重点找反向箭头、错接容器、额外伪代码和难读中文。发现问题只修有误关系，保留已核对内容，再看整图。

验证按结论选择仓库现有测试或离线可控实验。测试通过的数量不能替代图的技术校对。复查章节是否自洽、链接是否存在、图片是否落在工作区。任务进度保留在同目录，已完成与待验收明确区分。

全书扩展时还发现两个高频问题。第一，自动生图会给正确主链补上错误的小字，例如把结果正文写进 journal，或让每次重新调度都重开崩溃计数。验收要读全部小字，并逐条追闭环。第二，相同的“提交”在立即存储和 deferred 文档更新中有不同可见性，讲保证时必须把具体提交内容和适用条件写在图旁。读者复核要检查这些跨模块边界，不能只校验单个函数名称。
