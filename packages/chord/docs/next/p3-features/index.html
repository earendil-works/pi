Before we begin

p2 grew feature by feature on the phone: 33 plugins, about 65,000 lines, a web shell and a TUI. p3 is its rewrite on Chord v2, with an app kit that already gives hosts, workers, HTTP with sessions and pairing, plugins with versioned APIs, files and export. The meeting's job is to decide what p3 ships first, what waits, and how the work splits.

Some of it was settled yesterday (Armin's summary): sessions sync to R2 through Radius by commit log, the session index is a replicated Chord table, every host kind loads plugins through registries, hands connect proactively. The owner added: voice waits; environments turn around into hands; continuing a local session on Radius is core; subagents and handoff are in, artifacts are questionable; the plugin API stays small enough to evolve.

Ten things to know

  1. Proposed base: sessions (with delete), the agent and conversations, subagents, history and handoff, code mode, shell commands, models and login, prompt resources, workspace (read and review), file index, status and notices, search through the index, the web shell and the TUI, hands, session sync and continue-on-Radius.
  2. Proposed later: voice, terminals (need channels and hands), artifacts, port forwards, chat mode and guest sharing, MCP and tool_search.
  3. Hands replace SSH-dialled daemons: a long-lived daemon dials the server (or Radius), is enrolled once by a pairing code, and carries p2's existing daemon protocol over one multiplexed WebSocket.
  4. The sync handshake needs a driver identity. Two machines writing one session both push "from Radius's last seq" and silently diverge; an epoch or lease per session (Chord's rule S7) closes it.
  5. The index has two writers once a session continues on Radius; three options, one recommended (derive rows from session stores).
  6. Tools in base: read, write, edit, bash, codemode, subagent, team, agent, conversations, history_*, location tools, rename_session, send_file; artifacts, ports and reload_plugins wait or change.
  7. One CLI, no environment variables: p3 serve, p3 tui, p3 hand, p3 owner-link, p3 install; settings as arguments and files, per the app kit.
  8. The plugin API v1 is seven clusters, almost all already existing: Durable's extension, a Conversation contract, input transforms, environments and models, questions, UI registries, objects for state.
  9. Litmus test: all 78 coding-agent extension examples are expressible; Doom needs two small fixes (frame splitting in the TUI bridge, a path for large plugin assets); streaming frames from a worker and raw terminal ownership do not fit, by design.
  10. Twelve work packages, with p3's skeleton on the app kit and the session/index/sync core first.

Words used throughout

A hand is a daemon on a machine that connects out to a p3 server or to Radius and offers execution (commands, files, watching, terminals). A driver is the single host allowed to write a session's store at a time; a replica follows its commits. An epoch numbers driver changes. The index is the table of session metadata (title, status, idle state) the session list reads. The app kit is Chord's startApp/startWorker layer.

II

Hands

Environments turned around: the machine connects to the server, not the other way.

What p2 does

p2's server and workers start a daemon (pi-env) over SSH on demand, one connection per session and per use (four connection pools: each worker, the directory picker, the connection test, the terminal host). The daemon is stateless and kills its commands 30 seconds after its connection goes quiet. Its frame protocol (exec, files, watch, file listing, PTYs) does not depend on SSH.

What a hand is (proposed)

p2's daemon hand
who dials the server, over SSH the hand, over WSS, to the server or to Radius
needs sshd, a key, a network path to the machine outbound HTTPS only
lifetime per connection a service (systemd, launchd, Termux:Boot), reconnecting
install deployed and verified at each start installed once, signed updates
machine identity SSH host key a hand key pair, enrolled once
connections one per session and use one per hand and server, multiplexed
  • Enrollment: p3 hand enroll <server> shows a code; the owner approves it in the UI (the app kit's device pairing); the server pins the hand's public key; fingerprints shown on both sides. Revocation in a Hands panel.
  • Reachability: a hand reaches the owner's own server directly (LAN, own tunnel) or through Radius, which relays hands to whichever host drives a session (the upsell: no tunnel to set up; Radius can also offer sandboxed machines and hands of its own).
  • Protocol: p2's daemon protocol over the WebSocket, unchanged in shape; two changes: several sessions share one connection (cancellation, handles and backpressure per session), and a disconnect starts a grace period instead of killing everything (detached commands and PTYs reattach on reconnect; this moves the terminal host's job into the hand).
  • Binding: a session's location becomes { hand, cwd }; one server object holds the hand connections and the HarnessEnvironments entry resolves a hand id to an execution environment; workers reach hands through the server's links. An SSH machine stays possible as a hand kind the server dials.
  • Offline: an operation needing an offline hand fails with a clear error the model sees; the hand's status shows in the session list.
III

Session Sync and the Index

What was decided yesterday, and the three gaps it leaves.

Decided

The worker updates the session index from events and sends it to the server; sessions sync to R2 through Radius: Radius reports per session its last sequence number, pi uploads the commit log from there; R2 holds the SQLite file and the commit log, a SQLite Durable Object applies them; sessions have an owner id; the index is a Chord table replicated like a session, its row updated only on metadata, session idle and subagent idle changes.

Chord v2 has the pieces: a versioned outbox written in each commit's transaction, export archives, batch apply that refuses gaps and divergence, export and import per address (app kit). Missing (the sync layer): upload and trim, epochs, pull-back after a power loss, the split, starting from an archive.

Gap 1: who is the driver

Two machines both write session X (the laptop resumed it while Radius continued it). Both ask Radius for its last seq, both upload from there; Radius applies whichever arrives first and refuses the other as "not following". The copies have now diverged and nobody knows.

Proposed: a driver epoch per session, handed out by Radius. An upload names its epoch; an old epoch is refused; the refused copy becomes a new session (Chord's rule S7: a split, never a rollback, because tools already ran). "Continue on Radius" is an epoch change: the local driver waits for idle, uploads the tail and the session's files, Radius bumps the epoch and starts the agent from its store, the local side becomes a replica or closes. Back is the reverse.

Gap 2: two writers of the index

When a session continues on Radius, Radius writes its index row, and so does the local server.

Option How Cost
a. one index per writer each host keeps its own index, Radius merges per owner, newest epoch wins per row a second merge rule
b. rows derived from session stores every host computes a session's row from the session's own commits no index sync at all; each host needs the session's commits
c. rows tagged { epoch, seq } Radius keeps the highest per row rows must carry their source position

Recommended: (b) where the session's commits are present (Radius has them all), with (c)'s tag on the rows a local server writes for sessions it drives, so a list without the session store still sorts correctly.

Gap 3: what else moves

Files outside the store (uploads, sent files, the app kit's Files) must sync as blobs before the batches naming them, R2 as their home. Model access and secrets for a session continued on Radius: Radius's own models, or the owner's provider keys stored on Radius (decide). Local prompt resources (the device's AGENTS.md, skills) must be read through a hand or synced. Closed sessions have no worker: the server reads a session's outbox without starting it, or starts it to sync.

V

Running p3

Starting the server, the CLI, themes and keybindings.

The CLI (proposed)

One binary, p3, and no environment variables (app kit decision); settings are arguments or files in the data directory.

Command Does
p3 serve [--data-dir <dir>] [--host <addr>] [--port <n>] starts the server (startApp); prints the one-time owner link
p3 owner-link prints a new owner link for a running server (through the owner token file)
p3 tui [url] [--pair] the sandboxed TUI; on the same machine it uses the owner token file, elsewhere device pairing
p3 hand enroll <url>, p3 hand run enrolls this machine as a hand, runs it (or installs a service)
p3 radius login signs the server into Radius (device code)
`p3 install <git:... npm:...>`
p3 export <session> <file>, p3 import <file> the app kit's export per address

The data directory defaults to ~/.p3. Its files: settings.json, models.json, auth.json (locked), AGENTS.md, skills/, prompts/, plugins/ (the user's root), the server store, a directory per session worker, owner-token, logs/. Plugin-specific configuration moves into plugin objects (documents) instead of more files.

Themes and keybindings

Themes follow the looks-and-themes proposal (decided 2026-11-02): design tokens as CSS variables on the web, roles in the TUI, one Themes registry plugins contribute to, one dark and one light choice per user. Keybindings: commands are registry entries with default keys (p2's TuiCommands with when conditions, 78 binding ids); the user's overrides live in a preferences document (per user, synced like any data), not in files on each client; the web gets the same command registry with its own key handling.

VI

The Plugin API

The smallest surface that still expresses everything the coding agent's extensions do.

The rule

Offer few things, each stable: what an API offers, it must keep (versioned in the import path, @p3/app/v1). Every cluster below is a registry or a contract that already exists in Chord, Durable or p2; p3 v1 publishes those and nothing else. Legacy concepts of the old extension API are not carried: CLI flags, an event bus, RPC-mode UI, hasUI checks, "destructive switch" gates, pi.exec running locally regardless of the environment.

Seven clusters

The litmus test

All 78 examples map onto the seven clusters (table in /tmp/p3-prep/extensions.md). The examples that mix agent and UI split into a worker facet and a tui/web facet sharing a contract file: a tool that wants a dialog asks the Questions object, which works from any client, several clients or none.

  • Snake, Space Invaders, tic-tac-toe: a command plus an overlay in tui.ts and a canvas in web.tsx, engine in a shared file, saves in a user-keyed document. Fit today.
  • Doom: fits with two fixes in the TUI: the sandbox bridge caps a frame at 64 KiB and a Doom frame is about 160 KB (split writes at escape boundaries), and the sandbox has no files or network, so large plugin assets (a 4 MB WAD) need a documented "asset of my plugin" path (chunked reads through the plugin's server facet).
  • Does not fit, by design: streaming 35 FPS frames from a worker to clients (objects carry state; needs channels), engine state surviving an in-place reload (needs an explicit save), raw terminal ownership (interactive-shell becomes a terminal view; terminal notifications need a launcher action).

What v1 leaves out

Editor replacement (extension points only), raw provider stream events and response headers, a fork hook, a turn_start hook, an event bus. Each has one or two examples; add when a real plugin needs it.

Open Questions

To decide in the meeting.

  1. The proposed cut: base versus later per area (first table).
  2. Driver identity: epochs per session, handed out by Radius, with splits on conflict?
  3. The index with two writers: derived rows plus { epoch, seq } tags, or one of the other options?
  4. Who syncs a closed session (the server reading its outbox, or starting its worker)?
  5. Files outside the store as blobs on R2, uploaded before their batch?
  6. Models and secrets for sessions continued on Radius: Radius's own models, or the owner's keys stored there?
  7. Hands: through Radius as a relay to the driver, and may one hand serve the local server and Radius at once?
  8. Do hands keep commands and terminals alive across disconnects (absorbing p2's terminal host)?
  9. Hand install and updates: signed binary, service install, version negotiation.
  10. Is SSH kept as a hand kind for machines without a service?
  11. Plugin API v1: the seven clusters as listed, and what is explicitly left out?
  12. Work package owners and order.
