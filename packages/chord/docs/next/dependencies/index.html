Before we begin

It is a Tuesday morning and Mario opens a session on his phone. The server starts a worker for it. The worker connects to the server, loads its plugins and opens the agent's harness. One of the plugins, code mode, needs the harness before it can contribute its tools. Another, search, needs a feed that lives on the server. A third, sharing, was removed from the worker's plugin set last night, but the notes view still asks for it. At the same moment the browser tab holds the session's notes, which live on the worker that is still starting.

Every one of these is the same question asked in different places: what I need is not there yet; what now? Chord v2 answers it today in five different ways, depending on how the dependency was declared and where its provider lives. A missing type on the same host breaks the object for good; the same type missing on another host makes it retry every few seconds forever; a missing registry waits for a value; a reload that removes a type ends every reference to it. And when two hosts start at once and need each other's objects in a chain that has no cycle at all, both wait until a 60-second deadline breaks the knot.

The owner's direction was short: an object should be parked until its dependencies resolve, and there should be no difference between a dependency on this host and one on another: a link going away is like the provider's plugin being unloaded, and a link coming back is like it being loaded. This book works out what that means, rule by rule, and plays it through the scenarios that decide whether it holds.

Eight things to know

  1. A request outlives its provider. A reference stands for a request (type, params, principal, version). It ends only when its holder ends it, never because the provider is missing, went away or does not fit.
  2. One resolver for local and remote. The address decides where a request goes; the provider found there is checked; a missing provider here and a missing provider on another host give the same answer.
  3. Two kinds of not-yet. Something under way (activating, reconnecting, installing, not published yet) shows as loading; nothing under way (not served, no fitting version, a dependency failed) shows as failed with the new cause waiting.
  4. Dependents park. An object whose dependencies are not all live waits with no timer and no backoff, and is woken by events: a dependency changing state, or a name becoming usable on a host.
  5. broken means the object's own fault. Only its own code and cycles break an object; whatever it waits for is waiting.
  6. Startup needs one short gate, not a barrier. Requests wait only for the host's facets to be published, which is synchronous; that ends the startup deadlock. Whether load then also waits for first outcomes is the owner's call.
  7. One gap in cycle detection needs a choice. Objects on two hosts that start at the same moment and need each other are caught today only by a deadline. A probe can walk the waiting edges and find the ring without failing anything (recommended); a narrowed deadline is simpler but polls, misses a ring, or never finds the cycle at all.
  8. Only callers and own work keep clocks. Getters, parked calls and an object's own steps keep their deadlines; waiting for a dependency has none.

Words used throughout

A host is one participant (the server, a session worker, a browser tab). A provider is what serves a type or a registry on a host: a facet registered it with host.serve. A request is what a reference stands for: a type or registry, its params, the principal it acts as and the consumer's contract version. Its holder made it and owns it: an object's attempt (self.get, self.registry), a call (ctx.get), outside code (host.get, host.hold) or a peer host (a hold arriving over a link). A request is bound when it points at an object (here) or a hold (over a link), and unbound with a reason otherwise. An attempt is one try at activating an object: its factory, its requests, its natives. A dependency is a request an attempt needs live before it may go live. An attempt is parked while one of its dependencies is not live. A publication is the moment a host makes its facets' declarations visible: the setups of load, the commit of a reload, the commit of an install. A wake is an event that makes the resolver look at a request again.

The running example is a small p3: a server S with the session catalog and the search feed; a worker W for session S1 with the harness, code mode, the notes store and the search indexer; and a browser tab T that shows the notes. The plugins are core, models, codemode, notes, search and sharing.

I

Five Answers to One Question

What Chord v2 does today when a dependency is missing, and why the answers disagree.

Chord v2 was built slice by slice, and each slice answered "the provider is not there" for the case in front of it. Slice 1 made self.get of a type nobody serves throw, because a typo in a type name should fail loudly. Slice 3b made remote holds survive link drops, so a missing provider on another host became a refused hold that the consumer retries. Slice 8 made self.registry a dependency that waits for a value. Each answer was reasonable alone. Together they give five outcomes for one situation.

Declared as The provider is missing Today
self.get(LocalType) no facet serves it self.get throws, so the factory throws: the object is broken
self.get(RemoteType) the worker does not serve it the hold is refused broken; the dependent is transient and retried every 1 to 60 seconds, forever
self.registry(R) no plugin serves R transient, woken at R's first value only
self.registry(R), the reader newer than the provider broken
a reload removes the type every holder gets gone: ended for good

The differences are not about the situation. Whether the notes plugin is missing on this host or on the worker, the notes view cannot work until someone installs it. Yet in one case the view is broken until a reload, in the other it polls the worker every minute for the rest of the session, and the reload that finally brings the plugin back cannot revive a reference that got gone.

The deadlock without a cycle

The startup barrier has a worse problem. Sol reproduced it against the current code (/tmp/dep-graph-sol-barrier.log).

C has no dependencies and is registered the moment S's setups ran. Its hold waits anyway, because incoming holds wait for pendingLoad, and pendingLoad is the whole of load: the setups and the barrier that waits for every host-lifetime object, A included. Two jobs share one promise. Holds only need the first ("are the types registered?"); the second ("has every plugin had its first try?") is for the app. Mixing them makes an acyclic chain across two hosts wait until a timeout fires.

Timers standing in for events

Both problems have the same root. Where Chord does not know when something will change, it polls or waits for a deadline: the identity backoff retries a dependent whose remote provider refused it; the activation deadline breaks the startup knot; the same deadline is the only answer to two objects on two hosts that start at the same moment and need each other, a cycle the activation chains cannot see (design §6, "Known limitation").

A timer is the right tool when nothing else can tell Chord that the world changed: a disk that may be back, a worker process that may start this time, a silent transport. It is the wrong tool when an event exists or can exist. A missing plugin comes back through a reload, which is an event on the host that serves it. A dependency going live is an event. A link opening is an event. The model below uses those events and keeps timers only where no event can exist.

II

Requests That Wait

A reference is a request with a holder; it outlives every provider it meets.

The first change is a separation the code makes only halfway today: between what a reference asks for and what currently answers it. When the notes view on W does self.get(NoteStore, {}), it asks for "the NoteStore of this host, as the host, at contract version 3". Which object answers is a second question, and the answer can change: no object yet, an object activating, a live one, a failed one, none again after a reload, a new one after the next.

A request and its holder

A request is the asking part: type (or registry), params, principal and the consumer's contract version. Every request has exactly one holder, which made it and is the only one that ends it.

Holder Made by Ends when
an attempt self.get, self.registry, a keyed pin ref.notes.at(key) the attempt ends (its object ended, or a reload replaced it)
a call ctx.get the call settles
outside code host.get, host.hold, host.registry release(), or the getter gives up
a peer host a hold arriving over a link the peer releases it, or its link or origin closes
any of them revocation of its principal; its own host closes

That list is the whole of how a request ends. A request never ends because its provider is missing, went away or does not fit. Today it does in two places: a self.get of a type nobody serves throws before the request exists, and a reload that removes a type sends gone. Both go.

The address decides where

A request goes to one place, and the address decides which. For a local type, the place is this host. For a remote type, the consumer computes the address from the params with its own contract's hostAddress function (design §3; placement until 2026-10-29): Notes { session: "S1" } is placed on Session { id: "S1" }. If that is this host's address, the request goes here; otherwise over the route for that kind, or over the parent link.

Until 2026-10-29 the code checked something else first: whether the type is registered here. A type placed on this host but not registered yet was sent over the parent link, which is wrong twice. Sol's example: the server has address Server, the catalog type is placed on Server, and no facet serves it yet. That code, Placement.reference (host/placement.ts, now host/destination.ts), sent the server's own request over a parent link the server never had, and when the catalog plugin was installed later, nothing woke that request, because it was never registered as waiting here. The rename removed the first half; slice 7 builds the wait.

The rule, from the reviews (Sol B1, Astra F1): the destination never depends on what is registered when the type names an address. A request placed here whose provider is missing is unbound here, waiting for the name. A version check compares the consumer with the provider actually selected, never with a same-name registration on the consumer's own host (today #assertRoute does that before choosing the destination, so worker W1 serving Notes v1 rejects a Notes v2 request placed on W2, which serves v2).

Every remote type declares its hostAddress (owner, 2026-10-29, who also renamed placement to it). Until then remote() allowed leaving it out, a leftover of slice 3a, which built remote objects over one link before host kinds existed; such a type went "here if served, otherwise the parent", which needed its own fallback and a re-placement when a tab that loads before it connects gets its first parent link (Opus, Sol). Opus and Fable proposed making it required; the owner agreed.

What the check finds

Once placed, the provider found there is checked: served, a fitting version (the current one or an accepted older one, with the fingerprint computed from the provider's own history), authorize, and the provider's own host-address check. The request is then bound (to an object here, or to a hold over a path), or unbound with a reason:

The check finds The request Shows
a fitting provider bound its object's state
this host has not published its facets yet unbound unpublished loading
nobody serves the name at its address unbound not_served failed { waiting }
no fitting version, a fingerprint that differs at the same version, a host address the provider computes elsewhere unbound version failed { waiting }
the registry is served, but its first compose, or the reader's version mapping, threw unbound compose failed { waiting }
the provider host is installing, and the hold does not fit its current code unbound installing, at the provider loading
the path has no link (a drop, a route resolving) waits on the path loading
authorize refused, or the params are invalid refused failed { broken }, as today

The reasons that wait for a name (unpublished, not_served, version, compose) are kept in an index under that name, on the host that decided them: the consumer's host for a local request, the provider's host for a hold that arrived over a link. The provider already keeps such holds today as refused (remote/hold.ts), and retry re-runs them. installing belongs to the provider host's own install; no_link lives on the path, where the next link holds the request again, as today. Every index drops an entry when its request ends, so a released getter, a closed tab or a revoked guest leaves nothing behind. A refused request (no authority, bad params) is never indexed: a later publication cannot grant authority.

The publication gate

There is one short gate. Before a host has run its facets' setups, it does not know what it serves, so it cannot tell "not served" from "not registered yet". A worker connects to its parent before it loads (W6), so holds can arrive in that window, and p2's web shell holds references before its own load resolved.

So a request made on a host, or arriving on its links, before the host's first publication is not placed at all: it is unbound unpublished and shows loading. The publication places it. Without this gate the request would be placed by a half-empty registration table (Fable's trace: W1's own Notes sent over the parent, relayed back by the server, forever), and a tab would see "not served" during every worker start (Opus's trace).

The gate is not the barrier. It lasts only until the setups ran, and the setups are synchronous code at the start of load: they register types and registries and contribute, and wait for nothing. That is the difference that ends the startup deadlock (chapter VI).

III

Loading or Waiting

What a reference shows while it is not live, and why a missing plugin is an answer rather than a spinner.

ref.state keeps its four kinds: loading, live, failed, ended. What changes is one new kind of failure cause.

type RefState =
  | { kind: "loading" }
  | { kind: "live" }
  | { kind: "failed"; cause: FailureCause; retryAt: number | undefined }
  | { kind: "ended"; error: ChordError };

type FailureCause =
  | { kind: "transient"; error: ChordError }   // the object's own effect failed (an open, a follow): backoff
  | { kind: "broken"; error: ChordError }      // the object's own code, a cycle, or authority: retry() or a reload
  | { kind: "waiting"; error: ChordError };    // not the object's fault: woken by an event, never by a timer

The mapping

Whether a request that is not live shows loading or failed { waiting } follows from what it waits for:

The request is ref.state Calls on it
bound, its object activating, or parked with no failed blocker loading park, bounded
unbound unpublished or installing, or its path has no link loading park, bounded
unbound not_served, version or compose failed { waiting }, no retryAt reject at once with the cause
bound, its object failed failed with the object's own cause and retryAt, as today reject at once
bound, its object live live run
ended by its holder, revoked, or its host closed ended reject

The intuition is "is something under way?": an activation, a reconnect, an install, a load. When something is under way, the reference waits and calls park; when nothing is, the reference says what is missing and calls fail fast. The reviewers pointed out that "under way" is not something Chord can observe in general (a parent reconnect is the app's, a resolve may hang), so the table is the rule and the intuition only explains it.

A link drop and an unload, side by side

The owner's point was that a link going away is like the provider's plugin unloading. For the request they are the same: it stays, it keeps its last values readable, it binds again when a provider is reachable, and its holder notices nothing but the state. They differ in what is under way.

The notes view on T, once through a link drop and once through an unload on W

Live

T's notes view holds Notes { S1 } on W through the server. ref.state is live; the view renders the notes.

The link drops

W's link to the server closes (a crash, a network change). The request on T stays; the path has no link: unbound no_link, ref.state loading. The last notes stay readable. A call made now parks, bounded by readyTimeout. Calls already sent fail and are never resent: their outcome is unknown.

The link comes back

The route resolves again, the request is held anew on the new link, bound arrives with a fresh snapshot. live. Parked calls go out in order.

The plugin is removed on W

A reload on W removes the notes plugin. The provider's object ends as today: its natives close, its callers are rejected at once, its handlers drain. The request on T does not end: W sends failed { waiting, not_served } on the bound hold, which unbinds it. ref.state is failed { waiting }; the last notes stay readable; new calls fail at once with "notes is not served on Session S1".

The plugin comes back

A later reload on W serves Notes again. The publication re-runs W's refused holds for that name: loading, then bound. T's view is live again without having done anything.

One difference must stay: calls already sent. When a link drops, a sent call's outcome is unknown, so it fails and is not resent. When a plugin unloads on the same host, its handlers are drained on the old code (design §21). Location decides nothing else.

Review: a third cause kind, or not

Opus and Fable recommend waiting as above. Astra would keep two kinds and mark event-waited failures as transient with no retryAt (today's wire already carries a transient cause without retryIn, remote/remote-object.ts), so no kind is added; the cost is that transient then means two things, a backoff under way or an event awaited. Sol would show loading with a diagnostic; that parks every call on a missing plugin for 60 seconds and spins forever in the UI. The draft recommends waiting. Owner decision 3.

IV

Parked

An object whose dependencies are not all live waits, with no timer, and goes on the moment they are.

The owner's instinct was that an object is parked until its dependencies all cleanly resolve. This chapter makes that exact: what a dependency is, what the parked object shows, what it keeps, and where parking ends.

What counts as a dependency

A dependency is a request an attempt makes in its factory and needs live before the object may go live:

  • self.get(Type, params), local or remote: one rule for both;
  • self.registry(R): a registry at the reader's version (chapter X);
  • a keyed pin, ref.notes.at(key) on another object's keyed member: the key must be loaded.

Two things are not dependencies. self.follow(attach) is the attempt's own step: its attach runs Durable's code and may fail like an open, with the object's own transient failure and backoff (a follower that wants to recover the moment a new harness appears declares self.retryOn on the registry it reads the harness through). And a ctx.get in a method is not part of the object's activation at all: it is the call's request.

The dependency check

An attempt runs its factory, hydrates its persisted singletons (they are the object's documents, kept across attempts, as today), makes its requests, and is parked while any dependency is not live (and hydrated). What it shows follows its dependencies:

Its dependencies The parked object shows
any loading, none failed loading
any failed failed { waiting, "waiting for X: <X's cause>" }, no retryAt; the message keeps the nearest blocker and the root cause within the 500-character rule
one failed with invalid/cycle (a dependent off the ring) broken with the same error: it would wait on a ring that never heals by itself
one ended (revoked, or its host closed) broken with that error: the request cannot come back; retry() or a reload makes new requests

When every dependency is live, the attempt passes the dependency check and runs its own steps: its natives in declaration order, its follow attaches, the member checks, its derives. Those are bounded by its own readyTimeout deadline, as today. Then it goes live.

The dependency check is the boundary between waiting and working (Astra's F3). Before it, the attempt holds no natives; after it, a dependency that leaves live is treated as after live (R18): the attempt goes on, and its calls through that reference meet the reference's state. So a parked attempt never holds a native, and an attempt that opened a native is never parked. It is not a rule of its own: it is R18's rule for live objects (a dependency that goes away leaves the object live; same-host calls in flight finish, remote ones fail, new calls meet the reference's state), applied from the dependency check on. Without that boundary a contributor unloading while the attempt opens its natives would leave it half open and parked, or force a seal, a drain and a fresh attempt for a dependency the object may not even use at once.

No clock while parked

A parked attempt has no dependency deadline and no backoff. Its readyTimeout deadline is paused while it is parked, as eager migrations already pause it (attempt.ts, deadline.pause()), and resumes with the budget left when the attempt passes the check. Today a dependency that does not go live within 60 seconds fails its dependent transient, which then retries with backoff from 1 to 60 seconds. Both go: the dependent is woken when the dependency changes, and the time a dependency takes is bounded where it runs, by that dependency's own steps.

What a parked attempt keeps

It keeps its documents (the object's), its declarations and its requests (R18's holding today), and its seal token. It keeps no native. It ends with its object: when its last holder releases it, or, for a host-lifetime object, when its plugin is removed or the host closes. A parked object with params that nobody holds any more ends and releases its requests, so a whole parked chain goes when its top is released.

broken is the object's own fault

After the model, broken means exactly three things: the object's own code failed (a throwing factory, a derive that throws at activation, a hydration or migrate that fails, a document fingerprint mismatch, an open that throws broken(...)), the object is on a cycle, or it lost its authority (forbidden, a dependency that ended). Everything an object waits for, including a provider that is itself broken, makes it waiting. The difference matters for recovery: a broken object needs ref.retry() or a reload of its own plugin; a waiting one recovers by itself when what it waits for recovers.

Retry passes on

A Retry button on a waiting object should do something. Opus's trace: the tab's Panel waits for the server's Dash, which waits for Catalog, which is broken by a factory bug that a configuration fix would heal at the next attempt. The user sees "waiting for Dash: waiting for Catalog: …" and presses Retry. Today Panel would re-check, find Dash still failed and do nothing.

So ref.retry() on a failed { waiting } object retries its failed blockers, hop by hop, with the existing retry message over links: it retries the blockers that are broken or transient (the only ones a retry can change), passes through the waiting ones, and leaves the rest alone. Each retry carries an operation id, so a diamond of dependencies retries a shared leaf once. Retry of a broken or transient object starts a new attempt, as today. A retryOn value call still retries a failed object as slice 8 decided; while the object is parked waiting, it does nothing: its dependencies decide.

A reload of the parked object itself

The parked attempt's factory never runs again while it is parked, with one exception: a reload of the object's own plugin replaces the parked attempt with the new factory's attempt, as one handover: the new requests are made and bound first, then the old ones released (Astra: a dependency held only by this object, unchanged by the reload, must not end in between; today's #activate already binds before #releasePrevious). If the new code no longer declares the missing dependency, the object can go live at once.

After live, nothing changes

R18's second half stays: once an object is live, a dependency that leaves live (a link drop, a removal) leaves the object live. Its calls that use the dependency get the dependency's state: they park while it is loading and reject while it is failed. Reactivating every live consumer on every dependency loss would turn one worker disconnect into closed natives, withdrawn contributions and aborted jobs on the server; the reviewers agreed it should not.

V

What Wakes Whom

Two kinds of event replace every poll and every dependency deadline.

A model without timers lives or dies by its wakes: a wake that is lost leaves an object parked forever. So the wakes are kept to two kinds of event, each with one owner, and every unbound request and every parked attempt is subscribed to exactly the events that can change it.

Event Who is told Exists today?
a target changes state: an object goes live, loading or failed, or gets a new cause; a hold receives bound, loading or failed, also after a re-hold on a new link the requests bound to it, and the attempts that depend on those requests partly: dependencyLive covers only "goes live"
a name becomes usable on a host: a publication (load's setups, a reload's commit, an install's commit) serves a type, a registry or a version; a registry composes or maps a value at a version the unbound requests indexed under that name on that host; a refused hold re-runs its start and sends loading, then bound or failed partly: refused holds and retry exist; the re-run at publication is new; a registry wakes only at its first value

Every change, not only "live"

Draft 1 woke a parked attempt only when a dependency went live. Astra, Fable and Sol found the same hole: a dependency that moves from loading to failed, or from one cause to another, leaves its dependent showing a stale state, and a dependent that should now show failed { waiting } keeps parking calls. So a parked attempt re-evaluates on every state change of any of its dependencies and updates what it shows. It leaves parking only when all of them are live. Its factory never re-runs on a wake.

Three details keep this correct and cheap:

  • Coalesced, after the batch. Wakes run after the batch that caused them (a publication, a commit, an inbound bound), once per object, so a commit that changes three dependencies wakes their dependent once, and no factory runs inside another owner's batch.
  • Remembered. A change that arrives while the attempt runs its own steps or tears down is remembered and applied after (today's R18 wake memory, generalized).
  • Indexed by name. A publication touches only the unbound requests waiting for the names it serves. A reload of notes never looks at requests waiting for search.

Across a link: no new message

The wake across hosts needs no new message kind. Today a provider keeps a hold it could not serve as refused, and a retry from the consumer re-runs its start. The model adds one thing: the provider re-runs its refused holds itself, at its own publication, for the names that publication serves.

Two existing messages change: failed carries the new cause kind waiting, and loading and a waiting failed carry the provider's attempt id for the cycle probe (chapter VIII). The pinned list of causes and its test change with them, and PROTOCOL_VERSION stays 1 until p3 ships.

Registries

A registry reader is woken at every transition of the registry's value at its version to usable: when the registry is served, when it composes for the first time, when an older reader's mapping succeeds again after it failed. Today RegistryValueSource wakes only at the very first good value (#valued), which a registry whose provider is removed and added again would never pass a second time.

VI

Starting Up

The barrier did two jobs with one promise; separated, the deadlock disappears.

load does three things today: it runs every facet's setup, it publishes them (types served, registries composed once, contributions in their tables), and it waits until every host-lifetime object has had its first outcome. The promise of the whole thing, pendingLoad, is also what incoming holds and host.hold wait for. That is the startup deadlock of chapter I.

Publication first

The model splits load at the publication:

  1. Setups. Every facet's setup runs. Setups only declare: host.serve, self.contribute, host.references. They are synchronous and wait for nothing.
  2. Publication. All declarations become visible at once, in one batch: types served, registries served and composed once, contributions in their tables. Nothing activates inside that batch.
  3. Wakes. After the batch, every request that waited for the publication (unbound unpublished) is placed, and every unbound request for a name the publication serves is re-evaluated.
  4. First outcomes. The host-lifetime objects activate. Whether load waits for them is the barrier question below.

Requests wait for step 2 only. Since the setups wait for nothing, a host always reaches step 2, and a request from another host can never wait for this host's activations. Chapter I's knot comes apart:

The barrier: (a) or (b)

What is left of the barrier is the app's question "has every plugin had its first try?". R17 needs it: p3's base code resumes the harness after load, so the first turn sees the tools of every plugin that loaded. Two shapes are on the table.

(a) Chord keeps it. load resolves when every host-lifetime object of this load has a first outcome: it is live, failed by its own cause, or parked with no blocker that is a local object still without its first outcome. In code, per object:

const firstOutcome = (o: Obj): boolean =>
  o.live || o.ownFailure || (o.parked && o.blockers.every((b) => !b.local || firstOutcome(b)));

So CodeMode → Harness, both local, waits until the harness had its outcome: code mode is parked on a local object that is still in its first attempt, so code mode is not done. A wait on another host, or on a dependency that failed, ends the first pass: the barrier never waits for another host, a retry, a later contribution or a reload. The signal is separate from the readiness dependents wait for (Sol: resolving that for a parked object would let its dependents open natives too early), and it is counted once per object, never reopened by retries. An object of the cohort that ends before its first outcome (its plugin removed, the host closing) settles its entry as ended, and host.close settles a load that is still waiting (Astra).

(b) The app keeps it. load resolves after the publication. Chord adds host.startup, a watchable of the host-lifetime objects and their first outcomes with causes; base code decides when to resume (Fable). The tracker is the same; only who awaits it changes.

Three of the four reviewers recommend (a): the activation graph is Chord's, and every app that wants R17's behaviour would otherwise build the same cohort tracker. Fable recommends (b): the policy belongs to the app, and p2 already has three different ones. Owner decision 1.

What the barrier does not promise

Neither shape can promise that every tool is there for the first turn, and the model does not pretend it can. Sol reproduced it against today's code (/tmp/barrier-sol-first-outcome.log): object A's open fails on its first attempt (A's first outcome); B goes live and contributes; the registry changes and retryOn wakes A for a second, slow open; load resolves with only B's contribution in the table. Tools found in onLive (MCP) arrive later by design. What a first turn really needs (a model, an environment, a reconciled working directory) is p3's explicit admission check, as p2's whenRegistered and its harness prerequisites are today.

What p2 does today

p2 does not wait for all host objects before the first turn. Its worker (apps/p2/src/hosts/worker.ts) loads with awaitHostObjects: false, waits for the harness, resumes Durable, tells its parent control.ready() and only then awaits host.ready(). It has to: its subagent tools and the search indexer need server types, and the server admits the worker's link only after control.ready(). A barrier before that point would deadlock, exactly as in chapter I (Astra and Sol, independently).

VII

Plugins Coming and Going

Removals, versions and rollouts across hosts, as events the requests wait for.

Slice 7 brings reload and rollout, and with them the cases where a provider disappears on purpose. Today's design handles them with their own mechanisms: gone when a type is removed, a final contract_mismatch when a version is dropped, updating with a deadline during a rollout. Under the model all of them are one thing: a request becomes unbound with a reason, and the event that fixes the reason wakes it.

A type removed, and served again

A reload that removes a type ends its objects as today: natives close with reason end, callers of running calls are rejected at once, handlers drain. What changes is what happens to the requests that pointed at those objects.

  • Over a link, the provider sends failed { waiting, not_served } on the bound hold. A failed on a bound hold unbinds it (Fable: one message, one rule; the consumer applies it as today's #startOver plus failed). The provider detaches the hold's sources and drops its unsent pending ops and any queued bound. Two things it must not do (Sol): free the ack slots of bound and state messages already sent, which stay counted until their ack or the link's loss, or resend calls, which fail and free their slots once.
  • On the same host, a Binding whose target ended by removal becomes unbound and accepts a second bind. Its member sources re-bind by name (one frame from the last value, as on a restart today), keyed pins re-pin, parked calls flush or reject, presence lists it again. This is the one genuinely new piece of machinery in the model (Fable, Sol): today bind runs once per binding, and the ended object is forgotten.

When a later commit serves the name again, the publication wakes every request indexed under it, on every host that holds one, and they bind as if nothing had happened.

A version no longer accepted

A reload can also keep the type and stop accepting an old version (it drops accepts[1]). Draft 1 ended the provider object then; Sol and Astra caught it: the object, its documents, its jobs and its holders on the current version are fine. Only the requests on version 1 become unbound version. The object's own plugin reload still restarts it if it has natives (§21), as for any reload.

A type that moved

A plugin can move a type from the worker to the server by changing its hostAddress. A consumer's request carries the address its own code computed, so the provider appearing on the server cannot wake it: the request is not waiting there. The old host answers not_served; the consumer's own reload, which brings the new hostAddress, makes a new request. The model adds no redirect: moving state between hosts is a deliberate migration, not something Chord guesses.

Rollouts across hosts

A rollout installs a revision on the server first, then on the workers, then on the tabs (design §21). Between those installs, hosts run different code. The model needs only one rule for that: each host knows its own install, and nothing more.

  • A provider host that is installing keeps holds that do not fit its current code as unbound installing: the consumer sees loading, its calls park. When the install ends, by its commit or by its rejection, the host re-evaluates them against the code it now runs (Astra, Sol: a rejected install must not leave them asleep).
  • A provider host that is queued but not installing yet answers a mismatch with failed { waiting, version } until its install commits and wakes the request. That is a visible blip of at most one install; Opus judged it acceptable, and avoiding it would need revision fields in every answer.
  • Installs never wait for activations. An install that waited for its objects to go live would deadlock a rollout that runs in the other order: the worker's objects wait for the server's new types, the server's install waits for the worker.
  • A host whose own install was rejected fails its own requests at once with the reason (design §21).

Old calls

Calls that were running when the reload came follow §21 unchanged: a pure swap lets them finish on their old handles; a native restart drains them first; a removal rejects their callers at once and drains their handlers. Chord never resends a call.

VIII

Finding Cycles

Without the deadline, the one gap left in cycle detection needs an answer: a narrowed deadline, or a probe.

A provider that never appears keeps its dependents parked, and that is visible: they say what they wait for. A cycle is different: A waits for B, B for A, every provider exists, and still neither can go live first. Today Chord has two detectors and a deadline. On one host, self.get follows the waiting edges of activating objects. Across hosts, a hold carries the activation chain it was made in, and a provider refuses a hold whose chain contains the object being activated. The gap is documented (design §6): when A on the server and B on a worker start at the same moment, the holds carry [A] and [B], neither finds the other, and both fail at the 60-second deadline. The model removes the deadline, so the gap must close.

Two answers

The owner decided this gap once already. On 2026-10-24, after the slice 4b reviews, he made simultaneous starts across hosts "a documented limitation: they time out transient and retry; no probe message." That decision assumed the activation deadline. The model removes the deadline for dependency waits, so the decision needs one of two continuations, and this one is his (Owner decision 6):

  • (A) The 4b decision, narrowed. One deadline stays: an attempt parked on a dependency held over a link, whose target attempt is known and still activating or parked, fails transient after its readyTimeout and retries with backoff; its next attempt usually starts after the other side, and the activation chain in its hold finds the cycle. Working it through showed the catch. A target that is parked is the common case of a chain across hosts waiting for a missing plugin: a tab's view on a worker object that waits for an uninstalled type. Those dependents would time out and poll again, as today, so "local = remote" would stop at the link. Narrowing the deadline to targets that are loading avoids the polling but misses a real ring: A and B on two hosts wait on each other, and B also on a missing X. B is failed { waiting }, so A is too; when X appears, both stay failed { waiting } on each other, with no deadline to break it and no chain to see it. Worse (Fable, round 6): an object's activation chain is fixed when it is created and its instance id survives retries, so a retried attempt sends the same hold with the same chain; two simultaneous starts time out and retry in lockstep and are never found. The deadline would poll without finding what it is for.
  • (B) The probe (recommended, pending review) described in the rest of this chapter: no deadline at all, one new message kind, and the most intricate rules in the model. Five review rounds found a counterexample in each of the first four drafts; the version below answers all of them, with one choice left in rule 5. Slice 7 would prove it with tests before the old deadline goes.

The rest of the chapter describes (B): it is the answer that keeps one rule on both sides of a link, and its review history shows what a complete answer takes.

Why a growing chain is not enough

Draft 1 proposed letting chains grow: an activating object that receives a hold with a chain sends the grown chain on to its own dependencies. Astra and Sol showed two flaws. Chains are cut at 32 entries today, so a ring of 33 objects started at once is never found: the chain that reaches each object is always missing that object's own id. And a chain records ancestry, not the current wait graph: once A stops waiting for B, B's chain still names A, and a later wait of B on A looks like a cycle that is not there.

(B) The probe

The model uses an edge-chasing probe (the idea of Chandy, Misra and Haas), for the rings that cross a link; on one host the self.get walk stays, synchronous and exact, as today (Opus). Five rounds of review shaped it; the rules below are the result.

  1. Attempts, edges, tokens. Every attempt has its own id, minted per attempt: a retry or a reload is a new attempt (today the id is per instance and survives retries). A wait edge runs from a parked attempt to the activating or parked attempt it waits for, through a bound request. Unbound waits and registry reads are never edges: they are not deadlocks, they end when a provider appears. Every edge carries an edge token: a number from a counter the attempt keeps, never reused, replaced by a fresh one on any interruption or change of that edge (Astra, Sol: two requests to one object are two edges): a new target attempt (also when a local target retries without a re-bind), any loading on a bound or pending hold (a relay re-holding upstream included), an unbinding, a rebinding, a re-hold after a reconnect. An attempt is parked for one interval only (once past its dependency check it never parks again), and attempt ids are never reused. A provider tells its consumers which attempt they wait for on every answer that is not bound: loading { hold, attempt }, and a waiting failed { hold, cause, attempt }.

  2. A search per edge change. Whenever a parked attempt gets a new edge, or a new token on one, it starts a search: probe { kind: "search", round, initiator, trail }, with the next number of a counter the attempt keeps, its own attempt id, and the trail of (attempt, edge token) hops crossed so far, starting with its own. A ring closes at its last edge, and that edge's source starts the search that finds it (Sol's simplification after Astra's counterexample: a ring that forms only after a reconnect, with unchanged attempts, is otherwise missed). Searches are coalesced per batch. On the same host a probe is a call on the target attempt, forwarded through a queue rather than recursion; over a link it is a new message, probe { hold, to, ... }, consumer to provider, relayed by hold id with the origin. Probes are honoured on parent and route links and dropped on child links (accept), whatever trusted says (Opus): a tab learns attempt ids from loading and could otherwise break an object with a forged probe, while a worker whose transport is untrusted must still take part. Clients serve no remote types, so no real cycle runs through one.

  3. Forwarding. An attempt that receives a search drops it if to is not its current attempt or if it is not parked. If the initiator is itself, the search came back. If the attempt is already in the trail, it drops it: a ring that does not contain the initiator is found by its own members' searches (Opus). Otherwise it forwards it along every wait edge, appending itself and the edge's token to the trail, but only if its round number is higher than the one it stored for that initiator; then it stores it. A late, older round is dropped even if this attempt never saw it: its initiator has moved on (Astra, Opus). The seen map holds one number per initiator, up to 256 initiators, and goes with the attempt.

  4. The check. The initiator accepts a returned search while it is still parked, whatever round it carries (Astra: a re-search must not invalidate an older search still under way); the check decides. It verifies its own hop, then sends a probe { kind: "check", round, trail } along the recorded trail: each hop passes it on only if it is still that attempt, still parked, still holding the recorded edge token, pointing at the next hop's attempt. The check follows the trail by position, ignores the seen map and dies on any mismatch. When it returns, the initiator verifies its own hop once more. If the check comes back, the initiator fails broken invalid/cycle, naming the path from the trail, and today's propagation breaks the other activating objects on the ring and the dependents off it.

  5. No silent loss. Astra found the last hole: a search can reach an attempt first by a shortcut and be dropped there when it arrives again along the ring itself; if the shortcut breaks before the check, the check dies and nothing is left to find the ring. Round 6 tried dead notices sent back to the initiator. Sol and Astra showed that reliable notices need recovery state per search that the seen map's eviction may not drop, and that a long- parked attempt would otherwise keep for every initiator that ever passed: a leak, unless every search gets a full lifecycle with completion and cancellation. So rule 5 is a choice, part of Owner decision 6:

    • (B1) Re-search with backoff (recommended). An attempt parked on a remote attempt starts a fresh search again after a backoff, 1 second doubling to 60, reset by an edge change, whether it shows loading or failed { waiting }; the timer stops when the attempt leaves parking. No dead messages and no recovery state; eviction only costs work; a new search starts within one backoff period, so every stable ring that crosses a link is eventually found (no wall-clock bound: delivery is only fair). The timer runs as long as the attempt stays parked on a remote attempt: a view on a worker object that waits for a missing plugin re-searches every minute until a reload (Fable). The timer sends probes only: it never fails an object, never re-holds, never polls a provider. Its cost is one probe per parked remote dependent per period, which dies at the leaves of the downstream wait graph.
    • (B2) Events only. Every search is owned until it settles: branches report completion or abort along their trails, a dropped probe answers dead { initiator, round } by a reverse route, edges remember the searches they carry until those settle, and an initiator that ends or moves on cancels its old search. Complete without any timer, bounded by the searches in flight, and the most intricate protocol in Chord; not yet specified to the reviewers' satisfaction.

    Sol's correctness reference, enumerating every simple trail without dedupe, never suppresses a ring copy, but its work is exponential on chains of diamonds.

Why a reported ring existed

Draft 4 confirmed a cycle with a second, independent round. Sol showed a schedule in which two rounds pass through two different stale paths, each of them half replaced by reloads, and together report a ring that never existed at any moment (/tmp/model/sol-probe4.log). The check closes that: it walks the very path the search recorded and demands that every edge still carry the token it had when the search crossed it. A token changes on every interruption and is never reused, and an attempt is parked for one interval only, so an edge cannot vanish and come back unnoticed (Fable and Opus checked the argument in round 5). Every edge of the trail therefore existed from the moment the search crossed it until the moment the check crossed it; the search crossed all of them before the check began, so when the check began, every edge of the ring existed at once. In Sol's schedule the check dies at B, whose edge now points at another attempt.

Why every ring is found

Under an eventually stable wait graph and fair delivery (endless edge churn can keep invalidating searches), and with rule 5's (B1) or (B2) for a search suppressed behind a path that broke, a ring of parked attempts is closed by its last edge. When that edge appears, its source starts a search; every other edge of the ring exists at that moment, and every attempt on the ring waits, directly or not, on the source, so none of them can go live before the search and its check come back. Rings of any length are found, through local and remote edges alike. On a graph without cycles, searches die at the leaves; on a diamond, the seen map drops the second arrival.

What it does not promise

  • A ring broken up just after. A ring that existed when the check began may be broken up by a reload, a retry, an unbinding or a revocation a moment later; it is still reported, because it did exist. The objects it breaks recover as every broken object does, through ref.retry() or a reload of their plugin.
  • Linear work under every schedule. With more than 256 initiators passing one attempt at once, an evicted entry lets a search be forwarded again, so in an adversarial schedule the work can grow with the number of simple paths (Astra, Sol); never endlessly, since a search never revisits an attempt already in its trail. The seen map's memory stays bounded. Each edge change costs one search that crosses each downstream edge once, and one check per returned search; with (B1), every attempt parked on a remote attempt adds one search per backoff period, also while an acyclic chain only waits for a missing plugin.
  • Constant message size. A probe carries its trail, so it grows with the length of the path it crossed; a search that returns carries a trail as long as its ring. That is the price of the check; chains were cut at 32, trails are not, because the trail is the proof.
Review: the state of (B)

The check's argument (a reported ring existed at the moment the check began) was confirmed by all four reviewers in rounds 5 and 6, given exact edge identity (the tokens). Completeness under an eventually stable graph holds with (B1); with (B2) it holds once the search lifecycle is specified, which no draft has done yet. If the owner chooses (B), slice 7 keeps today's deadline for activations waiting across links until the probe's tests pass: long rings, diamonds, a ring closed after a reconnect with unchanged attempts, Sol's phantom schedule, Astra's broken shortcut, Sol's eviction schedule, 300 concurrent initiators, edges added and removed, reloads, relays, forged probes.

IX

Callers

Getters, holds and calls get one rule: wait while something is under way, answer when nothing is.

Objects park; callers do not. A caller is code that wants an answer: a method that needs a reference now, a tool that runs inside a turn, a tab that wants to render. The model keeps their deadlines and gives them one rule.

host.hold

host.hold returns a reference at once and never rejects; only invalid params throw, also before load. That was already the design; the model removes today's inconsistency: a missing local type throws after load but fails the reference before it. Now a missing local type gives loading before the publication and failed { waiting } after it, and the reference binds when a provider appears. A UI that wants to wait for something that may never come holds it and shows its state.

host.get, ctx.get, host.registry

The getters resolve when the reference is live. While it is loading, or failed { transient } (its object's own retry is under way), they wait, bounded by their readyTimeout. On failed { waiting } or failed { broken } they reject at once. On success, rejection or timeout their temporary wait goes; a rejected getter releases its request. host.registry returns the RegistryValue, whose watches and observers are owned as they are today; it has no release().

Opus's case decided the recommendation. A Durable tool runs chord((ctx) => ctx.get(SharingView, { session }), ctx) while sharing is not installed. If getters waited through waiting, the tool, and with it the agent's turn, would hang for 60 seconds and then fail; a call on the same reference would fail at once. With the rule above, the getter and the call give the same answer at the same moment. The rule has a cost Opus named: a dependent whose only blocker is an object recovering by itself (an SSH environment coming back, transient with its own backoff) is waiting, so a getter on the dependent rejects at once. Code that wants to ride that out holds the reference instead of getting it.

Owner decision 2: getters on waiting

Recommended: reject at once (Opus; Fable agreed in round 2). The alternative waits through waiting up to readyTimeout, which keeps "local = remote" just as well but makes every getter on a missing plugin cost its full deadline.

Calls

Calls on a loading reference park in order, each bounded by the reference's readyTimeout from the moment it was made (never renewed by a reconnect or a reload). Calls on a failed reference reject at once with the cause. A call already sent when its link drops, or when its object ends, fails and is never resent; its outcome is unknown, and idempotency is the app's (a requestId, as p2's chat does).

X

Registries

The same resolver on one host, with versions that can differ inside one revision.

A registry is host-local: its contributions are in-process values, often natives. Slice 8 made self.registry(R) a dependency that waits for a value. The model keeps that and folds it into the one resolver.

A reader's request

A reader asks for R at the version its own bundle was built against. The request is bound while R is served and has a usable value at that version: composed, and for an older reader mapped back by the provider's accepts[old].value. Otherwise it is unbound: not_served (no plugin serves R here), version (the provider does not accept the reader's version, or the reader is newer), compose (R is served, but its first composition, or this version's mapping, threw), or loading before the publication. The reader is woken at every transition of the value at its version to usable. S2's broken for a newer reader and S3's backoff go; so does #valued, the latch that woke readers only at the very first good value.

A registry waits for a value, never for a particular contribution: an empty table composes. "Wait until model X is there" is the app's admission check, not a registry rule; Durable's own "model unavailable" wait covers the harness.

Versions inside one host

Draft 1 claimed that a registry's provider and its contributors always run the same version, because a host installs a revision atomically. Astra corrected it: a revision is a set of plugin bundles, and a reload of the plugin that owns the registry leaves every other plugin's contributors and readers on the version they were built against. So the provider's adapters do real work inside one host: accepts[old].contribution maps an older contribution, accepts[old]. value maps the composition back for an older reader. A contribution without an adapter is left out and reported; a reader without one is waiting with version.

The last good value, and natives

Slice 8 decided that a throwing compose keeps the last good composition, so an extension point stays available while its owner fixes a bug. Astra found the case where that hands out something dead: the harness contributes its native H; a reader is live; the harness ends; the next composition throws for an unrelated reason; .value still returns the composition that contains the closed H.

The model narrows the rule: .value keeps the last good composition only while every contribution it was built from is still in the table. When one of them leaves (its contributor ended or was reloaded), the last good value is dropped and .value throws until compose succeeds again. And compose represents a missing contributor as a value (absent), never by throwing.

Review: drop the last good value, or fence the reads

Sol would keep the last good value and instead require natives in a registry to be looked up at use through their owner, without the guarantee. The draft takes Astra's narrower rule, because it keeps "a registry never hands out a native whose contributor ended" without asking every contributor to wrap its natives. It narrows a decision of slice 8, so it is the owner's: Owner decision 5.

XI

Keep-alive, Presence, Revocation

What a waiting request costs, who counts it, and who may end it.

A parked object and an unbound request are resources: they hold memory, they may keep a worker process alive, and they act for a principal. The model says how each of those works while nothing is bound.

Keep-alive and presence

A worker stays alive while host.activity shows work: references held over links, calls, jobs, lingering objects. A request that arrived over a link counts once in host.activity.references from its arrival to its end, bound or unbound. Without that, a session whose tab waits for a plugin that is not installed would see its worker stopped every idle period (five minutes in p2) and restarted by the next re-hold, forever (Opus). Presence is different: host.references lists only bound references, so "who is looking at these notes" counts viewers, not waiting requests.

Revocation

Revocation ends the requests of a revoked principal, bound and unbound, at every hop. A guest whose grant is revoked while their tab waits for a missing plugin does not get a reference later when the plugin comes back: the request is gone, and nothing revives an ended request (no publication, no Retry, no new grant). A refused request (no authority) is never indexed in the first place.

gone

gone remains for one thing: revocation. A provider host that closes closes its links and sends nothing (today's #close); its consumers see a link drop, loading, and hold again when the host comes back. A reload that removes a type sends failed { waiting } instead of gone (chapter VII).

Parked objects and their jobs

A parked object with params lives while it is referenced, like any object; when its last holder releases it, it ends and releases its requests, so a parked chain goes from the top down. A host-lifetime object parks until its plugin is removed or the host closes. Persisted job runs of a parked host-lifetime object are loaded with its documents, before it parks; run and finish start only once it is live, and the run count keeps the object as today.

Which timers stay, and why each of them has no event to replace it.

The owner expected the model to remove almost every timeout, "except maybe readyTimeout". That is what it does for dependencies. Every remaining timer bounds something no event can end: a caller's patience, an object's own code, a silent transport, a process that may start this time.

A Morning, Step by Step

The preface's Tuesday morning, played through under the model from the first click to the afternoon's rollout.

The rules of the earlier chapters meet in one story. Mario opens session S1 on his phone; the server S has the catalog and the search feed; the worker W for S1 has not started. W's plugin set has core, models, codemode, notes and search, but not sharing, which was removed last night; the notes view still asks for it. Later in the day a rollout brings sharing back, with a new contract.

Session S1 on Tuesday

1. The tab asks for the notes

T calls host.hold(Notes, { session: "S1" }). The address is Session { id: "S1" }, not T's own, so the request goes over T's parent, the server. S has a route for Session: it resolves the address by starting W. T's reference shows loading; the request waits on S's path until W's link exists.

2. W connects before it loads

W connects to S first (W6), then starts load. The hold for Notes arrives before W has published its facets: it is unbound unpublished and waits, still loading for T. Nothing is placed by a half-empty table, so the hold is not sent back to S.

3. W publishes

W's setups run, synchronously, and are published in one batch: Notes, NoteStore, Harness, CodeMode, Indexer are served; HarnessModels and HarnessExtensions are served and composed once. After that batch, the waiting hold for Notes is placed and binds; the host-lifetime objects start.

4. Code mode parks on the harness

CodeMode declared self.get(Harness). The harness is still opening Durable, so CodeMode parks: loading, no timer. The harness reads HarnessModels, which has a value (composed at the publication; the model runtime's contribution may arrive after), finishes its own steps and goes live. That state change wakes CodeMode, which passes its dependency check, opens its sandbox, goes live and contributes its tools.

5. The indexer waits for the server

Indexer needs the server's SearchFeed. The hold goes over W's parent; S published long ago, so it binds at once, SearchFeed is live, and Indexer goes live. Had S been starting at the same moment, the hold would have waited only for S's publication, never for S's activations: the startup deadlock of chapter I cannot form.

6. The first pass

With barrier (a), W's load resolves once Harness, CodeMode and Indexer had their first outcomes. CodeMode waited for the local harness, so its tools are in the table; base code resumes the harness, and the first turn sees them. With (b), base code would read host.startup and decide the same.

7. The notes view asks for sharing

Notes's factory declared self.get(ShareStatus), a local type of the sharing plugin. Nobody serves it on W: the request is unbound not_served, indexed under the name. Notes parks failed { waiting, "waiting for ShareStatus: not served on Session S1" }. T's reference shows the same; a call from T rejects at once with that cause. No backoff, no polling, no 60-second wait.

8. The phone changes networks

T's link to S drops. T's reference goes loading: its request stays, its last value stays readable, a call made now parks. A call that was in flight fails and is not resent. T reconnects; the request is held again on the new link; W answers as before: failed { waiting }.

9. Sharing comes back, with a new contract

In the afternoon a rollout brings the sharing plugin back at revision R+1, where Sharing on the server is v2. S installs first and serves Sharing v2. W's install is queued; nothing on W asks for Sharing yet, because the sharing plugin is not installed there, so nothing changes for W. (Had W still run a sharing facet built against v1 without an adapter on S, its requests would show failed { waiting, version } until W installed: the ordinary window of a server-first rollout.)

10. W installs R+1

W's install commits: a publication. It serves ShareStatus again: the index wakes Notes's request, which binds. ShareStatus activates, holds the server's Sharing at v2 (W's new code bundles v2), goes live, and Notes passes its dependency check, opens what it needs and goes live. T's reference becomes live without T having done anything.

What did not happen is the point. Nothing waited for a deadline; nothing retried on a timer; no reference ended because a plugin was missing; no host waited for another host's activations; and every waiting object said what it was waiting for.

Delayed facets across hosts, rollout windows, chains over three hosts, and the probe at work.

Open Questions

What the owner decides, and what slice 7's spec must still pin down.

The model replaces five answers to "the provider is not there" with one: the request stays, the dependent parks, an event wakes it. It ends the startup deadlock with a gate that lasts only for the synchronous setups, finds cycles with a probe instead of a deadline (or, if the owner prefers, one narrowed deadline), and keeps timers only where no event can exist. Four reviewers played more than 300 scenarios against five drafts; the catalog in the chapters before this one is a selection.

Decisions for the owner

  1. The barrier (chapter VI): (a) Chord's load waits for the first outcomes of this host's host-lifetime objects, with the local-blocker rule; or (b) load resolves after the publication and the app reads host.startup. Recommended (a); Astra, Opus and Sol for (a), Fable for (b).
  2. Getters on waiting (chapter IX): reject at once (recommended) or wait up to readyTimeout.
  3. waiting as a cause kind (chapter III): a new kind (recommended; Opus, Fable), transient without retryAt (Astra), or loading with a diagnostic (Sol).
  4. A pure swap whose new factory needs a dependency that is not there: the object parks (its gate closes, its holders see loading or failed { waiting }, calls park or reject; recommended), or it stays on the old code until the dependency resolves (old and new code would then overlap without bound, against §21's "a host is at R or R−1").
  5. The last good value (chapter X): kept only while every contribution it was built from is still in the table (recommended; Astra), or kept as slice 8 decided, with natives in a registry looked up at use through their owner (Sol).
  6. Cycles across hosts (chapter VIII): (B) the probe, with (B1) a re-search backoff that sends probes only (recommended) or (B2) a full search lifecycle with no timer at all; or (A) the slice 4b decision narrowed to one deadline, which polls chains across hosts again, misses a ring of waiting attempts, and retries in lockstep without finding the cycle it is for.

For slice 7's spec

  • The test list: the startup deadlock resolving without readyTimeout; an early hold placed here, not through the parent; remove-then-serve with a live dependent's calls recovering; a 1,000-hold publication wave under the window; the probe on long rings, diamonds, edge changes, reloads, relays, reconnects and forged probes; GC of a parked three-level chain after its top is released; every index entry gone after release, revocation and link loss.
  • The local re-binding of a Binding (member sources, keyed pins, parked calls, presence) and the unbinding of a live hold under flow control, both with their race tests.
  • The wire: waiting in the failed cause schema, the attempt id on loading and failed, the probe message, the pinned list; PROTOCOL_VERSION stays 1 until p3 ships.
  • The design changes listed in appendix A, folded into design.md and the decision log in the same commit as the owner's decisions.

Glossary

Attempt: one try at activating an object: its factory, requests, natives; its own id since the model. Bound: a request pointing at an object here or a hold over a path. Dependency: a request an attempt needs live before it may go live (self.get, self.registry, a keyed pin). Dependency check: the moment all of an attempt's dependencies are live; after it the attempt runs its own steps. Edge generation: a number of a wait edge, incremented by its source whenever the request binds anew. First outcome: an object is live, failed by its own cause, or parked with no local blocker still in its first attempt. Holder: whoever made a request and alone ends it. Parked: an attempt waiting for a dependency, with no timer. Probe: the message that walks wait edges to find cycles: a search, then a check along the recorded path. Publication: a host making its facets' declarations visible: load's setups, a reload's commit, an install's commit. Refused: a request without authority or with invalid params; never indexed. Request: what a reference stands for: type or registry, params, principal, version. Round: the number of one search, from a counter per attempt. Seen set: the newest round number an attempt has forwarded, per initiator (up to 256). Unbound: a request with no provider at the moment, with a reason (unpublished, not_served, version, compose, installing, no link). Waiting: the cause of a failure that is not the object's own, woken by an event. Wait edge: a parked attempt waiting for another attempt. Wake: an event that makes the resolver look at a request again.

1. Requests and one resolver

  • A request is what a reference stands for: type (or registry), params, principal, the consumer's contract version. Its holder makes it and owns it: an attempt (self.get, self.registry, keyed pins), a call (ctx.get), outside code (host.get, host.hold, host.registry), a link's peer (hold). It ends only when its holder ends it (the attempt ends, the call settles, release(), a getter gives up, the peer's link or origin closes, revocation, the holding host closes), never because its provider is missing, went away or does not fit.

  • The destination by address (round 1): a local type goes here; a remote type goes to the address its hostAddress (computed from the consumer's own contract) gives: here if that is this host's address, whether served here or not, else over the route for that kind or the parent (design §3). Every remote type declares its hostAddress (owner, 2026-10-29: the optional placement of slice 3a is removed and the field renamed, and with it the fallback "here if served, otherwise the parent" and its re-placement at the first parent link). A hold arriving for an address that is not this host's is relayed or refused (invalid/host_address) as today; a relay never captures a hold because it serves the same name.

  • Then the selected provider is checked (served, version or accepted version and fingerprint, authorize, the provider's own host-address check). Version checks never look at a same-name registration elsewhere.

  • The publication gate: a request made on this host, or arriving on its links, before the host's first publication (§6) is not placed yet; it shows loading and is placed by the publication. The gate lasts only for the synchronous setups, never for activation, so it cannot deadlock.

  • Outcomes of the check:

    The check finds Request
    a fitting provider bound (to the object here, or to the hold over a path)
    not published yet unbound unpublished: loading
    nobody serves the name at its address unbound not_served: failed { waiting }
    no fitting version, a fingerprint that differs at the same version, a host address the provider computes elsewhere (code skew) unbound version: failed { waiting }
    the registry is served, but its first compose (or the reader's version mapping) threw unbound compose: failed { waiting }
    the provider host is installing a revision and the hold does not fit its current code unbound installing at the provider: loading

    The unbound reasons that wait for a name (unpublished, not_served, version, compose) are indexed under it on the host that decided them: the consumer's host for a local request; the provider's host for a hold that arrived over a link (it already keeps such holds as refused: remote/hold.ts). installing is the provider host's own, re-evaluated at its install's end; no_link lives on the path, where the next link holds it again. Indexes drop an entry when its request ends; GC-tested.

3. Dependents: parked until their dependencies resolve

A dependency is what an attempt declares and needs before it goes live: self.get (local or remote), self.registry, keyed pins (at(key) on another object's keyed member). self.follow is the attempt's own step (its attach runs Durable's code), not a dependency; a follower declares retryOn on the registry it reads the harness through, or recovers by its own backoff.

  1. Order, as today up to the check: the factory runs; persisted singletons hydrate (the object's documents, kept across attempts); the requests are made. The attempt is parked while any dependency is not live (hydrated):

    Its dependencies The dependent shows
    any loading, none failed loading
    any failed failed { waiting, "waiting for X: <X's cause>" }, retryAt undefined; the message keeps the nearest blocker and the root cause within the 500-character rule
    one failed with invalid/cycle (a dependent off the ring) broken with the same error: it would wait on a ring that never heals by itself
    one ended (revoked, or its host closed) broken with that error: the request cannot come back; retry() or a reload makes new requests (a guard: a dependency ends only with its holder's principal or host, so the dependent ends too; Fable)

  2. The dependency check is the activation boundary: once every dependency is live, the attempt runs its own steps (natives in order, follow attaches, member checks, derives), bounded by its own readyTimeout deadline, and goes live. A dependency that leaves live after the check is treated as after live (R18): the attempt goes on. This is R18's rule for live objects applied from the check on, not a rule of its own (owner, 2026-10-29: a dependency can go away at any point of an object's life; the object stays live, its calls through that reference meet its state). So a parked attempt holds no natives, and an attempt that opened natives is never parked.

  3. No timer while parked: no dependency deadline, no backoff. The attempt's deadline is paused while parked (as eager migrations pause it) and resumes with the budget left.

  4. Wakes, one rule: the dependent re-evaluates on every state change of any of its dependencies (live, loading, failed, a new cause compared by value, ended; Opus: otherwise a ring of waiting attempts passes its causes round and round), updating what it shows; it leaves parking when all are live. The factory never re-runs while parked. Wakes are coalesced per object and run after the batch that caused them; a change during the attempt's own steps or its teardown is remembered.

  5. Kept while parked: its documents (the object's), its declarations and requests, its seal token; no natives. Ended with the object (its last holder; a host-lifetime object when its plugin is removed or the host closes).

  6. broken only for the object's own code (a throwing factory, a derive throwing at activation, hydration, migrate, a document fingerprint mismatch, an open throwing broken(...)), cycles (§7) and authority (forbidden, an ended dependency).

  7. Retry passes on: ref.retry() on a failed { waiting } object retries its broken and transient blockers, hop by hop (the existing retry message over links), once per retry operation (an id dedupes diamonds); waiting blockers pass it on; nothing else is touched. Retry of a broken or transient object starts a new attempt, as today.

  8. retryOn wakes failed objects as decided in slice 8 (a value call retries a transient or broken object); while the object is parked waiting, a value call does nothing: its dependencies decide.

  9. Own-code reload of a parked object: its plugin's reload replaces the parked attempt with the new factory's, as one handover: the new requests are made and bound first, then the old ones released (round 2, Astra N4: an unchanged dependency held only by this object must not end in between; today's #activate binds before #releasePrevious).

  10. After live, R18 unchanged: a dependency leaving live leaves its dependent live.

4. Wakes: two events

Event Re-evaluates
a target changes state: a dependency's object goes live, loading, fails, gets a new cause or ends; a hold's bound, loading, failed arrive, also after a re-hold on a new link the requests bound to it, and their dependents (§3.4)
a name becomes usable, or an install ends, on a host: a publication (load's setups, a reload's commit, an install's commit) serves a type, a registry, a version; a registry composes or maps a value at a version; an install ends without a commit (rejected) the unbound requests indexed under those names; the provider's installing holds; a refused hold re-runs its start and sends loading, then bound or failed

No new message kind for wakes: loading, bound, failed and retry exist. The wire's failed carries the new cause kind waiting; loading and a waiting failed carry the provider's attempt id for the probe (§7).

5. Removal, versions, rollout

  • A reload that removes a type: its objects end as today (natives close, reason end; callers rejected at once; handlers drain). Their requests are not ended: each becomes unbound not_served and binds again if a later commit serves the name.
    • Locally: a Binding whose target ended by removal becomes unbound and accepts a second bind: member sources re-bind by name (one frame from the last value, as on a restart), keyed pins re-pin, parked calls flush or reject, presence re-lists. The one new piece of machinery.
    • Over a link: a failed on a bound hold unbinds it (Fable: one message, one rule; the consumer applies it as #startOver plus failed); the provider detaches the hold's sources and drops its unsent pending ops and queued bound; the ack slots of bound/state messages already sent stay counted until their ack or the link's loss; calls in flight on it are rejected and free their slots once.
  • A reload that stops accepting a version unbinds only the requests on that version (version); the object stays (its own plugin's reload still restarts it if it has natives, §21).
  • A type moved to another host kind: the request carries the address its own consumer code computed; the old host answers not_served; the consumer's own reload makes a new request. No redirect.
  • A consumer whose code moves to a new version releases its old request and makes a new one (today).
  • Rollout, without revision fields: each host knows only its own install. A provider host that installs keeps holds that do not fit its current code installing (loading) and re-evaluates them when the install ends, by its commit or by its rejection. A provider host that is queued but not installing yet answers a mismatch failed { waiting, version } until its install commits and wakes it: a visible blip of at most one install, accepted (Opus). An install never waits for activations (a reverse-order rollout would deadlock); a host whose own install was rejected fails its own requests at once with the reason (design §21). The loader keeps its own duties (the desired code set, digests, serialized installs).
  • Old calls across a reload follow §21 unchanged: a pure swap lets them finish on old handles; a native restart drains them first; a removal rejects their callers at once and drains the handlers. Calls are never resent.

6. Startup: publication, then first outcomes

  1. Publication: load runs every facet's setup, then publishes all at once in one batch (types served, registries served and composed once, contributions in their tables), then wakes (§4) after that batch. Nothing activates inside it.
  2. No gate beyond it: holds and host.hold wait only for the publication, never for the barrier. This ends the startup deadlock: W's hold for C binds as soon as S's setups published; B goes live, then A.
  3. The barrier (Owner: (a) or (b); recommended (a), three reviewers of four):
    • (a): load resolves when every host-lifetime object of this load has a first outcome: firstOutcome(o) = o.live || o.ownFailure || (o.parked && o.blockers.every((b) => !b.local || firstOutcome(b))), where local means executing on this host (an object here, a keyed pin still loading here), not the contract's kind. So CodeMode → Harness waits for the harness's outcome; a wait on another host or on a failed dependency ends the first pass. One firstOutcome signal per object, separate from the readiness dependents wait for (Sol), counted once, never reopened by retries. An object of the cohort that ends before its first outcome (its plugin removed, the host closing) settles its entry as ended; host.close settles the waiting load (Astra R3).
    • What (a) promises: every host-lifetime object on this host had its first try, and the contributions of those that went live are in their tables. Not: every tool that will arrive (a parked or slow contributor, tools found in onLive, MCP; Sol's probe /tmp/barrier-sol-first-outcome.log). What a first turn needs is p3's explicit admission check.
    • (b): load resolves after the publication; Chord adds host.startup, a watchable of the host-lifetime objects' first outcomes with their causes; the app decides (Fable). The same tracker, awaited by the app.
    • p2 today resumes its harness without waiting for all host objects (apps/p2/src/hosts/worker.ts), because its worker objects that need server types are reachable only after control.ready().

7. Cycles

On one host, cycles are found exactly as today: at self.get, following the waiting edges of activating and parked attempts. Across hosts, a hold carries the activation chain it was made in (today), which finds every cycle whose objects start one after another. What remains is the documented gap (design §6): objects on two hosts that start at the same moment and need each other. The owner decided on 2026-10-24 (slice 4b review decisions (2)) that this is a documented limitation that times out and retries, with no probe message. Without dependency deadlines that timeout no longer exists, so the gap needs one of two answers (Owner):

  • (A) The 4b decision, narrowed. One deadline stays: an attempt parked on a dependency held over a link whose target attempt is known and still activating or parked fails transient after its readyTimeout and retries with backoff; its next attempt usually starts after the other side and its chain finds the cycle. It has a cost that decides against it: the target being parked is the common case of a chain across hosts waiting for a missing plugin (a tab's view on a worker object that waits for an uninstalled type), and those dependents would time out and poll again, as today, so "local = remote" would not hold across hosts. Narrowing it to targets that are loading (not failed { waiting }) avoids that but misses a real ring: A and B on two hosts wait on each other, B also on a missing X; B is failed { waiting }, so A is too; when X appears, both stay failed { waiting } on each other, with no deadline and no chain to find it. And even the timeout does not find what it is meant to (round 6, Fable): an object's chain is fixed when it is created and its instance id survives retries, so a retried attempt sends the same hold with the same chain; two simultaneous starts time out and retry in lockstep and are never found.
  • (B) The probe (recommended), below: no deadline at all, one new message kind, the most intricate rule set in the model. Five review rounds found a counterexample in each of the first four drafts; draft 6's version answers all of them, but it has not been reviewed again, and slice 7 would have to prove it with tests before the deadline could go.

(B) The probe

Replaces the activation chain in holds. On one host the self.get walk stays (it is synchronous and exact: a ring with no remote edge is found there, where (B1)'s timer does not run; Opus, round 7); the probe serves the rings that cross a link. It replaces draft 1's bounded chain too draft 1's bounded chain (a ring of 33 is never found with chains cut at 32; chains keep stale ancestry). Draft 5 replaces the second round by a check along the recorded path (round 4, Sol: two rounds through different stale paths can report a ring that never existed, /tmp/model/sol-probe4.log).

  1. Attempts, edges, tokens. Every attempt has its own id (uuidv7 per attempt: a retry or reload is a new attempt). A wait edge runs from a parked attempt to the parked or activating attempt it waits for, through a bound request (unbound waits and registry reads are never edges; they are not deadlocks). Each edge carries an edge token (round 5, Astra, Sol): a number from a counter per attempt, never reused, replaced by a fresh one on any interruption or change of that edge, so two requests to one object are two edges: a new target attempt (also a local target's retry, without a re-bind), any loading on a bound or pending hold (a relay's upstream re-hold included), an unbinding, a rebinding, a re-hold after a reconnect. An attempt is parked for one interval only (one that passed its dependency check never parks again) and ids are never reused. A provider tells its consumers the attempt they wait for on every non-live answer: loading { hold, attempt } and a waiting failed { hold, cause, attempt }.
  2. A search per edge change. Whenever a parked attempt gets a new edge or a new token on one, it starts a search: probe { kind: "search", round, initiator, trail } along each of its wait edges, round the next number of a counter the attempt keeps, trail the list of (attempt, edge token) hops it crossed, starting with the initiator's own. A ring closes at its last edge, and that edge's source starts the search that finds it. Coalesced per batch. Locally a call on the target attempt, forwarded through a queue (no recursion); over a link the message probe { hold, to, ... }, consumer to provider, relayed by hold id with the origin. Probes are honoured on parent and route links and dropped on child links (accept), whatever trusted says.
  3. Forwarding. An attempt receiving a search drops it if to is not its current attempt or it is not parked. If the initiator is itself, the search returned (4). If the attempt is already in the trail, it drops it (a ring that does not contain the initiator is found by its own members' searches; Opus). Otherwise it forwards it along every wait edge, appending (itself, the edge's token) to the trail, only if the round number is higher than the one it stored for that initiator (older or equal rounds are dropped: the initiator superseded them), and stores it. The seen map holds one number per initiator, up to 256 initiators, and goes with the attempt.
  4. The check. A returned search is accepted while its initiating attempt is still parked, whatever round it carries (round 7, Astra: a re-search must not invalidate an older search still under way); the check decides. The initiator then sends probe { kind: "check", round, trail } along the recorded trail: the initiator first verifies its own hop; each hop passes it on only if it is still that attempt, still parked, still has the recorded edge token, pointing at the next hop's attempt; otherwise the check dies (also on a to mismatch). The check follows the trail by position and bypasses the seen map. The initiator verifies its own hop again when the check returns. If the check returns, the initiator fails broken invalid/cycle, the path named for display from the trail, and today's propagation breaks the other activating objects on the ring and the dependents off it. 5. No silent loss. Dedupe can drop the copy of a search that travelled the ring in favour of a copy whose path later breaks (Astra, round 5); then the check dies and nothing is left to find the ring. Round 6 tried dead notices back to the initiator; Sol and Astra showed that reliable notices need recovery state per search that eviction may not drop and that a long-parked attempt would otherwise keep for every initiator that ever passed (a leak), i.e. a full search lifecycle with cancellation. Two ways (Owner, part of decision 6):
    • (B1) Re-search with backoff (recommended). An attempt parked on a remote attempt starts a fresh search again after a backoff (1 s doubling to 60 s, reset by an edge change), whether it shows loading or failed { waiting }; the timer stops when the attempt leaves parking. No dead messages, no recovery state, eviction only costs work; a new search starts within one backoff period, so every stable ring that crosses a link is eventually found (no wall-clock bound: delivery is only fair; a ring on one host is the walk's). The timer runs as long as the attempt stays parked on a remote attempt: a view on a worker object that waits for a missing plugin re-searches every 60 s until a reload (Fable: cheap, but for as long as it waits). The timer sends probes only: it never fails an object, re-holds or polls a provider. Cost: one probe per parked remote dependent per period, which crosses the downstream wait graph and dies at its leaves (an unbound wait is not an edge).
    • (B2) Events only. Each search is owned until it settles: branches report completion or abort back along their trails, a dropped probe answers dead { initiator, round } with a reverse route, an edge records the searches it carries until they settle, and an initiator that ends or starts a new round cancels its old one along the same routes. Complete without a timer, bounded by the searches in flight, and the most intricate protocol in Chord; not yet specified to the reviewers' satisfaction. Rejected: enumerating every simple trail without dedupe (Sol's correctness reference): no ring copy is ever suppressed, but work is exponential on chains of diamonds.
  • Why a reported ring existed: every edge of the trail kept its token from the moment the search crossed it to the moment the check crossed it; the search crossed all of them before the check started, so at the moment the check started every edge of the ring existed at once. A token changes on every interruption and is never reused, so an edge cannot vanish and come back unnoticed. Sol's counterexample fails at the check: C1 is no longer B's target.
  • Why every ring is found (under an eventually stable wait graph and fair delivery; endless edge churn can keep invalidating searches; with rule 5's (B1) or (B2) for a search suppressed behind a path that broke): a ring is closed by its last edge; its source starts a search when the edge appears; every other edge exists then and every attempt on the ring waits transitively on the source, so none goes live before the search and the check return. Rings of any length, local and remote mixed. On a DAG searches die at the leaves; on a diamond the second arrival is dropped.
  • What it does not promise: (1) a ring that existed when the check started may be broken up by a concurrent reload, retry, unbinding or revocation just after; it is still reported (it did exist). Its broken objects recover as every broken object does: ref.retry() or a reload of their plugin. (2) Linear work under every schedule: with more than 256 initiators passing one attempt at once, an evicted entry lets a search be forwarded again, so work can grow with the number of simple paths (never endlessly: a search never revisits an attempt in its trail). (3) Constant message size: a probe carries its trail, so its size grows with the length of the path it crossed (a returning search's trail is as long as its ring); no cap cuts it, since the trail is the proof.
  • Cost: one search per edge change, crossing each downstream edge once, one check per returned search; with (B1), one more search per backoff period for every attempt parked on a remote attempt, also while an acyclic chain waits for a missing plugin, plus the trail bytes. The bounded memory is the seen map's; probes in flight are bounded by the searches started.
  • Transition: today's dependency deadline for activations waiting across links stays until the probe's tests pass in slice 7 (long rings, diamonds, a ring closed after a reconnect with unchanged attempt ids, Sol's phantom schedule, 300 concurrent initiators, edges added and removed, reloads, relays, forged probes); then it goes in the same slice.

8. Getters, holds, calls: one rule

  • host.hold returns a reference at once; only invalid params throw (also before load). A missing local type gives failed { waiting } after the publication, loading before it.
  • host.get, ctx.get and host.registry: resolve when live; wait while loading, or failed { transient } (its own retry is under way), up to their readyTimeout; reject at once on failed { waiting } or { broken }. On success, rejection or timeout their temporary wait goes; host.registry returns the RegistryValue with its ordinary watch ownership (no release()). Owner: recommended (nobody waits 60 s for a plugin that is not there; code that wants to wait holds instead), or wait through waiting too.
  • Calls on a loading reference park, each bounded by the reference's readyTimeout from when it was made; on a failed one they reject at once with the cause; sent calls are never resent.

9. Registries

  • The same resolver on one host: a reader's request for R at its version is bound while R is served and has a usable value at that version (composed; mapped by accepts[old].value for an older reader), otherwise unbound not_served, version or compose, or loading before the publication. Woken at every transition to usable (#valued's first-value latch goes). S2's broken and S3's backoff go.
  • Version skew within one host: a reload of the registry's plugin alone leaves other plugins' contributors and readers on their bundled versions; accepts[old].contribution and .value keep them working, unsupported contributions are left out and reported, unsupported readers are waiting (version).
  • A registry waits for a value, never for a particular contribution (an empty table composes). After live, a later compose failure changes nothing for the reader: .value keeps the last good composition, but only while every contribution it was built from is still in the table (round 2, Astra N2): when one of them leaves (its contributor ended or was reloaded), the last good value is dropped and .value throws until compose succeeds, so it never hands out a native whose contributor ended. compose represents a missing contributor as a value.
  • Registries stay host-local (contributions are in-process values).

10. Keep-alive, presence, revocation, jobs

  • A request over a link counts once in host.activity.references from its arrival to its end, bound or unbound; presence (host.references) lists only bound references.
  • Revocation ends the requests of a revoked principal, bound and unbound, at every hop; nothing revives them.
  • gone stays only for revocation (a provider host closing closes its links and sends nothing; its consumers see a drop, loading, and hold again on the next link).
  • Persisted job runs of a parked host-lifetime object are loaded with its documents; run and finish start only once it is live; the run count keeps the object as today.

12. What changes in the design

R18 (dependency failures waiting, no backoff, the deadline paused while parked, the dependency check as boundary, wakes on every change, an ended dependency breaks), S2 and S3 (waiting, woken at every usable value), slice 8's last-good rule (dropped when a contribution leaves), §3's destination table (by address; the publication gate), §6 (the simultaneous-cycle gap: (A) one narrowed deadline or (B) the probe), §7 (host.hold, getters, calls), §21 (no gone on removal; a dropped version unbinds only its requests; installs never await activations; rollout without revision fields; the reload handover), the start barrier (R17, W6), FailureCause (+ waiting), loading/failed with the attempt id, one message kind (probe, tagged search or check). Unchanged: what an object's own code reload does (§21), R18 after live, retryOn outside parking, self.follow's R4, the call window and flow control, revocation, no client providers.
