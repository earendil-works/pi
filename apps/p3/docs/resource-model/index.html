Before we begin

Mario runs p3 on his laptop. He never thinks about resources: every session he opens has his models, his MCP servers, his machines and every tool the installed plugins offer. When he installs a plugin with a new tool, the tool is in his next turn.

At Earendil the same p3 serves three people. Colin, Cristina and Charlotta start a project. Colin brings his Linear MCP server, signed in as Colin; Cristina brings her GPU machine; Charlotta brings her Anthropic key. A session in the project uses exactly those three, whoever sends. Colin takes his MCP server back in the middle of a session; the next call to it is refused. Engineering may create MCP servers, research may not, yet a researcher in the project uses Colin's server. A Discord channel feeds a session that may only read the answers of one other session, for one hour.

The models we tried before mixed two questions: where does something appear (a project, a folder, a recent list, a Discord server) and what may a session use. Every attempt to let groupings decide resources produced selectors, precedence rules and login modes. This spec separates the questions. Groupings show. One list equips.

Ten things to know

  1. Where something appears is not what a session may use. A session appears in any number of groupings; it uses exactly one list.
  2. Users are people plus one instance user. The instance user owns company resources (a company key, the build machine, the Discord bot) and every plugin's built-ins. Nobody signs in as it.
  3. A resource is a Chord object of a resource kind, owned by one user forever. Its login, if it has one, never changes. A second login is a second resource.
  4. Users create resources only for themselves; admins create them for the instance user. Installing a plugin is an admin act: the plugin's setup-free built-ins (tools, prompt sections) become instance resources by themselves.
  5. A session has one resource source, one field in the catalog: its owner's defaults, its own list, or one grouping with resources. The defaults are a rule, "everything I own plus every instance resource I may use", so new built-ins appear in normal sessions automatically.
  6. Groupings are plugins. Computed ones (folders, recent) and curated ones (projects, Discord channels) show things. A grouping with resources keeps its own list in its own plugin and registers with core how to read and change it.
  7. Everyone who may send in a session uses its whole list. No per-run authority (decision 2026-11-08).
  8. One policy decides, through typed requests, at core's guarded steps. Plugins never import ACL, SAML or Radius; UIs never check anything, they render server views such as a user's creatable kinds.
  9. Workers follow their list. The harness admits an extension only while its resource is on the list and belongs to the plugin that contributed it; resource plugins' per-session server views check the list at every call. Anything unknown fails closed.
  10. Presentation is open. Creators per resource kind, renderers per contract and form, panels from several plugins for one detail view; layouts are plugins.

Words used throughout

A user is a person with a p3 account; the instance user (INSTANCE) is the reserved user owning company resources and built-ins. A resource kind is a Chord contract whose objects are resources, declared with resourceKind. A resource is one object of a resource kind, named by its kind and typed params; its owner is read from its params. A built-in is a setup-free resource a plugin declares, owned by the instance user. The index is core's table of every resource with its owner and the plugin that serves its kind. A list is a set of entries, each naming a resource, who brought it and an optional expiry. A session's resource source says where its list comes from: the defaults (a rule), its own list, or a grouping with resources. The effective list is the source's entries after core removed expired, unknown and denied ones; it is what the session's worker follows. A grouping is a plugin's object that shows other objects. The policy is the one contribution to the Policies registry; it answers typed requests given a baseline, the answer core and the owning plugin give without it. A guarded step is a core method that asks the policy before it changes anything. An extension grant is a worker contribution pairing a Durable extension with the resource it belongs to. A creator is a resource kind's page contribution that creates one; a renderer draws a contract's object in a form (row, card, detail); a panel is one part of a detail view.

I

Names Written Once

How the model stays typed: contracts and tokens in code, erased addresses only at storage, wire and registry boundaries.

The owner's rule is "no stringly-typed APIs". In p2 the session lock names MCP servers by string, capabilities are a string list ("ports" | "conversations"), and every tool repeats its own access fields. The model must not repeat that, yet resources of unrelated plugins have to live in one list, one table and one wire message. Those three places cannot hold a TypeScript type.

The answer is the same as Chord's own: an identity is a name written once, in a contract file; code refers to the constant. remote("mcp.server", ...) writes the name once; every other file imports McpServer. The model adds three tokens of the same kind, all built from Chord contracts:

// plugins/resources/contract.ts: core's resources plugin; every facet imports it through @p3/app/v1

/** A kind of resource: the contract whose objects are resources, and how an object's params name its owner. */
export type ResourceKind<C extends RemoteContract = RemoteContract> = {
	readonly contract: C;
	readonly ownerOf: (params: ParamsOf<C>) => UserId;
};
export function resourceKind<C extends RemoteContract>(
	contract: C,
	ownerOf: (params: ParamsOf<C>) => UserId,
): ResourceKind<C>;

/** One resource: its kind and the typed params of its object. */
export type Resource<C extends RemoteContract = RemoteContract> = {
	readonly kind: ResourceKind<C>;
	readonly params: ParamsOf<C>;
};
export function resource<C extends RemoteContract>(kind: ResourceKind<C>, params: ParamsOf<C>): Resource<C>;

/** Any Chord object as stored, sent and kept in registries: its contract's name and its params. */
export const ObjectAddress = obj({ contract: str(), params: map(union([str(), int(), bool()])) });
export type ObjectAddress = Static<typeof ObjectAddress>;

/** `r` erased, for a table, a list entry or a wire message. */
export function pack(r: Resource): ObjectAddress;

/** `a` as a resource of `kind` (its params checked with the contract's params schema), or undefined: another kind. */
export function match<C extends RemoteContract>(kind: ResourceKind<C>, a: ObjectAddress): Resource<C> | undefined;

A plugin's operation, when the policy needs to name it, is a method of its contract, taken as a value:

/** The name of a method of `C`'s current variants, as a value: a misspelled method does not compile. */
export function operation<C extends RemoteContract, M extends MethodName<C>>(contract: C, method: M): Operation<C, M>;

// MethodName<C> and ArgsOf<C, M> are small type helpers over Chord's CurrentVariants<C> (contracts/contract.ts).

Where the erased ObjectAddress appears, the code that reads it calls match(kind, address) and gets typed params or nothing. That is the only place a contract name is compared as a string: in match, inside core.

The rule for reviewers

Strings are allowed as identities written once in a contract file (remote("mcp.server"), builtin("coding-tools"), form("p3.row")), as erased addresses in storage, wire messages and registry tables, and as persisted user data (an admin's rule naming a kind). Anything else that switches behaviour on a string literal is a finding.

II

People

Users, the instance user, and the one way a person becomes a user.

Every person with an account is a user. One more user exists in every instance from the start: INSTANCE. It exists so that "who owns the company's Anthropic key" has an answer that is not a person who might leave. It owns the build machine, the Discord bot and every built-in tool. Nobody signs in as it; admins act for it.

// plugins/users/contract.ts
export type UserId = string & { readonly "~user": true };

/** The instance user: owns company resources and plugins' built-ins. Nobody signs in as it. */
export const INSTANCE: UserId;

/** p3's principals (decision 2026-11-06); links stamp them, a caller's data never sets one. */
export type P3Principal =
	| { readonly kind: "server" }
	| { readonly kind: "worker"; readonly session: string }
	| { readonly kind: "user"; readonly id: UserId }
	| { readonly kind: "guest" }; // reserved until sharing is designed

/** Users (server, host lifetime): who exists, and the one way to become one. */
export const Users = local("p3.users", {
	version: 1,
	params: {},
	members: {
		users: arr(UserRow), // { id, name, admin, signIns: [{ issuer, subject }] }
		/** The user an external identity signs in as, created at its first sign-in. Never keyed by email. */
		signIn: method(obj({ issuer: str(), subject: str(), name: str() }), str()),
	},
});

Sign-in plugins create users; nothing else does. The kit's owner link signs in as the first user (issuer p3.owner), which is the single-user laptop. A SAML plugin maps (issuer, subject) from a verified assertion; a Radius plugin does the same with a Radius account (chapter IX). The first user is an admin; who else administers is the policy's answer to the request administer (chapter VI).

III

Things a Session Uses

Resource kinds, the index, the guarded create, and built-ins that create themselves.

A resource is anything a session can use: a model provider, an MCP server, a machine, a drive, a tool, access to one other session. Each is an ordinary Chord object whose contract's params name its owner. Its plugin keeps its configuration and secrets; core keeps one row per resource in the index: its address, its owner, the plugin that serves its kind and a label for generic lists.

A kind, declared in the plugin's contract file

// plugins/mcp/contract.ts
export const McpServer = remote("mcp.server", {
	version: 1,
	params: { owner: str(), id: str() },
	hostAddress: () => Server(),
	variants: {
		user: { state: { info: McpInfo }, methods: { configure: method(McpConfig), signIn: method() } },
	},
});

/** MCP servers are resources; the owner is a param, so it can never change. */
export const McpKind = resourceKind(McpServer, (p) => userId(p.owner));

// plugins/mcp/server.ts: the server facet tells core the kind exists (and that this plugin serves it)
self.contribute(ResourceKinds, [McpKind]);

The worker facet, the page facet and the server facet all import McpKind from the same file; they cannot drift. The ResourceKinds registry (server) tells core which plugin serves which kind: that is the plugin recorded in each index row and checked on the worker (chapter VII).

Creating: the guarded step

A plugin creates a resource in its own user-facing method, as the calling user, and passes the creation through core before its own row exists:

// plugins/mcp/server.ts: the user's view of the MCP plugin
host.serve(McpServers, (_params, principal, self) => {
	if (principal.kind !== "user") throw forbidden("users only");
	const resources = self.get(Resources, {});
	const store = self.get(McpStore, {});
	return {
		variant: "user",
		members: {
			servers: store.serversOf(principal.id),
			create: async (config, ctx) => {
				const created = resource(McpKind, { owner: principal.id, id: newId() });
				// The guarded step: the owner rule, then the policy; refuses before anything is written.
				await resources.create({ actor: principal.id, resource: pack(created), label: config.name }, ctx);
				await store.insert(created.params, config, ctx);
				return pack(created);
			},
		},
	};
});

Resources.create is a local server method (callers are trusted server code; actor comes from the caller's checked principal, as Sol's design requires for local calls that act for someone):

export const Resources = local("p3.resources", {
	version: 1,
	params: {},
	members: {
		/** Every session's effective list, by session id; a worker's server view pins its own with at(session). */
		lists: keyed(SessionList),
		/** The guarded step for a new resource: owner rule, policy, then the index row. */
		create: method(obj({ actor: str(), resource: ObjectAddress, label: str() })),
		/** A resource's object is gone: out of the index, out of every list. */
		forget: method(obj({ resource: ObjectAddress })),
	},
});

What create does, in order:

  1. Find the kind by the address's contract in ResourceKinds; an unknown kind is refused.
  2. The owner rule, not overridable by any policy: the owner read with kind.ownerOf(params) is the actor, or the instance user and the actor administers. Nobody creates a resource that uses another person's login.
  3. The policy: { kind: "create-resource", actor, resourceKind, owner } with baseline allow. A SAML rule "only engineering may create MCP servers" denies here.
  4. Write the index row with the kind's plugin.
Review: order of the two rows

The index row is written before the plugin's own row. A crash between them leaves an index row without an object: its renderer shows it missing, and the owner can remove it. The reverse order would leave an object no list can name. Sol's design wants creation idempotent on retry; the reviewers should say whether the plugin should pass a stable id and core accept a repeated create for the same address and actor.

Built-ins: created by installing

Tools that need no setup (read, write, edit, bash, a third-party plugin's plain tools, a prompt section) are resources too, or a session could not be locked down to "only the conversation tool". Asking each user to create them would be absurd, so a plugin declares its built-ins and core creates them for the instance user when the plugin is installed. Installing a plugin is an admin act; the built-ins are part of it.

// core: one resource kind for all built-ins; an object per built-in describes it for people
export const Builtin = remote("p3.builtin", {
	version: 1,
	params: { id: str() },
	hostAddress: () => Server(),
	variants: { user: { state: { info: BuiltinInfo } } },     // label, description, plugin
});
export const BuiltinKind = resourceKind(Builtin, () => INSTANCE);

/** A built-in resource of a plugin: its id is written once, here, in the plugin's contract file. */
export function builtin(id: string): Resource<typeof Builtin>;

// plugins/coding-tools/contract.ts
export const FileTools = builtin("coding-tools.files");    // read, write, edit
export const Bash = builtin("coding-tools.bash");          // a separate resource: pickable on its own

// plugins/coding-tools/server.ts
self.contribute(Builtins, [
	describe(FileTools, { label: t.message("fileTools"), description: t.message("fileToolsAbout") }),
	describe(Bash, { label: t.message("bash"), description: t.message("bashAbout") }),
]);

Core follows the Builtins registry: a new entry becomes an index row owned by INSTANCE with the contributing plugin; a built-in whose plugin is not loaded (a failed reload, an uninstall) stays in the index marked unavailable and drops out of every effective list until it comes back. Two plugins declaring the same id is a reported conflict; the first by plugin name keeps it.

One Durable extension is one resource. A plugin chooses its granularity by how it splits its extensions: coding-tools above offers two, so a session can have the file tools without bash.

IV

One List

The session's one resource source, the defaults rule, bringing and withdrawing, expiry, and the effective list.

The session catalog (the sessions plugin's server table) gets one field:

// plugins/resources/contract.ts
export const ResourceSource = union([
	obj({ kind: lit("defaults") }),                          // the owner's defaults: a rule, not a list
	obj({ kind: lit("own") }),                               // the session's own list, kept by core
	obj({ kind: lit("grouping"), grouping: ObjectAddress }), // one grouping with resources
]);

// plugins/sessions/server.ts: the catalog row
type SessionRow = {
	readonly id: string;
	readonly owner: UserId;
	readonly title: string;
	readonly source: ResourceSource;
	// location, status, pin, archive: as before
};

There is one field, so a session has one source by construction: no check across groupings, no precedence. Moving a session into another grouping with resources replaces the field; the old grouping no longer equips it.

Entries

Every list, wherever it is kept, holds the same entries:

export const ListEntry = obj({
	resource: ObjectAddress,
	broughtBy: str(),           // the user who brought it, stamped by core, never caller data
	until: nullable(int()),     // an expiry in ms since the epoch; null: until removed
});

There is no login field and no mode: the resource's owner decides which login it uses, forever. An expiry sits on the entry, not on the resource: "Colin's MCP server in project pi until Friday" says nothing about the server.

The three sources

  • Defaults is not stored. It is the rule every resource the session's owner owns, plus every instance resource the policy lets the owner use. That rule is why Mario never configures anything and why a third-party plugin's new tool appears in his next turn: installing the plugin adds an instance resource, and the rule includes it.
  • Own is a list core keeps per session (p3.resources.session-lists, rows of session id plus entry). "Lock down this session" switches a session from defaults to own, starting from a copy of its current effective list, then the user removes what it should not have.
  • Grouping names a grouping with resources. Its plugin keeps the list; core reads it through the plugin's registration (chapter V).

The effective list

Core turns the source into the list a session actually gets, and keeps it live as one keyed member, Resources.lists.at(session):

/** What a session's worker follows: ready with its entries, or unavailable (fail closed). */
export const SessionList = union([
	obj({ kind: lit("ready"), entries: arr(EffectiveEntry) }),   // { resource, plugin, owner, until }
	obj({ kind: lit("unavailable"), reason: MessageSchema }),
]);

function effective(row: SessionRow, facts: Facts): SessionList {
	const entries =
		row.source.kind === "defaults" ? defaultsOf(row.owner, facts)
		: row.source.kind === "own" ? (facts.ownLists.get(row.id) ?? [])
		: facts.groupingLists.read(row.source.grouping);           // undefined: its plugin is not loaded
	if (entries === undefined) return { kind: "unavailable", reason: messages.message("sourceUnavailable") };
	return {
		kind: "ready",
		entries: entries.flatMap((entry) => {
			const indexed = facts.index.get(addressKey(entry.resource));
			if (indexed === undefined || indexed.unavailable) return [];          // unknown: never usable
			if (entry.until !== null && entry.until <= facts.now) return [];     // expired
			const use = facts.policy.decide({ kind: "use", session: row, resource: indexed }, ALLOW);
			if (use.kind === "deny") return [];
			return [{ resource: entry.resource, plugin: indexed.plugin, owner: indexed.owner, until: entry.until }];
		}),
	};
}

Core recomputes a session's entries when anything it read changes: the catalog row, the own lists, the index, a grouping's list, the policy value, or the clock. The clock is a small writable a routine advances at the next expiry, so an entry with until drops out at its deadline; every server-side admission also compares until with the current time itself, so a late timer never extends access.

Bringing and withdrawing

People change lists through core's per-user view, so the actor is always the link-stamped principal:

export const MyResources = remote("p3.resources.mine", {
	version: 1,
	params: {},
	hostAddress: () => Server(),
	variants: {
		user: {
			state: {
				owned: arr(IndexRow),      // my resources, any kind
				usable: arr(IndexRow),     // instance resources the policy lets me use
				creatable: arr(str()),     // kinds I may create: contract names (erased: wire state)
			},
			methods: {
				bring: method(obj({ resource: ObjectAddress, into: ListRef, until: nullable(int()) })),
				remove: method(obj({ resource: ObjectAddress, from: ListRef })),
				withdraw: method(obj({ resource: ObjectAddress })),   // the owner takes it out of every list
				setSource: method(obj({ session: str(), source: ResourceSource })),
			},
		},
	},
});

/** A list: a session's own, or a grouping's. */
export const ListRef = union([
	obj({ kind: lit("session"), session: str() }),
	obj({ kind: lit("grouping"), grouping: ObjectAddress }),
]);

Bringing needs both sides (owner, walkthrough): the resource side, you own it, or it is an instance resource and you administer, and the list side, the list's own rule lets you add to it (a session's own list: its owner; a grouping's: whatever its plugin says, for a project its members). Then the policy sees { kind: "bring", actor, resource, into } and may narrow or widen.

Review: instance resources in lists

The walkthrough said "for instance resources, admins can bring them; a policy plugin may widen that". Locking down a session copies instance resources from its defaults into its own list, which a non-admin must be able to do. This spec lets the resource side pass also for an instance resource the actor may already use (the policy's use answer), so the copy never widens anything. Reviewers: is that the right baseline, or should lock-down be a separate operation?

Taking out: the resource's owner can always withdraw it from every list (withdraw: core asks each list keeper to remove it); a list's maintainers can remove anything from their list (remove, the list side's rule), never touching the resource itself. Neither needs the policy's permission to take something away.

Changing the source (setSource): into a grouping, the grouping's rule for adding sessions must pass; to own, core copies the current effective list first; to defaults, only the session's owner. The policy sees { kind: "set-source", actor, session, source }.

V

Where Things Appear

Groupings as plugins: computed and curated ones, the few that carry resources, members and who sees a session.

The owner's requirement (2026-11-07): plugins contribute kinds of groupings, each grouping shows any addressable thing and renders its own header, without stepping on other plugins. This model adds one thing to that: most groupings only show, and a grouping with resources registers with core.

Groupings that only show

  • Folders are computed from where sessions work: the folders plugin reads the catalog's locations and groups by env and directory. Moving a session's location moves it to another folder. Nobody puts it there, and the plugin keeps no facts of its own.
  • Recent is per user: the recent plugin keeps a table (user, session, at) written when a user opens or sends in a session (its web facet calls its own view's touch), and serves each user their own rows. Cristina's recent list is not Mario's.
  • A mirrored SAML group shows its members (chapter IX).

None of them registers anything with core. They cannot equip a session, so being in them is never security-sensitive.

Groupings with resources

A project is a grouping with resources. So is a Discord channel linked to a session. Their plugins keep the lists, in their own tables, and tell core how to read and change them:

// plugins/resources/contract.ts
export type GroupingKind<C extends RemoteContract = RemoteContract> = { readonly contract: C };
export function groupingKind<C extends RemoteContract>(contract: C): GroupingKind<C>;

/** What a grouping kind tells core. Groupings that only show register nothing. */
export type GroupingRegistration<C extends RemoteContract> = {
	readonly kind: GroupingKind<C>;
	/** Users and groupings in each grouping, by the grouping's identity key; read for visibility and policy rules. */
	readonly members?: KeyedWatchable<readonly MemberRef[]>;
	/** Present only on a grouping with resources. */
	readonly resources?: {
		readonly lists: KeyedWatchable<readonly ListEntry[]>;
		mayBring(actor: UserId, grouping: ParamsOf<C>): boolean;    // the list side of bringing
		mayRemove(actor: UserId, grouping: ParamsOf<C>): boolean;   // maintainers taking something out
		mayJoin(actor: UserId, grouping: ParamsOf<C>): boolean;     // making it a session's source
		add(grouping: ParamsOf<C>, entry: ListEntry, ctx: Ctx): Promise<void>;
		remove(grouping: ParamsOf<C>, resource: ObjectAddress, ctx: Ctx): Promise<void>;
	};
};
export function registerGrouping<C extends RemoteContract>(r: GroupingRegistration<C>): ErasedRegistration;
export const GroupingKinds = defineRegistry<readonly ErasedRegistration[], GroupingTable>("p3.groupings", { version: 1 });

export type MemberRef =
	| { readonly kind: "user"; readonly user: UserId }
	| { readonly kind: "grouping"; readonly grouping: ObjectAddress };

The projects plugin, which knows nothing about MCP, models or ACL:

// plugins/projects/contract.ts
export const Project = remote("projects.project", {
	version: 1,
	params: { id: str() },
	hostAddress: () => Server(),
	variants: {
		maintainer: { state: { view: ProjectView }, methods: { rename: method(obj({ title: str() })), addMember: method(MemberArgs) } },
		member: { state: { view: ProjectView } },
	},
});
export const ProjectKind = groupingKind(Project);

// plugins/projects/server.ts: a host-lifetime store registers the kind once
host.serve(ProjectStore, (_params, self) => {
	const projects = self.table(ProjectRows);      // id, title, maintainers, members
	const lists = self.state(ProjectLists);        // keyed by project: ListEntry[]
	const members = self.state(ProjectMembers);    // keyed by project: MemberRef[]
	const isMember = (user: UserId, p: ParamsOf<typeof Project>) => /* expanded through core's Members */;
	self.contribute(GroupingKinds, [registerGrouping({
		kind: ProjectKind,
		members,
		resources: {
			lists,
			mayBring: isMember,
			mayRemove: isMaintainer,
			mayJoin: isMember,
			add: (p, entry, ctx) => addEntry(lists, p, entry, ctx),
			remove: (p, resource, ctx) => removeEntry(lists, p, resource, ctx),
		},
	})]);
	return { /* create, rename, addMember: through core's guarded steps (chapter VI) */ };
});

A project's sessions are a query, not a list it keeps: catalog rows whose source is this project. That is why the session points up and not the project down: two projects listing the same session would give it two sources.

Members and who sees a session

Members are users or groupings (a project can have the mirrored SAML group "engineering" as a member). Core's Members object expands them through every registration's members, cutting cycles, and serves has(grouping, user) and the groupings a user is in. The policy reads the same object.

A user sees a session when they own it, it is shared with them (the session's own people list, kept by the sessions plugin; guests stay reserved), or they are a member of its source grouping. The sessions plugin's catalog view for a user filters rows by exactly these three facts; no other grouping is asked.

A Discord channel

The Discord plugin's grouping DiscordChannel { bot, channel } is a grouping with resources. Linking a channel to a session sets the session's source to the channel; the channel's list starts nearly empty (a model provider) and the link sheet adds what the channel may use. Who may change the channel's list is the Discord plugin's rule (the link's creator, and admins: the bot is an instance resource). The people in the channel are not users; they are attributed authors of inputs, and like every sender they drive the whole list.

VI

Who May

One replaceable policy answers typed requests; core asks it at its guarded steps; views carry the answers to the page.

Groupings from SAML, from Radius and from projects do not know each other. Something must still decide that Colin may create an MCP server, that Cristina may not, and that a researcher may still use one. One policy, behind one registry, decides; core asks it at the moment an action happens, on the server.

// plugins/policy/contract.ts: core
export type Decision = { readonly kind: "allow" } | { readonly kind: "deny"; readonly reason: MessageData };

/** Everything core asks. Kinds and operations are tokens, compared by identity, never by name. */
export type Request =
	| { readonly kind: "create-resource"; readonly actor: UserId; readonly resourceKind: ResourceKind; readonly owner: UserId }
	| { readonly kind: "create-grouping"; readonly actor: UserId; readonly groupingKind: GroupingKind }
	| { readonly kind: "bring"; readonly actor: UserId; readonly resource: Indexed; readonly into: ListRef }
	| { readonly kind: "set-source"; readonly actor: UserId; readonly session: SessionRow; readonly source: ResourceSource }
	| { readonly kind: "add-member"; readonly actor: UserId; readonly member: MemberRef; readonly to: ObjectAddress }
	| { readonly kind: "use"; readonly session: SessionRow; readonly resource: Indexed }
	| { readonly kind: "administer"; readonly actor: UserId }
	| { readonly kind: "call"; readonly actor: UserId; match<C extends RemoteContract, M extends MethodName<C>>(
			op: Operation<C, M>,
		): { readonly target: ParamsOf<C>; readonly args: ArgsOf<C, M> } | undefined };

export type Policy = {
	/** The answer to one request; `baseline` is the answer core and the owning plugin give without a policy. */
	decide(request: Request, baseline: Decision): Decision;
};

/** One provider (the built-in default when no policy plugin is installed); a value that changes is a writable. */
export const Policies = defineRegistry<Policy, Policy>("p3.policy", { version: 1 });

The default policy is (_request, baseline) => baseline. Baselines come from facts the owning code has: the owner rule, the grouping's own mayBring, the session owner for setSource, the users plugin's admin flag for administer, allow for use. On one laptop nobody ever sees it.

Hard rules come before the policy and cannot be overridden: nobody creates a resource owned by another person; workers never change lists or create resources; an unknown kind is refused. A missing policy contribution (zero, or a policy plugin that failed) is not the default: the registry's compose yields deny-all until it is fixed, so removing an organization's policy never opens everything.

Asking: core's guarded steps

Core's own operations (create a resource, bring, remove, set a source, add a member, administer) are core methods that build the typed request and ask. A plugin's own operation that a company might want to restrict asks through one helper, typed by its contract:

// plugins/drives/contract.ts
export const ShareDriveLink = operation(Drive, "shareLink");

// plugins/drives/server.ts: inside the method
shareLink: async (args, ctx) => {
	await guard(access, ShareDriveLink, params, args, ownerBaseline(principal, params), ctx);   // throws forbidden on deny
	return links.create(params, args, ctx);
},

access is core's local Access object (self.get(Access, {})); guard sends it the erased request ({ operation: { contract, method }, target, args }), and core hands the policy the typed call request, whose match checks the operation by identity and gives back typed target and args. Plugins never see which policy is installed.

The rules plugin

The policy a company installs is a plugin. The one p3 ships, rules, stores rules an admin edits in a settings sheet, each "members of grouping G may ...", where G comes from any plugin (a mirrored SAML group, a hand-made team, a project):

// plugins/rules/contract.ts: persisted data, so kinds are names here (the storage boundary)
export const Permission = union([
	obj({ kind: lit("create-resource"), resourceKind: str() }),
	obj({ kind: lit("create-grouping"), groupingKind: str() }),
	obj({ kind: lit("use"), resourceKind: str() }),
	obj({ kind: lit("administer") }),
]);
export const Rule = obj({ members: ObjectAddress, may: Permission });

// plugins/rules/server.ts
host.serve(RulesPolicy, (_params, self) => {
	const rules = self.state(RulesDoc);
	const members = self.get(Members, {});
	const policy = self.writable<Policy>(denyAll);
	self.contribute(Policies, policy);
	self.on([rules, members.version], () => policy.set(rulesPolicy(rules.value.rules, members)));
	return { rules, addRule, removeRule };     // admins only: the request `administer`
});

/** A permission with rules is restricted to members of their groupings; one without rules keeps the baseline. */
function rulesPolicy(rules: readonly Rule[], members: MembersReader): Policy {
	return {
		decide: (request, baseline) => {
			const relevant = rules.filter((rule) => covers(rule.may, request));
			if (relevant.length === 0) return baseline;
			const actor = actorOf(request);    // the session's owner for `use`
			return relevant.some((rule) => members.has(rule.members, actor))
				? ALLOW
				: deny(messages.message("restricted"));
		},
	};
}

So "only engineering may create MCP servers" is one rule. Cristina in research cannot create one; she still uses Colin's in the project, because using is a separate request and has no rule. A company that wants research not to use MCP at all adds { members: everyone-but-research, may: use mcp.server }. A company with stranger needs replaces the plugin; no other plugin changes.

VII

On the Worker

The worker follows its effective list; the harness admits extensions by resource and plugin; server views check every call.

The list is computed on the server; the worker only follows it. Core's server view for workers pushes it:

	version: 1,
	params: {},                         // the worker's principal names its session; no caller-supplied id
	hostAddress: () => Server(),
	variants: {
		worker: {
			state: {
				list: SessionList,
				builtins: arr(obj({ resource: ObjectAddress, plugin: str() })),   // every declared built-in
			},
		},

	if (principal.kind !== "worker") throw forbidden("session workers only");
	const resources = self.get(Resources, {});

On the worker, core's harness plugin holds it in a host-lifetime object. A read is local; a change arrives as one state push. Nobody polls and nobody asks the server per call.

Extension grants

A plugin's worker facet contributes its Durable extension with the resource it belongs to, imported from its own contract file:

// plugins/harness/contract.worker.ts: core
export type ExtensionGrant =
	| { readonly kind: "resource"; readonly resource: Resource; readonly extension: Extension }
	| { readonly kind: "any-of-kind"; readonly of: ResourceKind; readonly extension: Extension };
export function grant<C extends RemoteContract>(resource: Resource<C>, extension: Extension): ExtensionGrant;
export function grantForKind<C extends RemoteContract>(of: ResourceKind<C>, extension: Extension): ExtensionGrant;
export const Extensions = defineRegistry<
	readonly ExtensionGrant[] | Watchable<readonly ExtensionGrant[]>, ExtensionTable
>("p3.harness.extensions", { version: 1 });

// plugins/coding-tools/worker.ts
self.contribute(Extensions, [grant(FileTools, fileToolsExtension), grant(Bash, bashExtension)]);

The harness builds Durable's registry from the extensions table and the followed list, the way p2's durableRegistry(extensions, switches) does with switches:

/** The extensions a session may run: only grants whose resource is on its list, from the plugin that serves it. */
function admitted(table: ExtensionTable, list: SessionList): readonly Extension[] {
	if (list.kind !== "ready") return [];                                  // fail closed
	return table.flatMap(({ plugin, grant }) => {
		const ok =
			grant.kind === "resource"
				? list.entries.some((e) => sameAddress(e.resource, pack(grant.resource)) && e.plugin === plugin)
				: list.entries.some((e) => e.resource.contract === grant.of.contract.name && e.plugin === plugin);
		return ok ? [grant.extension] : [];
	});
}

Three properties matter:

  • A plugin cannot borrow another plugin's resource. The entry carries the plugin that serves the resource's kind (the index's), and the table carries the plugin that contributed the grant (Chord keeps it per entry). They must be equal.
  • An unregistered built-in never runs and is reported. A grant naming a built-in absent from the pushed builtins is reported once (extension_unregistered, naming plugin and id), so the author sees the mistake.
  • Tools stop guarding themselves. p2's origin, locked and per-tool lock checks (src/runtime/tool-access.ts) go away; scope (main conversation, subagents) stays, as decided. Without code mode, deferred tools still get tool_search as in p2's durableRegistry; code mode is itself a built-in resource.

any-of-kind exists for extensions whose tools follow configured resources: the conversations tool is present when any ConversationAccess is on the list (chapter VIII), the drives tools when any drive is.

Server views check every call

Resource plugins serve per-session server views that read the same effective list, so a call through a resource that left the list a moment ago is refused even if the worker has not updated yet:

// plugins/resources/contract.ts: the helper every kind's server view uses
/** The resources of `kind` on a worker's session list, typed; empty while the list is unavailable. */
export function resourcesOf<C extends RemoteContract>(self: RemoteSelf, principal: WorkerPrincipal, kind: ResourceKind<C>):
	Watchable<readonly OnList<C>[]>;        // OnList<C> = { resource: Resource<C>; until: number | null }

/** Throws forbidden unless `resource` is on the list now and not expired (checked against the current time). */
export function admit<C extends RemoteContract>(on: Watchable<readonly OnList<C>[]>, resource: ObjectAddress): Resource<C>;

A call admitted before the commit may finish; nothing is replayed (p2 already marks MCP calls not replay-safe). Output already in the transcript stays.

VIII

Kinds in Code

Six resource kinds end to end: built-in tools, conversation access, model providers, MCP servers, machines and drives.

Every kind follows the same three parts: a contract file with its kind or built-in token, a server facet that registers it and serves a per-session view reading resourcesOf, and a worker facet that grants its extension under the same token. What differs is what the worker gets: an extension that runs locally, pushed credentials, or methods the server runs.

Built-in tools

Shown in chapter III and VII: coding-tools declares FileTools and Bash with builtin, describes them in its server facet, grants them in its worker facet. Bash and the file tools run at a conversation's location, so they work only when a machine is on the list too (below). Every p2 plugin that contributes an extension today (agent, artifacts, cache-warming, codemode, conversations, dev-tools, discord, history, locations, mcp, ports, powershell, prompt, send-file, sessions, subagents, terminals, voice) becomes one or more built-ins this way; the review checks each.

Builtins also takes instance resources of a plugin's own kind, for things a plugin brings with it:

// plugins/envs/contract.ts
export const LocalMachine = resource(EnvKind, { owner: INSTANCE, id: "local" });

// plugins/envs/server.ts: the machine p3 runs on is an instance resource, created at install
self.contribute(Builtins, [describe(LocalMachine, { label: t.message("thisMachine") })]);

describe accepts only a resource whose ownerOf is INSTANCE; anything else is left out and reported.

Charlotta's provider uses Charlotta's credential whoever sends: there is no login choice.

MCP servers: methods the server runs

Decided earlier (decision 8): a checkout's .pi/mcp.json is a suggestion, enabled per checkout and run in that env; server-configured stdio servers run on the server machine; HTTP servers have no location; there is no runOn. In this model each is one resource with its transport in its configuration:

// plugins/mcp/contract.ts
export const Transport = union([
	obj({ kind: lit("http"), url: str(), headers: opt(map(str())) }),                       // no location
	obj({ kind: lit("server-stdio"), command: str(), args: arr(str()), env: opt(map(str())) }),  // the p3 server machine
	obj({ kind: lit("checkout"), env: ObjectAddress, dir: str(), entry: str(), digest: str() }),  // an enabled suggestion
]);
export const McpConfig = obj({ name: str(), transport: Transport });
export const CreateMcp = operation(McpServers, "create");
  • Creating asks core's create-resource like every kind; a server-stdio transport runs code on the server machine, so the MCP plugin also calls guard(access, CreateMcp, {}, config, baseline) with the baseline the actor administers for that transport. A company policy can widen or narrow it, matching on the typed config.transport.
  • Suggestions: the worker reads .pi/mcp.json at its conversations' locations and reports them to its SessionMcp view; the session shows "this checkout suggests ...". Enabling one creates an MCP resource owned by the enabling user, bound to that env, directory and the entry's digest, and brings it into the session's source list. Its tools are offered only to conversations working at that env and directory; a changed entry (another digest) needs enabling again; another user visiting the checkout gets nothing until they enable it or a project lists it.
  • The worker gets one extension per MCP resource on the list (one extension, one resource), tool names prefixed by a stable short id of the resource, so two github servers never collide; every tool calls the server:
// plugins/mcp/worker.ts
host.serve(McpInSession, (_params, self) => {
	const session = self.get(SessionMcp, {});
	const grants = self.writable<readonly ExtensionGrant[]>([]);
	self.contribute(Extensions, grants);
	self.on(session.servers, ({ value }) => grants.set(value.map((server) =>
		grant(server.resource, mcpExtension(server, (tool, args, context) =>
			chord((ctx) => session.call({ server: pack(server.resource), tool, args }, ctx), context))))));
	return {};
});

// plugins/mcp/server.ts: the worker variant of SessionMcp
call: async ({ server, tool, args }, ctx) => {
	const on = admit(mine, server);                 // on the list now, not expired
	return supervisor.call({ resource: on, session: principal.session, tool, args }, ctx);
},

The supervisor keys processes by resource and placement (a checkout server per env and directory), never by session or by who sends, and closes one when no admitted session needs it. Credentials and OAuth refresh stay in the server's MCP store, as in p2 today.

Machines

An Env { owner, id } is a resource; the machine p3 runs on is the instance resource LocalMachine. A conversation's location is { env: ObjectAddress, cwd } and must name an env on the list; the worker's env adapter contributes the connection to the harness's environments registry. Moving a session to an env not on its list is refused; an env that leaves the list leaves the location unavailable (tools refuse, the session shows "relocate"), never a silent fallback to the server machine. Terminals, the workspace view and file browsing check the same env through their own server views.

IX

Sign-in and Directories

SAML and Radius touch three places: sign-in plugins create users, sync plugins mirror groups as groupings, the policy names those groupings.

Nothing about SAML or Radius appears in projects, MCP, models or the harness. They touch three places, each already in the model.

1. Sign-in creates users. A SAML plugin verifies the assertion and calls Users.signIn({ issuer, subject, name }); the result is the principal { kind: "user", id } the kit's session carries. A Radius plugin does the same with a Radius account. Emails are never identities.

// plugins/saml/server.ts
self.contribute(Http, { routes: { "POST /saml/acs": async (request, ctx) => {
	const assertion = await verify(await request.body(), idp.value, ctx);       // signature, audience, time
	const id = await users.signIn({ issuer: assertion.issuer, subject: assertion.subject, name: assertion.name }, ctx);
	await directory.mirror({ user: id, groups: assertion.groups }, ctx);
	return signInResponse(sessions, { kind: "user", id: userId(id) }, request);
} } });

2. Sync mirrors groups as groupings. The SAML plugin's SamlGroup { name } is a grouping kind registering only members; its directory updates them at every sign-in (and from SCIM, if the company has it). A Radius sync plugin mirrors Radius org groups the same way through the Radius API. These groupings show their members in a sidebar section like any other grouping and can be members of projects.

3. The policy names them. The rules plugin's settings sheet offers every grouping as "members of ..." and every creator as a kind. "Only engineering may create MCP servers" is { members: SamlGroup{engineering}, may: { kind: "create-resource", resourceKind: "mcp.server" } }.

Radius resources are ordinary resources. Signing in with Radius can create the user's Radius MCP server and Radius model provider: the Radius plugin calls the MCP and models plugins' create methods as that user, inside the sign-in, so "users create resources only for themselves" holds. Whether one Radius sign-in can serve the relay connection, the model gateway and the MCP server is the open question to Armin and Vegard; in p2 these are three logins. The relay (the brain's outbound connection) is an instance integration an admin sets up, not a session resource.

At the deadline the entry leaves the effective list; a call a second later is refused by requireAction against the current time, whatever the worker still shows.

SAML: only engineering creates MCP servers. The rule exists; Colin (engineering) sees the MCP creator, Cristina (research) does not: her creatable lacks mcp.server. Colin brings his server into pi; Cristina's sessions in pi use it. An admin adds research to the rule: the sequence in chapter VI, and her picker shows the creator without a reload.

A new tool in normal sessions. As in Mario's case: built-in, instance-owned, included by the defaults rule. A Discord session does not get it: its source is the channel's list.

Drives. The company drive is an instance Drive; Mario's own drive is his. Both in pi's list: the agent's drive tools see two drives; members open both read-only from the project's resources; Mario manages his own.

Open Questions

What this spec leaves open, for the reviewers and then the owner.

  1. Excluding from defaults. p2 has a code mode switch; here code mode is a built-in on the defaults. Someone who wants it off in every session needs an exclusion on their defaults rule (proposal: a per-user excluded list core keeps, the rule minus it), or must lock sessions down one by one.
  2. One source per session. Both designs call it their weakest point: a session cannot draw from two projects. The owner accepted it in the walkthrough; reviewers should name any p2 feature it breaks.
  3. Peers. conversations.peers reaches sessions sharing the session's source. p2 reaches every session; in a project, reaching the session owner's private sessions would expose them to every member.
  4. Instance resources when bringing (the review note in chapter IV).
  5. MCP stdio next to the code. p2 runs non-shared stdio servers at the location by default; decision 8 leaves that only to checkout suggestions (stress test, gap 13).
  6. Execution on the server machine and SSH keys in workers. The stress test's gap 1 (local location, server stdio, credential commands, project plugins) and how workers reach envs without private keys stay their own track; this model only makes them admin-only by baseline.
  7. Ambient cloud credentials. Bedrock and Vertex resolve AWS profiles and ADC files; pushing an empty AuthResult does not work. Those providers need a server-side stream or are unsupported.
  8. One Radius sign-in for relay, gateway and MCP: pending Armin and Vegard.
  9. Creation order and retries (the review note in chapter III).
  10. Copies. Clone and fork copy the source field and an own list; a grouping source stays; a Discord channel source becomes defaults for the copy. To be confirmed per plugin.
