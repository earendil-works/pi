Before we begin

p3 gives one Pi to each person. Colin's plan has two dates. On December 1, Pi Roam: a person runs their own Pi, reaches it through Radius, backs it up there. On December 18, Org Devices: an org has a machine, and each member creates their own Pi on it with "Create my Pi here" in Radius. Dana works at Acme. Her Pi is hers: her sessions, her logins, her plugins. But Acme wants three things from it. It should start with Acme's plugins, MCP servers and models already set up. It should not share sessions with people outside Acme. And it should not quietly load code Acme never approved.

The obvious answer is a permission system: plugins name their operations, the org writes rules over them, a policy plugin decides each call. The consultations showed what that costs. Every plugin author classifies every method, the base grows levels, a rule registry and a may member, and the result is still a guardrail, because code running in the Pi's process can skip any check. And it does not even cover the first wish: provisioning ("start with our MCP servers") is a separate mechanism.

This design takes the other road. Everything an org wants is a setting. Plugins already need settings for their settings page; they declare them through one base mechanism. Acme's values form one managed layer on top of Dana's own values. For each setting it names, the layer either provides a default (Dana may change it, or add entries beside Acme's) or locks it (only Acme's value counts). "Start with our MCP servers" and "no MCP servers except ours" are the same data with a different lock.

Ten things to know

  1. An org profile is a list of setting values, each with a lock: default or locked. Plugins to install, MCP servers, model providers, sharing and peer audiences, company instructions: all are settings. There are no operations, levels, rule tables or policy functions.
  2. Plugins declare settings with defineSetting, a token with a name, a schema, an initial value and a merge kind: value (one value) or entries (a record by name, such as MCP servers). Authors write nothing about orgs.
  3. Every write goes through Settings.set: the settings page, the agent's tools, other plugins. It refuses a locked setting and any change to an org's entry with the error code managed ("Managed by Acme").
  4. Enrollment is a root-owned file: "you belong to org Acme, its server is this, its key is this; do nothing before you have synced". It holds no secrets and no settings.
  5. The profile comes from the org server (Radius), signed with the org's key. An enrolled Pi starts locked, fetches its profile, installs the required plugins, writes the signed profile as its cache and unlocks. Later starts use the cache at once and follow the server live.
  6. The gate is one tagged state: unmanaged, pending, ready, stale, revoked. Sessions start, workers authorize and plugins load only when it is unmanaged or ready.
  7. In the Pi it is a guardrail; at Radius it is real. It stops Dana's agent and well-behaved plugins. A shell under the Pi's Unix user, root, or an admitted plugin can ignore it. Sharing, peers and org-paid models are enforced at Radius from the same profile.
  8. The base must have one settings mechanism now, before any org exists: one write path, a managed error, base switches for sharing and peers, and a gate that is always unmanaged. Retrofitting a single write path later is the expensive part.
  9. One mechanism covers every case Acme cares about. Adding an MCP server, editing Acme's Jira entry, installing a plugin, writing one, sharing outside Acme, a live removal, and a lock on Acme's own plugin's setting all end in Settings.set, admit or a setting a plugin follows. Chapter IV traces each one through the code.
  10. On an Org Device the shell is moved out of reach. The Pi runs as a service under its own Unix user, from a root-owned install; the agent's tools run as the member through pi-env; Radius serves org resources only to a Pi that proves a device-bound key. Then a member's agent can no longer edit the Pi's files at all.

Words used throughout

A member is a person in an org, and the owner of one Pi. A setting is a named, typed piece of configuration a plugin declares with defineSetting. Its merge kind is value (one value) or entries (a record of named entries). The user layer holds the member's own values; the managed layer holds the org's, each with a lock: default (the org's value is a starting point) or locked (only the org's value counts). The effective value is what plugins read after both layers are combined. The enrollment file binds a machine's Pis to an org. The profile is the org's managed layer for one member's Pi, signed with the org key; the Pi keeps the last good one as its cache. The gate is the Pi's org state. Admit is the kit's check that decides at discovery which plugins load. A guardrail holds against the member's agent and well-behaved code; a wall holds even against a modified Pi, because Radius enforces it. On a locked-down machine the Pi runs as a service user of its own, and the agent's tools run as the member through pi-env, the tool daemon of packages/env.

What this supersedes

The decision "Resource model direction" (2026-11-08) planned one replaceable policy plugin that guards create, bring and add-member operations. It is dropped: an org restricts by locking settings. Company resources of the decision "Instance resources" (2026-11-13: a shared login, a team server) become org-managed entries of the setting that holds them, such as an MCP server in mcp.servers. The research note authz-research.md (named operations, levels, may) is not pursued.

I

What Acme Sets

The two files behind an org-managed Pi: the admin's enrollment and Acme's signed profile.

Two documents make Dana's Pi Acme's. The first sits on the machine and never changes: it says which org the machine's Pis belong to. The second lives in Radius, changes whenever Acme's admin edits it, and says what Acme wants. The split matters. The machine admin decides once that a machine is Acme's. Acme's admin then edits one profile in Radius, and every member's Pi follows it live, with no agent on the machine keeping files in sync.

The enrollment file

On an Org Device, the Device's own setup (running as root, with the org's service token) writes this file once. On a member's laptop, the org's device management (MDM: the tool an IT department uses to push files and settings to company laptops) delivers it. Without the file, a Pi is personal and unmanaged, as on December 1.

// PROPOSED · /etc/p3/enrollment.json, owned by root, mode 0644, parent directories root-owned
{
  "org": "acme",
  "name": "Acme",
  "server": "https://radius.example.com/orgs/acme",
  "orgKey": "ed25519:MCowBQYDK2VwAyEAq4…",
  "pluginSources": ["https://github.com/acme/"]
}

It holds no secrets. orgKey is the public key profiles are signed with. pluginSources limits where the org may push code from: a profile naming a plugin outside these prefixes is refused, even when signed. The path is fixed in the base code: no flag and no environment variable can point the Pi at another file, so a member's agent cannot enroll the Pi somewhere else or skip enrollment.

The Pi's own credential is not in the file. "Create my Pi here" in Radius, or Dana's Radius sign-in on the gate page, gives her Pi its own token, kept in the Pi's data directory. A shared token in a machine-wide file would be wrong: the profile is per member.

The consultation says the profile is signed "with the org key, not with Radius's key, so Radius alone cannot forge one". If Radius's profile editor signs with a per-org key it stores, the signature still stops edits of the cache on the machine, but a compromised Radius can push code to every member's Pi. Decision needed (Open Questions).

II

Everything Is a Setting

One declaration per setting, two merge kinds, two locks, one write path: what plugin authors write, and what they do not.

Without a shared mechanism, every plugin keeps its configuration its own way. p2's MCP plugin reads mcp.json, the models plugin reads models.json. An org that wants to lock MCP servers would need a hook in each of them, and a plugin that keeps a private config file would escape any lock. So the base owns configuration: a plugin declares each setting once, the base stores the member's values, combines them with the org's, and every write goes through one method that knows about locks.

Declaring a setting

A setting is a token in the contract file of the plugin that owns it, like a defineState token: a name, a schema, a merge kind and an initial value. The plugin contributes it to the registry SettingKinds, from which the settings page renders its forms and which the Pi reports to the org server so its admin form knows the setting.

// PROPOSED · apps/p3/plugins/mcp/contract.ts (full file in chapter IV)
export const McpServers = defineSetting("mcp.servers", map(McpServerConfig), { merge: "entries", initial: {} });

defineSetting, SettingKinds, Settings and setting() are in apps/p3/app/v1/settings.ts, shown in full in chapter IV.

Two merge kinds, two locks

Value settings hold one value: a boolean, a string, an object. p3.sharing.audience is a value setting. Entries settings hold a record of named entries: MCP servers by name, providers by name, plugins by name. The difference matters for the default lock: an org default of a value setting is replaced by the member's value; org entries are added beside the member's.

The effective value follows four rules:

Managed layer says Value setting Entries setting
nothing the member's value, else the initial value the member's entries
default the member's value, else the org's the member's entries plus the org's; on the same name the org's wins, read-only
locked the org's value the org's entries only
(gate not open) the initial value none

A locked setting does not delete the member's values. They are kept and ignored, so when Acme unlocks mcp.servers, or Dana's Pi leaves Acme, her own servers come back. While the gate is closed (pending, stale, revoked), every setting reads its initial value; nothing from Dana's own configuration acts before Acme has spoken.

The one write path

Settings is a local object with empty params on the server: one per Pi, persisted, the only writer of the user layer. Its one method, set, takes either a whole value or one entry of an entries setting, and refuses in this order:

  1. the gate is closed: gated, "Waiting for Acme";
  2. no loaded plugin declares the name: unknown_setting;
  3. the org locked the setting: managed, "Managed by Acme: mcp.servers is locked";
  4. the write touches one of the org's entries: managed, "Managed by Acme: the entry jira of mcp.servers";
  5. the value fails the declaring plugin's schema: invalid_value.

Then it writes Dana's layer. The gate is read per call, not when the page was drawn, so a lock that arrived a second ago counts. Pages and the terminal render managed as "Managed by Acme" and draw a lock beside every name in the store's managed member; Dana's agent gets the same error from its tools, which call the same set. Chapter IV has the code (apps/p3/plugins/settings/server.ts) and traces both paths.

Workers read settings through the server

Settings is a server object. A session worker that needs a setting (the harness reading prompt.instructions) follows it through a server view, as other per-session server data is followed today; the worker never holds its own copy.

What a plugin author writes

The MCP plugin declares its servers as a setting, contributes it, and reconciles its connections with the effective value. It never names an org, a lock, a gate or a principal.

// PROPOSED · apps/p3/plugins/mcp/server.ts, shortened (full file in chapter IV)
export default defineFacet<P3Principal>((host, facet) => {
	facet.contribute(SettingKinds, [McpServers]);
	host.serve(McpConnections, (_params, self) => {
		const servers = setting(self, McpServers);                     // Acme's entries, plus Dana's unless locked
		self.on(servers, async ({ value }) => reconcile(value));       // a server an update locks out disconnects now
		return { status, tools, call };
	});
});

The self.on routine is needed for Dana's own edits anyway: when she removes a server on the settings page, it disconnects. An org update that locks a server out takes the same path. That is the whole point of the design: the plugin already follows its configuration, so following the org costs it nothing.

The plugin review rule is one sentence: all configuration goes through settings. A plugin that keeps a private config file escapes the locks. The remedy is not a check in the base but the plugin list: Acme admits only plugins it reviewed.

Provisioning and deny lists are the same data

Acme's first draft gave every member Jira and Linear and let them add more: mcp.servers with lock default. A month later security asks for "no MCP servers except ours". The admin changes one word, default to locked. Dana's personal servers disconnect within a second, stay stored, and come back if the lock is ever lifted. There is no second mechanism for restrictions.

III

Enrolled, Locked, Ready

How a Pi waits for its org, unlocks, starts from its cache and follows updates, and the one kit change it needs.

The enrollment file says "do nothing before you have synced". The Pi needs a single place that knows whether it has synced, which every part consults: the start of a session, a worker's authorization, plugin loading, Settings.set. That place is the gate, a derived value of one base object, OrgGate.

Five states

// PROPOSED · OrgGate.gate
unmanaged                        no enrollment file: personal Pi, everything open
pending { org, why }             enrolled, no valid profile yet: locked; the page shows "Connect to Acme" and why
ready   { profile, live }        a valid profile is applied: open; live = following the server now, else from cache
stale   { profile }              offline longer than the profile's maxOffline: locked again (only if Acme set one)
revoked { org }                  Acme removed this member or Pi: locked; the data stays where it is

Locked means four things, all through hooks Chord already has or the one kit change below:

  • The session worker kind's start throws and its synchronous authorize refuses: no session runs.
  • admit lets only the app's own root load: the base, Settings, OrgGate and the gate page. Neither Acme's plugins nor Dana's own load.
  • Every setting reads its initial value, and Settings.set refuses with "Waiting for Acme".
  • The base's own paths (share a session, connect to a peer) refuse.

First start

  1. The start script (base code, not a plugin) reads the enrollment file before startServer, and the cache if there is one. With no cache the gate starts pending.
  2. OrgGate connects to server with the Pi's token. Without a token, the gate page asks Dana to sign in with Radius.
  3. It checks the profile: the signature against orgKey, org, member and pi, every plugin source under pluginSources. A profile that fails is not used, and the gate page says why.
  4. It installs every required plugin at its pinned ref into the org root, and checks each installed tree against its hash. A required plugin that fails to install or build keeps the gate pending, with the reason on the page.
  5. It writes the signed profile as the cache, in one atomic rename. This one write is the commit: the managed layer is whatever the cache holds.
  6. The gate turns ready. The base runs Apply: admit now follows the profile, so Acme's plugins and Dana's admitted ones load, and workers may start.

Later starts

The start script reads the cache with the enrollment file, before startServer, and checks the signature and, if Acme set maxOffline, the age of issuedAt. If both hold, the gate is ready from the first moment, with no network wait, and admit loads the right plugins at the first discovery. OrgGate follows the server in the background.

Review: the cache is a file, not a Chord document

The consultation kept the cache as a persisted Chord document in the server store. But admit runs at the first discovery, inside startServer, before any store object exists. With the cache in the store, every start would load only the app root first and run a second Apply once the gate reads the cache: a second build pass on every start, against the decision "Efficiency is a requirement". A file the start script reads synchronously avoids it. A file also moves with the machine, not with a backup: restoring a backup onto another machine must enroll there, not carry Acme's profile along.

Updates

A profile with a higher revision arrives live. Its settings and its plugins apply in a fixed order:

  1. Settings first, at once. The new cache is written and the gate's profile changes. Every effective setting changes in place: the MCP plugin disconnects a server that is now forbidden, the sharing plugin ends shares whose audience no longer conforms, the peer plugin closes links outside the audience. Removed plugins unload on the Apply that follows.
  2. Plugin additions when installed. New and updated plugins install into the org root; each loads with the next Apply once its hash matches. Until then the previous version keeps running.
  3. A failed install is reported, to Dana on the page and to Acme through Radius, and retried. It never holds back a tightening: a broken new plugin in the same update as a removed MCP server does not keep that server connected.

No restart is needed: the roots stay fixed, and admit plus Apply change which plugins are loaded.

Review: "never half-applied" refined

The consultation applies an update whole or not at all, keeping the last good profile when an install fails. Two other consultations point out that this lets one broken plugin publish keep a revoked MCP server or an outside share alive. Settings first, plugins when installed, keeps every tightening immediate; additions wait for their install.

The one kit change

Today startServer fixes the plugin roots to two (packages/chord/src/node/app/app.ts, line 348: the app root, required, and layout.plugins) and loads everything discovered. Discovery already lets the first root win a name and reports the duplicate (discover.ts, discoverPlugins), so a plugin in a later root cannot shadow an org plugin.

own() reads the effective p3.plugins.own: from the cached profile before the host is up, from Settings after. admits (apps/p3/src/admit.ts, in chapter IV) is a few lines. The app root always loads. Nothing else loads while the gate is locked. In the org root, a plugin loads when its name is an org entry of p3.plugins and its tree matched its hash. In the member root, a plugin loads when the Pi is unmanaged, or when the effective p3.plugins.own is true.

p3.plugins.own is how "no agent-written plugins" becomes enforceable: not by tracking who wrote a file, which no check can know, but by loading only approved builds. An org plugin edited in place no longer matches its hash: the base checks the org root's hashes at start and before each Apply, and an edited plugin stays out until it is installed again.

The gate object

OrgGate owns the connection to the org server as a native, follows it, and runs installs and Apply in a routine.

// PROPOSED · plugins/org/server.ts (app root). Chord API: local, self.open, self.follow, self.get, self.derive,
// self.on. `OrgClient` (base code) reads the enrollment file and the cache, follows the server with backoff, checks
// profiles, and writes the cache by atomic rename; `Plugins` is the plugin service of chapter IV.
host.serve(OrgGate, (_params, self) => {
	const client = self.open((ctx) => openOrgClient(ctx), (c) => c.close());
	// { enrollment, cached, offered, revoked, live, now }: the client's observer, attached once it opened.
	const org = self.follow((observer, ctx) => client.value.attach(observer, ctx));
	const plugins = self.get(Plugins, {});
	const offered = self.derive([org], ([o]) => o.offered);   // a checked profile newer than the cache, or null
	self.on(offered, async ({ value }, ctx) => {
		if (value === null) return;
		const first = org.value.cached === null;
		// First sync: required plugins install before anything opens; a throw leaves the gate pending.
		if (first) {
			const failed = await plugins.reconcile(orgPlugins(value), ctx);
			if (failed.length > 0) throw new PluginError("required_failed", failed.map((f) => `${f.name}: ${f.error}`).join("; "));
		}
		await client.value.commit(value, ctx);                  // the cache is the managed layer: settings apply now
		// Updates: settings first, plugins when installed; failures are reported and retried, never thrown.
		if (!first) await plugins.reconcile(orgPlugins(value), ctx);
		await plugins.apply(null, ctx);                         // recheck hashes, readmit, the kit's applyChanges
	});
	return { gate: self.derive([org], ([o]) => gateOf(o)) };
});

gateOf is the table of five states as a pure function. The first sync is the same routine: with no cache, offered is the first profile, and the cache is written only after reconcile installed the required plugins. When the routine throws, the client offers the profile again after its backoff.

IV

Acme End to End

What Acme's admin types into Radius, the files that come out of it, the code they pass through, and eight traces from a click or a tool call to what Dana and her agent see.

The chapters so far describe the mechanism. This one shows all of it at once, for one org: what the admin fills in, the two documents that result, every file of p3 that takes part, and what happens, line by line, in the eight cases an org cares about. import { compile, type Validator } from "@earendil-works/pi-schema";
import { Server } from "./hosts.ts";

/** A declared setting as the registry and the store see it. */
export type SettingKind = {
	readonly name: string;
	readonly merge: "value" | "entries";
	readonly initial: JsonValue;
	/** Reported to the org server, which renders its form from it. */
	readonly schema: Schema;
	/** Checks a whole value (an entries setting: the whole record); compiled once, at declaration. */
	readonly validator: Validator;
};

/** A declared setting with its value type. */
export type Setting<T extends JsonValue> = SettingKind & { readonly initial: T };

/** Declares a setting; its plugin contributes it to `SettingKinds` and reads it with `setting(self, token)`. */
export function defineSetting<S extends Schema>(
	name: string,
	schema: S,
	options: { readonly merge: "value" | "entries"; readonly initial: Static<S> & JsonValue },
): Setting<Static<S> & JsonValue> {
	return { name, merge: options.merge, initial: options.initial, schema, validator: compile(schema) };
}

/** Every declared setting by name, with its plugin; a name declared twice is reported, the first by plugin name kept. */
export const SettingKinds = defineRegistry<readonly SettingKind[], ReadonlyMap<string, TableItem<SettingKind>>>(
	"p3.setting-kinds",
	{ version: 1 },
);

/** How the org manages one setting: what pages draw and the agent is told. */
export const ManagedMark = obj({ orgName: str(), lock: oneOf("default", "locked"), entries: arr(str()) });

/** One write: a value setting's whole value, or one entry of an entries setting (`null` removes it). */
export const SettingWrite = union([
	obj({ kind: lit("value"), name: str(), value: unknown() }),
	obj({ kind: lit("entry"), name: str(), entry: str(), value: unknown() }),
]);

export type SettingWrite = Static<typeof SettingWrite>;

/** The settings store, on the server: the only writer of the member's values (server objects only). */
export const Settings = local("p3.settings", {
	version: 1,
	params: {},
	members: {
		/** Effective values by setting name. */
		effective: map(unknown()),
		/** The settings the org manages. */
		managed: map(ManagedMark),
		set: method(SettingWrite),
	},
});

/** The store for the owner's page and terminal and the owner's session agents. */
export const SettingsView = remote("p3.settings-view", {
	version: 1,
	params: {},
	hostAddress: () => Server(),
	variants: {
		main: {
			state: { effective: map(unknown()), managed: map(ManagedMark) },
			methods: { set: method(SettingWrite) },
		},
	},
});

/** A setting's effective value, for any server object. */
export function setting<T extends JsonValue>(self: Self, token: Setting<T>): Watchable<T> {
	const all = self.get(Settings, {}).effective;
	// Cast: `set` and the profile check validated the value against this token's schema.
	return self.derive([all], ([values]) => (values[token.name] ?? token.initial) as T);
}

/** The error a plugin throws when an effective setting forbids an action; pages and the harness say who manages it. */
export function refusedBy(token: SettingKind, message: string): PluginError {
	return new PluginError("refused_by_setting", message, { setting: token.name });
}

refusedBy is the only thing a plugin may use that sounds like policy, and it says nothing about orgs: it names the setting that forbade the action. Whether that setting is Dana's own choice or Acme's lock is for the page and the harness to say, from managed.

const UserLayer = defineState("p3.settings.user", {
	schema: obj({ values: map(unknown()) }),
	version: 1,
	initial: () => ({ values: {} }),
	persist: true,
	checkpointWhen: () => true,
});

export default defineFacet<P3Principal>((host) => {
	host.serve(SettingKinds, {
		compose: (table, context) =>
			keyedEntries(table, (kinds) => Object.fromEntries(kinds.map((kind) => [kind.name, kind])), context.report),
	});

	host.serve(Settings, (_params, self) => {
		const user = self.state(UserLayer);
		const kinds = self.registry(SettingKinds);
		const gate = self.get(OrgGate, {}).gate;
		return {
			effective: self.derive([user, kinds, gate], ([mine, declared, now]) => effectiveAll(mine.values, declared, now)),
			managed: self.derive([gate], ([now]) => managedMarks(now)),
			set: async (write, ctx) => {
				// Followed state, read per call: a profile that arrived since the page rendered counts.
				const kind = writable(write, kinds.value.get(write.name)?.value, gate.value);
				const next = write.kind === "value" ? write.value : withEntry(user.value.values[write.name], write.entry, write.value);
				// Trust boundary: the page's and the agent's input, checked against the declaring plugin's schema.
				const checked = kind.validator.validate(next);
				if (!checked.ok) throw new PluginError("invalid_value", `Invalid value for ${write.name}`, { errors: checked.errors });
				await user.change((draft) => {
					draft.values[write.name] = next;
				}, ctx);
			},
		};
	});

	host.serve(SettingsView, (_params, principal, self) => {
		// The owner (page, terminal) and the owner's session workers; a guest never writes settings.
		if (principal.kind !== "user" && principal.kind !== "worker") throw forbidden("Settings are the owner's");
		const settings = self.get(Settings, {});
		return {
			variant: "main",
			members: { effective: settings.effective, managed: settings.managed, set: (write, ctx) => settings.set(write, ctx) },
		};
	});
});

/** The declared setting `write` may change, or the refusal. */
function writable(write: SettingWrite, kind: SettingKind | undefined, gate: Gate): SettingKind {
	if (gate.kind !== "unmanaged" && gate.kind !== "ready")
		throw new PluginError("gated", `Waiting for ${gate.orgName}`, { setting: write.name });
	if (kind === undefined) throw new PluginError("unknown_setting", `No setting ${write.name}`);
	const managed = gate.kind === "ready" ? gate.profile.settings[write.name] : undefined;
	if (managed === undefined) return kind;
	const orgName = gate.profile.orgName;
	if (managed.lock === "locked")
		throw new PluginError("managed", `Managed by ${orgName}: ${write.name} is locked`, { setting: write.name });
	if (write.kind === "entry" && kind.merge === "entries" && Object.hasOwn(managedEntries(managed), write.entry))
		throw new PluginError("managed", `Managed by ${orgName}: the entry ${write.entry} of ${write.name}`, {
			setting: write.name,
			entry: write.entry,
		});
	return kind;
}

/** Every declared setting's effective value: the table in chapter II. */
function effectiveAll(
	mine: Readonly<Record<string, JsonValue>>,
	declared: ReadonlyMap<string, { readonly value: SettingKind }>,
	gate: Gate,
): Record<string, JsonValue> {
	const open = gate.kind === "unmanaged" || gate.kind === "ready";
	const layer = gate.kind === "ready" ? gate.profile.settings : {};
	const out: Record<string, JsonValue> = {};
	for (const [name, { value: kind }] of declared) {
		out[name] = open ? effectiveOf(kind, layer[name], mine[name]) : kind.initial;
	}
	return out;
}

/** One setting's effective value from the org's entry (if any) and the member's value (if any). */
function effectiveOf(kind: SettingKind, managed: ManagedSetting | undefined, mine: JsonValue | undefined): JsonValue {
	if (managed === undefined) return mine ?? kind.initial;
	// An org value that fails the plugin's schema: a lock reads as the initial value, a default as absent (reported at sync).
	const valid = kind.validator.check(managed.value);
	if (managed.lock === "locked") return valid ? managed.value : kind.initial;
	if (!valid) return mine ?? kind.initial;
	if (kind.merge === "value") return mine ?? managed.value;
	// Cast: an entries setting's values are records (its schema is a `map`).
	return { ...((mine ?? {}) as Record<string, JsonValue>), ...(managed.value as Record<string, JsonValue>) };
}

managedMarks, managedEntries and withEntry are three-line helpers: the marks are { orgName, lock, entries: Object.keys(value) } per managed setting, and withEntry copies the member's record with one entry put or deleted. The member's own entry named like an org entry stays stored and is hidden by the spread, so it comes back if Acme ever drops its entry.

// The plugin service: installs into the right root, checks org plugins against their hash, writes agent plugins, and
// runs Apply. `PluginManager` is the kit's platform binding (base inventory #14): install, readmit, apply, discovered.

import { rm } from "node:fs/promises";
import { join } from "node:path";
import { forbidden, PluginError } from "@earendil-works/chord";
import type { Context } from "@earendil-works/chord/context";
import { defineFacet, type P3Principal, PluginManager } from "@p3/app/v1";
import { OrgGate } from "@p3/app/v1/org";
import { OwnPlugins, PluginEntries, type PluginEntry, Plugins, PluginsView } from "@p3/app/v1/plugins";
import { refusedBy, Settings, setting } from "@p3/app/v1/settings";
import { MEMBER_ROOT, ORG_ROOT, readVerified, writeVerified } from "../../src/org/roots.ts";
import { treeHash } from "../../src/org/tree-hash.ts";

export default defineFacet<P3Principal>((host) => {
	host.serve(Plugins, (_params, self) => {
		const kit = self.get(PluginManager, {});
		const settings = self.get(Settings, {});
		const entries = setting(self, PluginEntries);
		const own = setting(self, OwnPlugins);
		const gate = self.get(OrgGate, {}).gate;
		const stored = self.open(() => readVerified(ORG_ROOT), () => {});
		const verified = self.writable<Readonly<Record<string, string>>>({});
		// The start script read the same file for its first discovery; this copy serves the catalog and later Applies.
		self.onLive(() => verified.set(stored.value));

		/** Installs an org entry into the org root and keeps it only if its tree matches the entry's hash. */
		const installOrg = async (name: string, entry: PluginEntry, ctx: Context) => {
			await kit.install({ source: entry.source, root: ORG_ROOT }, ctx);
			const actual = await treeHash(join(ORG_ROOT, name));
			if (actual !== entry.hash) {
				await rm(join(ORG_ROOT, name), { recursive: true, force: true });
				throw new PluginError("hash_mismatch", `${name}: the installed tree is not the approved build`);
			}
			const next = { ...verified.value, [name]: actual };
			await writeVerified(ORG_ROOT, next);                  // read by the start script at the next start
			verified.set(next);
		};

		return {
			catalog: self.derive([kit.discovered, entries, settings.managed, gate, verified], (values) => catalogOf(...values)),
			verified: self.derive([verified], ([v]) => v),
			install: async (request, ctx) => {
				const mark = settings.managed.value[PluginEntries.name];
				if (request.kind === "catalog") {
					// Only the org's entries are in the catalog to install from by name.
					if (!mark?.entries.includes(request.name)) throw new PluginError("unknown_plugin", `${request.name} is not in the catalog`);
					await installOrg(request.name, entries.value[request.name]!, ctx);
				} else {
					if (!own.value) throw refusedBy(OwnPlugins, "Plugins from other sources do not load on this Pi");
					if (mark?.lock === "locked") throw refusedBy(PluginEntries, "Only the catalog's plugins can be installed");
					const [name] = await kit.install({ source: request.source, root: MEMBER_ROOT }, ctx);
					await settings.set({ kind: "entry", name: PluginEntries.name, entry: name!, value: { source: request.source, hash: null, required: false } }, ctx);
				}
				await kit.readmit(ctx);
				await kit.apply(ctx);
			},
			write: async ({ plugin, path, content }, ctx) => {
				if (!own.value) throw refusedBy(OwnPlugins, "Plugins written on this Pi do not load");
				await writePluginFile(MEMBER_ROOT, plugin, path, content, ctx);   // stays inside the member root
			},
			reconcile: async (wanted, ctx) => {
				const failures: { name: string; error: string }[] = [];
				// `wanted` comes from the offered profile: at the first sync it is not the effective value yet.
				for (const [name, entry] of Object.entries(wanted)) {
					const installed = Object.hasOwn(verified.value, name);
					if (verified.value[name] === entry.hash || (!entry.required && !installed)) continue;
					await installOrg(name, entry, ctx).catch((error: Error) => failures.push({ name, error: error.message }));
				}
				await removeUnlisted(ORG_ROOT, wanted, ctx);          // dropped by the org: gone at the next Apply
				return failures;
			},
			apply: async (_args, ctx) => {
				// An org plugin edited in place no longer matches its hash: it is dropped from `verified` and left out.
				verified.set(await recheck(ORG_ROOT, verified.value));
				await kit.readmit(ctx);
				await kit.apply(ctx);
			},
		};
	});

	host.serve(PluginsView, (_params, principal, self) => {
		if (principal.kind !== "user" && principal.kind !== "worker") throw forbidden("Plugins are the owner's");
		const plugins = self.get(Plugins, {});
		return {
			variant: "main",
			members: {
				catalog: plugins.catalog,
				install: (request, ctx) => plugins.install(request, ctx),
				write: (file, ctx) => plugins.write(file, ctx),
				apply: (_args, ctx) => plugins.apply(null, ctx),
			},
		};
	});
});

// PROPOSED · apps/p3/src/admit.ts (base code)
// Which discovered plugins load: the kit asks `admits` at every discovery (the kit change of chapter III).

import type { Plugin } from "@earendil-works/chord/plugins";
import type { Gate } from "../app/v1/org.ts";

/** What admission depends on: the gate, the org root's verified hashes, and the effective `p3.plugins.own`. */
export type AdmitState = {
	readonly gate: Gate;
	readonly verified: Readonly<Record<string, string>>;
	readonly ownPlugins: boolean;
};

export type Roots = { readonly app: string; readonly org: string; readonly member: string };

/** Whether `plugin` loads now. */
export function admits(state: AdmitState, plugin: Plugin, roots: Roots): boolean {
	if (plugin.root === roots.app) return true;
	const { gate } = state;
	if (gate.kind === "unmanaged") return true;
	if (gate.kind !== "ready") return false;
	if (plugin.root === roots.org) {
		// Cast: `p3.plugins` passed its schema when the profile was checked.
		const entry = (gate.profile.settings["p3.plugins"]?.value as Record<string, { hash: string }> | undefined)?.[plugin.name];
		return entry !== undefined && state.verified[plugin.name] === entry.hash;
	}
	return state.ownPlugins;
}

import { readdir, readFile } from "node:fs/promises";
import { join, relative, sep } from "node:path";

/** sha256 over a plugin's files: sorted relative paths, each with its length and bytes; `.git` and `node_modules` left out. */
export async function treeHash(dir: string): Promise<string> {
	const files = (await readdir(dir, { recursive: true, withFileTypes: true }))
		.filter((entry) => entry.isFile())
		.map((entry) => relative(dir, join(entry.parentPath, entry.name)).split(sep).join("/"))
		.filter((path) => !path.startsWith(".git/") && !path.includes("node_modules/"))
		.sort();
	const hash = createHash("sha256");
	for (const path of files) {
		const bytes = await readFile(join(dir, path));
		hash.update(`${path}\0${bytes.length}\0`);
		hash.update(bytes);
	}
	return `sha256-${hash.digest("hex")}`;
}

The hash covers the plugin's own files, including its package-lock.json; npm install (run by the kit with --ignore-scripts) checks every dependency against the integrity hashes in that lockfile. A plugin without a lockfile cannot be pinned, and Radius refuses to save it as an org plugin.

// PROPOSED · apps/p3/plugins/harness/refusals.ts (app root, worker side)
// Every tool error goes through `toolError`: a refusal that names a setting tells the model who manages it and that
// retrying will not help.

import { PluginError } from "@earendil-works/chord";
import type { ToolExecutionResult } from "@earendil-works/pi-durable";
import type { ManagedMark } from "@p3/app/v1/settings";

/** The tool result for `error`, with `managed` (the view's marks) to say who manages the setting it names. */
export function toolError(error: unknown, managed: Readonly<Record<string, ManagedMark>>): ToolExecutionResult {
	if (!(error instanceof PluginError)) return text(error instanceof Error ? error.message : String(error));
	// Wire input: `details` came over a link.
	const setting = typeof error.details === "object" && error.details !== null && "setting" in error.details ? String(error.details.setting) : undefined;
	const mark = setting === undefined ? undefined : managed[setting];
	if (mark === undefined) return text(error.message);
	return text(
		`${error.message}. The setting ${setting} is managed by ${mark.orgName}` +
			(mark.lock === "locked" ? " and locked" : "") +
			`. Do not retry or look for another way; tell the user to ask ${mark.orgName}'s admin.`,
	);
}

function text(message: string): ToolExecutionResult {
	return { output: [{ type: "text", text: message }], isError: true };
}

The last sentence matters. Without it, a model told "refused" tries the next way: edit a config file, write a plugin, run a command. With it, the model stops and tells Dana.

// The connections: one MCP client per effective server, reconciled whenever the effective `mcp.servers` changes.

import { forbidden, PluginError, type Reference } from "@earendil-works/chord";
import { BACKGROUND_CONTEXT } from "@earendil-works/chord/context";
import { McpClient, StreamableHttpTransport, type Tool } from "@earendil-works/pi-mcp";
import { defineFacet, type P3Principal } from "@p3/app/v1";
import { RadiusAuth } from "@p3/radius/contract";
import { SettingKinds, setting } from "@p3/app/v1/settings";
import { McpConnections, type McpServerConfig, McpServers, McpToolsView } from "./contract.ts";

type Live =
	| { readonly kind: "connected"; readonly config: McpServerConfig; readonly client: McpClient; readonly tools: readonly Tool[] }
	| { readonly kind: "failed"; readonly config: McpServerConfig; readonly error: string };

export default defineFacet<P3Principal>((host, facet) => {
	facet.contribute(SettingKinds, [McpServers]);

	host.serve(McpConnections, (_params, self) => {
		const servers = setting(self, McpServers);              // Acme's entries, plus Dana's unless locked
		const radius = self.get(RadiusAuth, {});
		const pool = self.open(
			async () => new Map<string, Live>(),
			async (live) => { for (const each of live.values()) if (each.kind === "connected") await each.client.close(); },
		);
		const snapshot = self.writable<ReadonlyMap<string, Live>>(new Map());

		// The same routine serves Dana's edits, Acme's updates and the first start.
		self.on(servers, async ({ value: wanted }) => {
			const live = pool.value;
			for (const [name, each] of live) {
				if (JSON.stringify(wanted[name]) === JSON.stringify(each.config)) continue;
				live.delete(name);
				// Removed or changed: calls in flight fail with McpConnectionClosedError.
				if (each.kind === "connected") await each.client.close();
			}
			for (const [name, config] of Object.entries(wanted)) {
				if (!live.has(name)) live.set(name, await connect(config, radius));
			}
			snapshot.set(new Map(live));
		});

		return {
			status: self.derive([snapshot], ([live]) =>
				Object.fromEntries([...live].map(([name, each]) => [name, each.kind === "connected" ? { state: "connected" } : { state: "failed", error: each.error }])),
			),
			tools: self.derive([snapshot], ([live]) =>
				[...live].flatMap(([server, each]) =>
					each.kind === "connected"
						? each.tools.map((tool) => ({ server, name: tool.name, description: tool.description ?? "", inputSchema: tool.inputSchema }))
						: [],
				),
			),
			call: async ({ server, tool, args }, ctx) => {
				const each = pool.value.get(server);
				if (each?.kind !== "connected") throw new PluginError("mcp_unavailable", `MCP server ${server} is not connected`);
				// Cast: MCP arguments are a JSON object; the tool's input schema was checked by the harness.
				return each.client.callTool(tool, args as Record<string, unknown>, { signal: ctx.abortSignal });
			},
		};
	});

	host.serve(McpToolsView, (_params, principal, self) => {
		if (principal.kind !== "worker" && principal.kind !== "user") throw forbidden("MCP tools are for the owner's sessions");
		const connections = self.get(McpConnections, {});
		return { variant: "main", members: { tools: connections.tools, call: (args, ctx) => connections.call(args, ctx) } };
	});
});

/** A connected client, or the reason it is not; never throws, so one bad server does not stop the others. */
async function connect(config: McpServerConfig, radius: Reference<typeof RadiusAuth>): Promise<Live> {
	const client = new McpClient({ name: "p3", version: "1" });
	const auth = config.auth;
	try {
		await client.connect(
			new StreamableHttpTransport({
				url: config.url,
				// Host lifetime: the provider is asked before every request, long after this routine call ended.
				authProvider: auth === null ? undefined : { token: () => tokenFor(auth, radius, BACKGROUND_CONTEXT) },
			}),
		);
		return { kind: "connected", config, client, tools: await client.listTools() };
	} catch (error) {
		return { kind: "failed", config, error: error instanceof Error ? error.message : String(error) };
	}
}

RadiusAuth and RadiusOrg are the Radius plugin's server objects (PROPOSED: tokens for Radius connections, membership, shares). tokenFor asks the Radius plugin (RadiusAuth.token({ connection: "jira" })) for a short-lived token, or the secrets store for a named secret. The Jira token never enters the profile, the settings or the MCP plugin's state.

// Shares: refused by the audience setting before Radius is asked; ended when the setting tightens.

import { arr, defineState, forbidden, obj } from "@earendil-works/chord";
import { defineFacet, type P3Principal } from "@p3/app/v1";
import { RadiusOrg } from "@p3/radius/contract";
import { refusedBy, SettingKinds, setting } from "@p3/app/v1/settings";
import { Share, Shares, Sharing, SharingAudience } from "./contract.ts";

const ShareList = defineState("p3.shares.list", {
	schema: obj({ shares: arr(Share) }),
	version: 1,
	initial: () => ({ shares: [] }),
	persist: true,
	checkpointWhen: () => true,
});

export default defineFacet<P3Principal>((host, facet) => {
	facet.contribute(SettingKinds, [SharingAudience]);

	host.serve(Shares, (_params, self) => {
		const audience = setting(self, SharingAudience);
		const radius = self.get(RadiusOrg, {});
		const list = self.state(ShareList);

		// A tightened audience ends every share that no longer conforms, here and at Radius.
		self.on(audience, async ({ value }, ctx) => {
			for (const share of list.value.shares) {
				if (value === "anyone") break;
				if (value === "org" && (await radius.isMember({ email: share.invitee }, ctx))) continue;
				await radius.revokeShare(share.id, ctx);
				await list.change((draft) => {
					draft.shares = draft.shares.filter((each) => each.id !== share.id);
				}, ctx);
			}
		});

		return {
			shares: self.derive([list], ([doc]) => doc.shares),
			share: async (request, ctx) => {
				const now = audience.value;
				if (now === "nobody") throw refusedBy(SharingAudience, "Sessions on this Pi cannot be shared");
				if (now === "org" && !(await radius.isMember({ email: request.invitee }, ctx)))
					throw refusedBy(SharingAudience, `${request.invitee} is not a member of the org; sessions can be shared with members only`);
				// Radius checks again from the profile it signed: a modified Pi gets the same answer.
				const share = await radius.share(request, ctx);
				await list.change((draft) => {
					draft.shares.push(share);
				}, ctx);
				return share;
			},
			revoke: async (id, ctx) => {
				await radius.revokeShare(id, ctx);
				await list.change((draft) => {
					draft.shares = draft.shares.filter((each) => each.id !== id);
				}, ctx);
			},
		};
	});

	host.serve(Sharing, (_params, principal, self) => {
		if (principal.kind !== "user") throw forbidden("Only the owner shares sessions");
		const shares = self.get(Shares, {});
		return {
			variant: "owner",
			members: {
				shares: shares.shares,
				share: (request, ctx) => shares.share(request, ctx),
				revoke: (id, ctx) => shares.revoke(id, ctx),
			},
		};
	});
});

async function createShare(request: Request): Promise<Response> {
	const pi = await authenticatePi(request);                 // a short-lived token minted against the device key
	const profile = await profiles.current(pi.org, pi.member, pi.id);
	const audience = profile.settings["p3.sharing.audience"]?.value ?? "anyone";
	const { session, invitee, mode } = await request.json();

  2. toolError turns it into: "Plugins written on this Pi do not load. The setting p3.plugins.own is managed by Acme and locked. Do not retry or look for another way; tell the user to ask Acme's admin."
  3. Without the lock-down, a determined agent could still write the files with its own file tools into the member root and call plugin_apply. Apply runs, the plugin is discovered, admits returns false, and the apply tool's result lists weather: left out: plugins written on this Pi do not load (managed by Acme). With the lock-down, the write itself fails: the member root belongs to the Pi's service user, and the agent's shell runs as Dana.

(vi) Dana shares a session with an outside email

Dana opens the share sheet of a session and types sam@partner.example.

  1. Sharing.share → Shares.share. audience.value is "org". radius.isMember({ email: "sam@partner.example" }) answers false. The method throws refusedBy(SharingAudience, "sam@partner.example is not a member of the org; sessions can be shared with members only"), and the sheet shows it with "Managed by Acme".
  2. A modified Pi that skips that check reaches Radius's createShare. Radius loads the profile it signed for pi_7f3a, finds "org", asks its own membership table and answers 403 outside_org. No grant, no link, no relay.
  3. A grant made before the lock (when the audience was "anyone") is ended by the self.on(audience, …) routine: radius.revokeShare for every invitee who is not a member. Radius also ends such grants itself when the profile changes, so a Pi that is offline at that moment does not keep them alive.

(vii) Acme removes Linear, live

Acme's admin deletes the Linear row and saves. Radius signs revision 43.

  1. OrgClient receives it over the follow connection, checks the signature, member, pi and the plugin sources, and offers it. OrgGate's routine writes the cache (settings first) and calls plugins.reconcile (nothing to install) and plugins.apply.
  2. gate changes, so Settings.effective changes: mcp.servers is now { jira }.
  3. McpConnections's routine runs with { jira }. linear is live but no longer wanted: removed from the pool, its client closed. A Linear call in flight at that moment rejects with McpConnectionClosedError; its tool result is an error the model sees ("MCP server linear: connection closed").
  4. snapshot.set → tools loses Linear's tools → every running session's McpAgent routine sets its tools → the harness's next model request in each session no longer offers mcp__linear__*. No session restarts; nothing else reconnects.

(viii) Acme locks its own plugin's setting

acme-deploy declares deploy.targets and reads it with setting(self, DeployTargets). Its authors wrote the settings page form for it, as for any setting; they never mention orgs.

  1. Acme's admin opens "Other settings" in Radius. The setting is listed because Dana's Pi reported the SettingKinds of its loaded plugins at its last sync, with the schema map(DeployTarget). Radius renders the form from the schema; the admin adds staging and production and picks "locked".
  2. The profile carries "deploy.targets": { "lock": "locked", "value": { … } }. On Dana's Pi, effectiveOf returns exactly those two targets; Deployer.targets (a derive of the effective value) shows them; deploy({ target: "my-box" }) fails with "No deploy target my-box" from the plugin's own check.
  3. Dana's attempt to add my-box on the settings page, or her agent's through a settings tool, ends in Settings.set with "Managed by Acme: deploy.targets is locked".

The plugin did one thing: it kept its configuration as a setting. That is the whole contract between plugin authors and orgs. A plugin that keeps its targets in a private file instead would escape the lock; Acme's answer is not to admit it.

V

Guardrails and Walls

Who this stops, who it does not, and what Radius enforces whatever the Pi does.

Every check in the Pi runs in the Pi's process, as the Pi's Unix user. That decides what it can stop. The design is honest about it: in the Pi, managed settings are a guardrail; where Radius sits in the path, they are a wall.

Three adversaries

Dana's agent is the main target: prompt injection or plain sloppiness. Its ordinary means are the settings tool, the plugin tools, the share tool and file edits. Settings.set refuses locked settings. The base's install path refuses plugins outside the profile, and admit keeps unapproved code from loading. The enrollment file is root-owned. An edited cache fails its signature, and the gate falls back to pending. All of these hold. What does not hold, on a Pi that runs as Dana's own user, is bash under the Pi's Unix user: it can start a modified copy of the Pi on the same data directory, with Dana's token, ignoring the gate. On a personal Pi that is the decided trust line ("The agent writes plugins": the boundary is access to the server). On an Org Device chapter VI moves it: the Pi runs as a user of its own and the agent's shell runs as Dana, so the shell cannot reach the Pi's files.

A third-party plugin is server code in the Pi's process. It can do anything the process can. Admitting it is the trust decision, and the only control is p3.plugins. A plugin that keeps its configuration through settings is covered without knowing it.

Dana herself. On her own laptop she is not an adversary: enrollment is compliance, and she could simply not enroll. On an Org Device she is held as far as her agent is. Anything that must hold against a determined member is enforced at Radius.

On an Org Device, the Device's setup may pre-install Acme's plugins into a root-owned directory such as /opt/p3/org-plugins and give it as the org root. Revocation while offline

Radius-enforced parts end the moment Acme removes Dana: guest links, peer links and org models stop at Radius. The Pi-side settings follow only when the Pi reconnects and receives revoked. A Pi that stays offline keeps its cached profile, and an offline Pi can be given an older signed profile it was once sent. Acme bounds both with maxOffline, at the price of a Pi that locks itself after that long without the server.

VI

Locking Down the Machine

How a managed Pi holds against a member or an agent with a shell: a signed install, a service user, tools that run as the member, execution control, and a key Radius checks.

Chapter V ends at one line: bash under the Pi's Unix user defeats every check in the Pi. On a personal Pi that line is fine, it is the decided trust boundary. On an Org Device it is the first thing a curious agent finds. Dana's agent runs bash as the user the Pi runs as, so it can edit the profile cache, read the Radius token, write into the org root, or start a patched copy of the Pi on the same data directory with Dana's token.

The fix is not more checks inside the Pi. It is to move the Pi out of reach of the shell: the Pi runs as a user of its own, from files nobody else can write, and the agent's tools run as Dana, who owns none of the Pi's files. Five pieces do that. Each stops some adversaries and not others; the table at the end says which.

(a) One signed executable in a system location

The Pi is installed by the machine's admin (on a laptop: the MDM, the tool an IT department uses to push software and settings to company machines) into a directory only an administrator can write: /opt/p3 on Linux, /Library/Application Support/p3 or /usr/local/p3 on macOS, C:\Program Files\p3 on Windows. Dana and her agent can read and run it, not change it.

What pi has today. The coding agent already ships standalone binaries:

  • packages/coding-agent's build:binary script and scripts/build-binaries.sh compile dist/bun/cli.js with Bun's --compile into one executable per platform (darwin arm64 and x64, linux x64 and arm64, windows x64 and arm64), embedding two worker entry points (the image resize worker and the code mode worker).
  • The executable is not alone: the release archives carry assets next to it (themes, the export template and its vendor scripts, the photon wasm file, docs), and src/config.ts finds them relative to the executable when isBunBinary is set (getPackageDir, getThemesDir, getExportTemplateDir).
  • There is also an esbuild-bundled Node distribution (dist/bundle/cli.js, detected by isBundledNode).
  • Nothing is signed. .github/workflows/build-binaries.yml builds and uploads the archives; there is no code signing, notarization or Authenticode step.

What p3 needs is different. p3's server is a Chord app, and the kit depends on Node in ways the coding agent does not: the store uses node:sqlite; session workers are separate Node processes started with child_process.fork and advanced serialization (packages/chord/src/node/workers/process.ts); plugin builds call esbuild, which is a native executable of its own (packages/chord/src/node/plugins/build.ts); installs run git, tar and npm (packages/chord/src/node/plugins/install.ts). So p3's executable is a Node single executable application (Node's own mechanism: one Node binary with the bundled server injected into it), and it does not travel alone either:

File in /opt/p3/bin Why it is separate Signed
p3 Node with the bundled server, the worker entry and the TUI; started as p3 serve, p3 worker, p3 (TUI) yes
esbuild plugin builds; found through ESBUILD_BINARY_PATH yes
pi-env the tool daemon of packages/env (Rust), started as the member, (c) below yes
p3-devkey the device key helper, (e) below yes, with the platform's key access entitlement on macOS

Three kit changes follow, all for laptops later rather than Dec 18: the worker fork must start the same executable in worker mode (fork runs process.execPath, which is p3 itself, so its entry point dispatches on its arguments, and the worker kind's Node flags are fixed at build time); installs of org plugins must not need npm and git on the machine, so Radius (or Acme's CI) builds each approved plugin into a complete tree with its node_modules, hashed as a whole, and the kit installs that tarball; and esbuild's path comes from the install directory, never from the data directory, where the service user could replace it.

On macOS the four files are signed with a Developer ID and the package is notarized; on Windows they carry Authenticode signatures. Signing is what lets (d) tell this Pi from a patched copy.

(b) The Pi runs as a service under its own user

Each member's Pi is a system service with a Unix user (a Windows service account) of its own, created by the root setup when Dana's Pi is created:

The profile cache, the Radius token and both plugin roots now belong to p3-dana. Dana's user cannot read or write them, and neither can anything running as Dana: her shell, her editor, her agent's tools.

How Dana's clients sign in. The kit already has the pieces: device sign-ins, the owner token file (a device sign-in of the owner, mode 0600, ownerTokenFile in packages/chord/src/node/app/owner.ts), and one-time owner links for the browser. Only where the token lives changes:

  • When the root setup creates the Pi, it writes ~dana/.p3/pi.json, owner dana, mode 0600: { "url": "http://127.0.0.1:47123", "token": "<a device sign-in of the owner>" }. Other members on the same Org Device cannot read it. On Windows the file is under %LOCALAPPDATA%\p3 with an ACL for Dana only.
  • The TUI (p3, run by Dana) reads the file and opens its Chord link with the token as a bearer credential, as command-line clients use the owner token file today.
  • The browser on the same machine: p3 open reads the same file, asks the Pi for a fresh one-time owner link (POST /_chord/owner-link with the bearer token; the base route calls the kit's existing App.ownerLink() through the platform binding), and opens it. The page posts the one-time token from the URL fragment and gets the owner cookie, as the kit's owner link works today.
  • The browser anywhere else (an Org Device in the cloud, Dana's phone): through the Radius relay. Dana signs in with Radius; the Radius plugin's authenticator, contributed to the kit's Authenticators registry, maps her Radius identity to the owner.

A unix socket checked by peer credentials would avoid the token file, but Node has no API to read a socket peer's credentials (SO_PEERCRED, LOCAL_PEERCRED), and the kit listens on TCP only (ListenAddress is a host and a port). The token file gives the same guarantee through the file system: only Dana can read it. Her agent can read it too, and that is fine: it then talks to the Pi as the owner, and the owner is held by the locks.

(c) The agent's tools run as Dana

A Pi running as p3-dana that runs bash in its own process would hand p3-dana's rights to the agent, and the service user would protect nothing. So the session's tools never run as the service user. Every session's execution environment is the pi-env daemon from packages/env, started as Dana:

// PROPOSED · apps/p3/plugins/environments/server.ts: the member's environment of a service-run Pi.
// pi-env API as on origin/main: Connection (a command speaking the daemon's protocol on stdin/stdout), RemoteExecutionEnv.
import { Connection, RemoteExecutionEnv } from "@earendil-works/pi-env";

/** The member's machine environment: the daemon started as the member through the one rule the setup wrote. */
export function memberEnvironment(member: string, cwd: string): RemoteExecutionEnv {
	const connection = new Connection({ command: ["/usr/bin/sudo", "-n", "-u", member, "/opt/p3/bin/pi-env"] });
	return new RemoteExecutionEnv({ connection, id: `pi-env:member:${member}`, cwd });
}
# PROPOSED · /etc/sudoers.d/p3-dana, written by the root setup when Dana's Pi is created.
# p3-dana may start exactly one program as dana, with no arguments ("" forbids any).
p3-dana ALL=(dana) NOPASSWD: /opt/p3/bin/pi-env ""

bash, read, write and edit go through RemoteExecutionEnv as they do for an SSH machine today. Terminals use openTerminal and local MCP servers (the stdio kind) use openProcess on the same connection, so they run as Dana too. Dana's agent can do everything Dana can do on the machine, and nothing the Pi's user can.

How each platform starts a process as another user:

  • Linux: the sudoers rule above. sudo is the privileged helper; the rule names one binary with no arguments.
  • macOS: the same rule works. A root launchd helper that starts pi-env for the console user is the alternative when an org disables sudo for service accounts.
  • Windows: a service account cannot start processes as a logged-in user without that user's token. So the direction turns around: a per-user launcher (a logon task in Dana's session) starts pi-env as Dana and connects it to the service over a named pipe whose ACL admits Dana only. Tools work only while Dana is logged in, and terminals are not supported by pi-env on Windows yet.

What it costs. One pi-env process per session environment (a small Rust daemon, a few MB, an estimate), started once per connection, not per command; sudo adds its start time to that first start only. Every file operation becomes a message on a pipe instead of a call in the process, which the coding agent's SSH environments already pay. And the setup grows: a Unix user and a sudoers file per member Pi.

What it does not fix. Plugins are Pi code: they run in the service as p3-dana, can read the token and could start pi-env as Dana themselves. The plugin list stays the control for them.

(d) Execution control

(a) to (c) protect the managed Pi. They do not stop Dana from running a different Pi: a patched copy of the binary, or pi from source, as her own user, with her own provider keys. Execution control is the MDM's job, not the Pi's:

  • macOS: an endpoint-security agent installed by the MDM, with an allow list by signing team; Dana is not an administrator. Gatekeeper alone checks only downloaded files.
  • Linux: fapolicyd with a trust database of approved binaries, or noexec mounts for home and temporary directories.
  • Windows: App Control for Business or AppLocker publisher rules, pushed by the MDM.

Execution control has a hard limit on developer machines: it stops a patched p3 binary, not a Pi run from source by an interpreter Dana needs for her work (node, python). That is why (e) matters more: a copy that runs gets nothing from Acme.

(e) A device-bound key

At enrollment the Pi asks p3-devkey to create a key that cannot leave the machine: in the Secure Enclave on macOS (P-256, the only curve it offers), in the TPM 2.0 on Linux and Windows (/dev/tpmrm0, the Windows Platform Crypto Provider; a cloud Org Device has a virtual TPM). The public half goes to Radius with the first sync and is in the profile as deviceKey. From then on Radius gives org resources only to a Pi that proves it holds the private half:

The org's resources at Radius (the model gateway with Acme's keys, the MCP credentials behind auth: radius, the sharing relay, peer links) all take only that short-lived token. Copying the data directory, or the Pi's long-lived Radius token, to another machine gives a Pi that cannot get one. The key handle is readable only by p3-dana (on Linux the TPM device is opened by the service, in the tss group; Dana is not).

For Dec 18 a simpler form is enough: a key file in the data directory, mode 0600, owner p3-dana. It stops Dana and her agent (they cannot read it) but not root, which could copy it; the TPM form stops the copy too.

What the Base Needs Now

What p3 must build before any org exists, and what waits for December 18.

The org machinery itself is small and late: an enrollment reader, a client, a gate page. What is expensive to add later is the shape it relies on: that every piece of configuration is a declared setting with one write path, and that every place that starts a session or loads a plugin asks one gate. With no org, all of it is one store and a constant.

Now, for December 1

  1. One settings mechanism. defineSetting, SettingKinds, the Settings store with set as the only write path, and setting(self, token) for readers. No plugin JSON files like p2's mcp.json and models.json: MCP servers, model providers, company or personal instructions and the plugin list are settings from the start.
  2. The managed error. set throws it for a locked setting; the page, the terminal and the agent's settings tool render it as "Managed by X", and the page draws locks from Settings.managed.
  3. Plugins only through the base. Installs, Apply and the plugin-writing tool are methods of one base object (Plugins, on top of the kit's PluginManager binding, base inventory #14), never a side effect of a file write; the member root is a separate root from the app's own.
  4. Base switches with permissive defaults: p3.sharing.audience ("anyone" | "org" | "nobody") and p3.peers.audience. The share and peer paths read them, and end shares and links that no longer conform when they change.
  5. A gate that is always unmanaged, already consulted by the worker kind's start and authorize and by Apply.
  6. Credentials by reference. Setting values name credentials (auth: { radius: "jira" }) and never contain them (base inventory #13).

  • OrgGate, OrgClient, the profile cache and the gate page ("Connect to Acme", the reason, sign-in).
  • The kit change: plugin roots and admit.

What It Cannot Do

The limits of managed settings, and the decisions still open.

Managed settings lock configuration. That covers what Acme asked for: provisioning, closed lists, audiences, approved plugins. It does not cover everything, and the limits are deliberate.

  • Rules over values. "MCP servers only on *.acme.com" or a token budget is not a lock. A plugin has to offer a setting for it (an allowed-hosts setting), and budgets belong at Radius.
  • Denying an action that is not configuration, such as exporting or deleting a session, unless the base or the plugin exposes a switch setting for it.
  • Different rights for different people in one Pi. There is one person per Pi; Radius picks the profile per member, and guests get what the session gives them.
  • A plugin's private config files. The answer is the plugin list.
  • A shell under the Pi's Unix user, root, or an admitted plugin. They are past the boundary.
  • Instant revocation while offline, and replays of an older signed profile, unless Acme sets maxOffline.
  • Running without the org server. A new enrolled Pi does nothing before its first sync, by design.
  • One Pi in two orgs. The enrollment file names one.

Decisions needed

  1. Who holds the org key. The admin in the browser (Radius cannot forge profiles; key loss and rotation are the org's problem), or Radius per org (simpler; a compromised Radius can push code). Recommended: Radius for December 18, with the key id in the profile so an admin-held key can replace it later.
  2. maxOffline default. None (offline work always continues) or a default such as 30 days for Org Devices.
  3. Instructions as entries. prompt.instructions is drawn here as an entries setting so Acme's text and Dana's sit side by side. The harness's prompt design may want a different owner for it.
  4. What revoked does to data on an Org Device. Keep it (as here), export it to the org, or delete it.
  5. Lock-down on laptops. A per-member system service (chapter VI) protects the Pi's files from the member's shell, but costs a service user, a helper to start tools as the member, and on Windows a logon launcher. The alternative is a Pi under the member's own user with Radius-side enforcement only. Recommended: the service on Org Devices from Dec 18; decide for laptops once an org asks for MDM deployment.
