# Pi Roam base inventory — parity and coverage

Status: completed source-backed inventory; proposed Pi contracts are explicitly marked NEEDED, not claimed as implemented.

Scope: all 39 p2 plugins; the old coding-agent extension API as a capability catalogue, not a compatibility target; concrete products beyond parity. The instance is the trust boundary. The earlier resource/ACL design is one possible plugin, not the mandatory base.

Evidence categories used below: **EXISTS-CHORD/DURABLE/P2** identifies a source mechanism, not an implemented Pi Roam service. **NEEDED-BASE** is a missing stable seam. **PLUGIN** is product logic built on those seams, not something to add to base.

## 1. Conclusion before the inventory

The base should expose **mechanisms for composition, execution, observation and lifecycle**, not mandate Home, projects, resources, an ACL, a transcript layout, or a workflow engine. Even the providers of core Pi registries and the harness should be reloadable required-root plugins; the non-reloadable base is the versioned contract package and bootstrap integration. This already matches `packages/chord/src/node/app/README.md`, “Base code”.

The six harness parts are necessary but insufficient alone. Rebuilding the old extension ecosystem also requires: universal ingress and non-tool execution interception; provider transport instrumentation; actionable turn/final-answer boundaries; observable entries/documents/commits with replay; session lifecycle and catalog operations; arbitrary client presentation/editor/commands; and whole-instance data/secret/backup access through a deliberate API. Merely exporting Durable's `Extension` would miss several of these and violate the harness direction.

**Change from the previous resource review:** the resource model is a possible policy plugin built using these seams. Do not install its `ResourceKinds`, `Policies`, one-list admission, per-resource ownership or company directory model as unavoidable base policy. Preserve authenticated identities and typed boundaries so such a plugin can implement them, but do not reintroduce per-run authority or login modes as a default.

## 3. Filter / chain / wrap for every harness part

### Common contribution discipline

One registry **per part**, not one per verb and not one monolithic Durable Extension. A part's contribution is an array of discriminated entries, conceptually `offer(...) | filter(...) | chain(...) | wrap(...)`; use part-specific typed helpers, never `register("hooks", unknown)`. A host-lifetime object may contribute one watchable array per registry, which permits dynamic providers/tools without imperative lifetime bookkeeping. The defining plugin composes deterministically and preserves contributor identity (D §17). Conflicts and broken contributors are reported; removing a provider actually removes its offerings.

Selection values use typed tool/section/task tokens in code and declaration identities at persisted/wire boundaries. No raw JavaScript token equality across separately bundled/reloaded plugins. No numeric magic-priority strings. Each composition defines semantic stages and tie-breaking; a phase uses a pinned executable snapshot, while a **separate live admission check** can implement resource withdrawal. “Not offered to the model” is not “cannot be called by another tool”.

**Do not manufacture missing Durable hooks.** `afterTools` runs after a tool round, `onYield` can continue a final answer, and `afterRun` may create child tasks after answer settlement. They are not interchangeable with the old `turn_end`, mutable `message_end`, `agent_before_settle`, or final-idle event. Expose Pi contracts with precise guarantees and bridge each explicitly; extend Durable only for a genuinely missing transaction/boundary, not for product names.

**There is no “exactly once external side effect” hook.** Safe tools/tasks replay; unsafe calls interrupt. Approval decisions may be memoized for an exact call/arguments, but cannot authorize newly rewritten arguments. Durable task ownership/cancellation must propagate through nested tools and child conversations. Observer callbacks must record synchronously and do their I/O later; `observeCommits` is not a place to send email.

## 7. Concrete constructions and semantic traps

### A. Automations without an always-open worker

**Problem:** `self.routine(async ctx => sleep(...))` only runs while its owner lives; a worker's registry/task definition is not a server alarm. Example: a reminder sleeps until tomorrow, the last UI closes, and no process is there tomorrow to fire the callback.

**Construction:** Tasks offers a versioned checkpointed definition; the task records its next wake in the harness; worker observes `H.wake` and publishes a revisioned summary to a server owner. The server owner persists next-due/session/ack state and drives a Chord job that holds SessionControl when due. Holding starts the worker; keep it until the worker accepts/resumes due work and publishes an updated wake. On app restart, scan persisted due rows before waiting for the next future deadline. Use current incarnation/revision fences to reject stale “idle”/“wake tomorrow” messages from an older worker.

**NEEDED:** the Pi worker-to-server wake adapter and coherent publication/start acknowledgement. Existing kit worker acquisition, Chord jobs, public Http and Durable tasks need no second general scheduler. If the entire computer is off, only an external service/OS alarm can wake it; Radius/cloud provisioning can supply that optional service.

### B. A server session factory any plugin can call

**Problem:** putting create only inside a session-list UI forces Discord, automations and domain apps to import its internals. Copying a live worker DB directly from the server also violates single-writer ownership.

**Proposed typed service:** `Sessions.create(plan, ctx) → Operation<SessionRef>`, `configure(session, patch, ctx)`, `archive(session, ctx)`, `restore(session, ctx)`, `relocate(session, placement, ctx)`, `fork(session, source, ctx)`, `delete(session, ctx)` and bounded `query(...)`/observable summaries. `Operation<T>` is a tagged `{kind:"pending", id} | {kind:"done", value:T} | {kind:"refused", reason} | {kind:"failed", error}` state, not “RPC returned, therefore durable effect completed”. `SessionRef`, `Placement`, seed/config patches and fork source have declared schemas; no callback or raw filesystem path crosses the wire.

Creation has a **preparing → ready** boundary: template/plugin metadata/config are durably installed before first input or ordinary resume. Cross-owner initialization uses acknowledged idempotent steps, not an imaginary transaction spanning server/worker stores. Server facts (existence/archive/location/deletion) belong to the server; stopped-worker desired config gets a revision/ack protocol; worker publishes only worker-owned title/content/status fields. A worker that restarts must not overwrite newer server config with a stale full-row mirror. This is the rule p2's plugin-practices document already enforces.

A template is a plugin that prepares a plan and its own referenced metadata, not an obligatory base template catalog. A domain app can attach its own typed object keyed by SessionRef. Branch/main selection, clone content policy and initialization are public worker operations; final session navigation remains a particular client's action.

### C. Statistics without private-field access

**Problem:** entries alone show what was committed, not every transient request transform or rejected external action. Example: a RAG hook inserts 50 KB for one request; the transcript never contains it, so a context dashboard cannot reconstruct that request afterward.

**Construction:** an observer uses public harness entry/document projections and commit sequence; a Models/request wrapper captures the **effective** assembled request after context/section transforms and the selected declaration snapshot. Persist compact per-request records keyed by session/conversation/run/task/request attempt; attach provider usage, actual route, timestamp and elapsed spans. Store optional large content snapshots in Files; aggregate in a server-owned bounded/cursor-fed index. Tool observations include parent IDs; Env/PTY owners expose real file/command effects and domain plugins can expose skill/provenance facts. Watching a view may coalesce commits; durable catch-up uses a cursor or retained history, not token-event counting.

Do not inspect another plugin's private documents. Owners expose typed facts/views they want observed. Actual billing totals and category estimates are separate, child usage must not be counted twice, and “tool reported a write” differs from “sandbox audit proves this path changed”. Include failed, aborted, cache-warm and direct non-generation model calls. Exact provider payload capture may reveal secrets and is opt-in/redacted; a general dashboard need not store every body forever.
Durable afterTool hooks can be skipped at restart/abort limits (`H:1060–1070`); complete statistics must catch up committed result/task records instead of relying on one callback per terminal outcome.


### D. Policy hooks versus a real confinement boundary

**Problem:** hidden tools are not blocked tools, and intercepted agent tools are not all paths to an environment. Example: deny `bash`, but a user opens a PTY or another tool calls Models directly or writes through workspace upload.

A policy package can be built without mandatory resource machinery **if** the selected providers participate in public seams:

| Path | Required intercept, not a cosmetic filter |
|---|---|
| Model-issued and nested/code tools | Tools selection plus live dispatch; canonical validated final args; transformed results in every output channel. |
| Agent generation, compaction, helper, warmer and tool direct model calls | Wrapped effective Models runtime, including deferred/image/classifier operations and usage. |
| Filesystem/bash/argv/watch/prompt resource reads | Wrapped Env factories and every relevant ExecutionEnv operation; no accidental raw-native escape in official tools. |
| `!`/`!!`, workspace git/upload/download, PTY/ports, file/voice/media sockets | Their typed owner-operation gate and byte-channel admission/revocation; Tools hook alone is irrelevant. |
| Human/integration/peer/task sends; passive writes and continue | Input/entry admission with trusted source attribution, destination policy and before-first-worker-start route check where needed. |
| Session create/configure/archive/restore/fork/move/delete | Session service operation middleware, pending-operation state and current checks at commit/effect. |
| Task creation and recovered work | Tasks definition/creation admission and explicit persisted-task handling; built-ins need an engine-level seam if universal control is promised. |
| Views/queries/files/public publication and later revocation | Per-principal provider variants/projections and current owner checks. List visibility is not authority; existing channels must be stopped separately. |

Approval must run after the **last** argument rewrite/schema normalization and authorize exactly those args. The Pi adapter can own this order because raw Durable extensions are private; do not assume arbitrary beforeTool registration order provides it. Durable `harness/tool.ts:157–196` currently validates, runs beforeTool, revalidates and records intent; any adapter approval stage must account for that normalization and replay placement.

No policy plugin can confine malicious same-process server plugins that import Node and read OS credentials. Neither Chord import checking nor “no tools offered” is a server-code sandbox. Under the current direction, installed instance plugins are trusted. Strong isolation requires OS/process/VM separation with narrowly mediated capabilities; that can be an optional runner/backend product, not policy expressed as prompt text.

**Actual scope limit:** Chord has HTTP wraps and provider-owned checks, not universal middleware for every plugin method/view/channel. Base-owned operations can expose typed wrappers; other plugins must expose equivalent seams or be replaced. If the requirement is transparent ACL enforcement over **arbitrary non-cooperating third-party contracts**, a Chord dispatcher/admission extension is NEEDED; this report does not claim it exists. It still cannot constrain arbitrary trusted Node code outside Chord.

### E. Radius code delivery, sharing and backup are three products

Remote access relays this instance's own UI; backup copies its durable data; anonymous sharing grants access/publishes a UI. They have different lifetimes, credentials, audiences and trust. Do not collapse them into “Radius integration”.

Cristina's proposal avoids Radius vouching for arbitrary instance-served plugin JavaScript: Radius builds the guest UI it will serve, with version/API checks and unknown-type fallbacks. The direction explicitly wants the instance's extensible UI relayed. These can coexist **only with an explicit split**: isolated instance origins for remote instance UI and an optional Radius-controlled restricted guest code set, or a deliberately trusted instance-served guest mode. Never silently serve arbitrary facets with Radius cookies or on an origin trusted for unrelated instances. Opening a public share is not implicit agreement to import/install that instance's plugins into the viewer's own Pi.

The default sharing warning in the direction is important: a person who can operate the shared session can reach the instance/environment's capabilities. A plugin may build tighter read-only/resource restrictions using §D, but the new base must not silently claim old p2 ACL safety by default. Radius cannot infer sandboxing from a session label.

### F. Backup/clone/delete need real lifecycle support

**Backup:** current kit `AppInstance.exportData(address,path,ctx)` exports one worker under its lock or through its running HostData facet (`app.ts:253–271`, `data.ts`). `packStore` pairs a consistent store point with finished Files. It does not by itself inventory all workers/server stores/config/plugins/secrets, provide a global logical checkpoint or transfer incremental outbox batches and their referenced blobs. Pin blobs for a snapshot until export/upload acknowledgement; a concurrent remove/GC must not produce a manifest whose referenced file is missing. Either expose snapshot/retention APIs or quiesce writers for an explicit full export. Cross-host consistency is a protocol or an honest per-host checkpoint manifest, not a distributed transaction implied by SQLite.

**Restore:** import into empty target under address lock, restore matching API/plugin/config manifests and dependencies before reopening workers, then choose how unfinished safe/unsafe work resumes. Preserve stable references when restoring the same instance, or remap them deliberately on import-as-copy. Secrets need encrypted backup/rekey/rotation and explicit credential consent. Local machine paths and unavailable SSH envs are unresolved dependencies, not an excuse to run locally.

**Fork/clone:** decide active-task/schedule/approval/reference/Files behavior before copying a store. In-progress unsafe external effects cannot simply resume twice under copied task IDs. A sensible default is content/config clone with activation paused and new session identity; domain plugins can explicitly initialize new schedules or reuse immutable blobs. Expose lifecycle participation so project/artifact/index/connector plugins can initialize or reconcile their associations.

**Delete:** commit catalog tombstone first to block routes and revival, close channels/revoke links, stop worker/jobs, then remove owned store/blob files and reconcile indexes/project mappings/ports/MCP leases. Retried cleanup is idempotent; absent owner plugins may leave retained namespaces recorded for later cleanup rather than making deletion impossible. Backup retention/published copies are separate policy. Archive and closing a client are not delete.

## 10. Minimal proposal: keep mechanisms, merge adapters, cut policy products

### A. What the non-reloadable base actually contains

1. **Versioned Pi contracts/types and bootstrap wiring** for host kinds, declared schema identities, worker placement/auth/routing, public API import exposure, and required-root provider validation. Reuse Chord/kit hosts, principals, owners, storage, registries, jobs, surfaces and Files; do not fork them into Pi equivalents.
2. **Narrow native runtime delegates where bootstrap/platform has exclusive access:** app/worker lifecycle, startup configuration/diagnostic buffering, store snapshot/import locks, and trusted client-launcher actions. Expose typed handles/services; product code must not import the launch script's closure. These are capabilities of the existing runtime, not a global business-action dispatcher.
3. **Any genuinely missing Durable transaction/phase boundary** required to implement public before-settlement/entry transforms and universal task admission. Keep the engine correctness rule below plugins; let plugins choose policies. Do not move Home/approvals/cost budgets into Durable.

Almost everything called “base service” elsewhere can be a **required-root reloadable provider plugin**, not frozen kernel code. Required means absence has a clear unavailable state or prevents dependent work from starting, not that it is privileged to invent resource/ACL policy. Removing a metrics plugin should not stop Pi; removing the Harness provider should stop starting new harness work safely.

### B. A small default provider stack

| Provider / shared API package | Responsibilities merged here | Explicitly not required product behavior |
|---|---|---|
| **Sessions + worker bridge** | F3 session catalog/service; server-owned state and lifecycle, wake-summary/ack bridge (F12), lifecycle export/delete hooks (F13). | Projects, Home, template UI, issue tracker, global company/team directory or forced shared-session ACL. |
| **Harness + six parts** | F2 Durable storage adapter, F4 part composition, F5 observation/control and F6 authoritative entry admission. Preserve their separate typed parts. | Built-in coding tools, fixed prompt files, mandatory model provider, MCP, chat-mode, mandatory per-run authority. |
| **Environments** | F4 provider registry/resolution, location/capability facts and selected operation path. Optional standard implementations packaged separately. | Fixed SSH-only/sandbox-only machine taxonomy, local fallback or bundled production credentials. |
| **Application runtime adapters** | F11 control/config/error/private-secret services, F14 plugin/app lifecycle, existing kit data/worker/Http surfaces. | Mandatory models.json schema, package marketplace policy, Radius account/service, organization IAM. |
| **Client presentation/interaction** | F9 roots/renderers/layouts and F10 command/editor/completion/flow/device APIs; browser and terminal adapters remain different hosts. | Mandatory transcript/sidebar, single Home screen, hardcoded tool renderer switch, old TUI class hierarchy imposed on web. |

This is packaging, **not five new generic registries**. The existing Chord services/registries already provide ownership, cancellation, reload and distribution. Domain plugins own their contracts/state and contribute directly to the public services they need.

### C. Cut or merge these proposed obligations

- **CUT compulsory resource/ACL/company/project machinery.** Build the earlier model as one policy plugin if desired; retain only the identity/config/selection/operation/view seams that let it work.
- **CUT monolithic public Durable Extension and singleton HarnessConfig/default provider.** Use six parts and an effective facade. Keep raw Extension private to the adapter.
- **CUT a stringly global action/event/permission DSL.** A `Questions`/`Search`/`MCP` plugin may define its own typed contract and registry. Need for one integration is not a reason for a kernel registry named “everything”.
- **MERGE duplicated submit routes** into one ingress contract, but keep passive writes, non-turn continues, direct shell operations and new model input as tagged different effects. Do not flatten all of them into user chat text.
- **MERGE config/error/process/worker/app access** into public narrow runtime delegates instead of one private closure per product. Do not hand every worker a raw AppInstance or all secret contents.
- **MERGE renderer, command and editor parity work** across surfaces through shared identities/data, not shared native UI callbacks. Factories remain page/terminal-local and disposable.
- **CUT fixed UI slot catalogs per product** (one required tab each for Projects/Issues/Stock/Memory). Open layout/form/route composition plus domain refs suffices; only real UI composition mechanisms need stable contracts.
- **CUT “proxy-marker” as a behavior plugin** if it remains empty. Keep verified relay provenance in transport.
- **CUT mandatory always-on full request payload logging.** Public hooks and opt-in bounded capture support dsh-context; server summaries/cursors support usage charts efficiently.
- **CUT promises of atomic whole-instance backup or live multi-master sync without their protocols.** Start with honest per-host snapshots + instance manifest + single writer. Stronger cross-host checkpoints/fenced handoff are optional, explicit additions.
- **CUT a second generic scheduler/queue/workflow engine.** Chord jobs/routines plus public Durable Tasks/wake/session APIs suffice; priorities, business workflows and calendar semantics are plugins.
- **CUT compatibility obligations to old JSONL paths, jiti loading, untyped string buses, mutation of event payloads, specific file names and old UI component classes.** Preserve capability, not accidents of API shape.

### D. What cannot be “just a normal plugin”, and why

- **Facts upstream code never exposes:** a plugin cannot reconstruct erased request transforms or run an exact atomic pre-settlement edit after settlement. Expose the fact/boundary from the owner/engine; the observer/editor itself stays plugin code.
- **Bootstrap-before-plugin decisions:** trust of executable code, initial auth/relay provenance, server data-dir locks, launcher secrets and OS actions must be established before less-trusted code can claim them. Later configuration/policy can be plugin-owned.
- **Capabilities held only by start/runtime closures:** build/apply, stop workers, process output and consistent store export need kit delegation. Exposing them makes admin/backup plugins possible; importing private process internals is not an API.
- **Actual isolation and external uptime:** a policy plugin cannot prevent trusted Node plugins from bypassing it or make a powered-off machine execute. OS/VM/remote services provide those boundaries; Pi exposes adapters.
- **External exactly-once effects:** local transaction/replay cannot atomically commit with GitHub, mail, a calendar or a different independent owner. Use service idempotency keys, durable outbox/receipts, explicit retry/unsafe-recovery and user confirmation where appropriate.
- **Client privileges not granted by the platform:** camera, microphone, native file writes and external editors need browser permissions/trusted launcher/native extension, not a worker callback. Base supplies the narrow bridge, product plugin supplies experience.

## 11. Open questions / decisions to settle before API freeze

1. **Policy scope:** only complete interception of Pi-owned public operations plus cooperative providers, or transparent gates over arbitrary Chord contracts/views/channels? The latter requires new Chord dispatcher support; it still does not sandbox trusted Node plugins.
2. **Task promise:** filter/wrap only offered plugin definitions, or also built-in generation/tool/compaction phases and recovered tasks? Define denied persisted work, abort/migration availability and current-policy checks before adding generic runtime hooks.
3. **Boundary parity:** retain old mutable same-role message_end and exact turn_end/agent_before_settle capabilities, or replace some with explicit entry/context edits? Decide the observable guarantee and add engine support only for the residual gap.
4. **Composition rules:** exact semantic order for command/expansion/attribution, request transforms, argument rewrites/schema normalization/approval and result redaction; provider replacement and mandatory-gate failures; pinned execution versus live revocation. These are API rules, not hidden registration order.
5. **Session initialization/clone:** which config/content/tasks/Files/domain associations are copied, when first resume is allowed, and how cross-owner metadata initialization is acknowledged. Is content clone with schedules paused the default?
6. **Idle/wake:** what counts as foreground/background/needs-human; who publishes/acks due work; which holds keep it alive; when a task's external wait is legitimate sleep rather than lost work. Avoid overloading busy/task count as semantic progress.
7. **Radius UI trust:** instance-origin remote UI only, Radius-controlled guest bundle, or both explicitly? Which plugin code/API versions are served to guests, how are unknown types rendered, and what is the origin/cookie/native-capability boundary?
8. **Backup scope:** minimum recovery promise for server/worker stores, Files/config/plugin code/secrets; snapshot/blob pinning; encrypted credential treatment; per-host versus coordinated checkpoint. Which low-level archive APIs will kit expose to an ordinary server plugin?
9. **Multi-device scope:** remote clients + backup, offline read-only replicas, or writer transfer? Do not accidentally promise multi-master conflicts/effect reconciliation from outbox replication.
10. **Client parity:** exact lowest common command/composer/renderer API, and which terminal-only actions get launcher support. How do multi-viewer prompts choose a respondent and unavailable-client actions fail?
11. **Observability/privacy:** which harness/document facts are public, request/attempt identity, usage ownership and retention limits; how domains expose provenance without private document reads. Full sensitive payload retention must be explicit.
12. **Required providers/reload:** compatibility and dependency order, behavior when required contribution disappears or schema migrates during work, and rollback boundaries for native/DB changes. Kit rollout does not magically undo external effects.
