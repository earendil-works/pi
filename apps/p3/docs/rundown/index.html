Before we begin

It is Friday, 13 November. The onsite is next week, and p3's design is spread over 22 decisions, five design books written between 7 and 13 November, three sketches from this morning, a views mockup from this morning and a proposal another session wrote an hour ago. There is no p3 code. p2 runs on the owner's phone every day and already has a working, single-user version of most of what the p3 documents argue about: guests, read-only sharing, a session lock, views, artifacts, a harness with filtered tools, code-mode namespaces.

The same questions keep coming back in every round: who owns a resource, who may bring it into a session, who checks that, and where the check runs. Each round a new document answers them a little differently, often with APIs that do not exist, and the older documents are never marked as superseded. That is what going in circles feels like.

This rundown does one thing: it sorts every piece into decided, built and proposed, shows real code for each, and names the contradictions. It also checks today's main proposal against the one Chord rule it breaks, "a factory is synchronous and only declares", and shows how each of its three mechanisms would have to be written with Chord as it is.

Ten things to know

  1. p3 has no code. Everything marked built lives in p2 (apps/p2), Chord (packages/chord) or Durable (packages/durable). p2 is single-owner with guests.
  2. The resource direction is decided in outline. Resources are owned by a user or by the instance (2026-11-13), you bring only your own, and everyone who may send in a session uses the session's whole list (2026-11-08). The mechanics are not decided.
  3. A factory decides only from params and the principal. Chord runs it synchronously; the values of what it declares arrive later. "There is no async activation guard" (design §7). Every other check runs in a method or shows as derived state.
  4. That is why p2 puts a guest's rights in the principal. GuestPrincipal.sessions maps each shared session to "view" or "full", so a factory can choose the viewer or editor variant on the spot; any change bumps a revision and ends the old objects. p3's decided user principal carries only an id, so this trick does not carry over.
  5. Today's "three edges" proposal needs Chord hooks that do not exist. scope: "user" on tables, ctx.scope, a policy gate inside Chord's dispatch, and a list check before the factory runs. It also contradicts Chord's ownership principle ("the owner enforces its rules in its methods"). Each edge can be built from today's Chord as a small library pattern; chapter VI shows all three.
  6. Two policy shapes are on the table. The resource-model book's policy is a synchronous decide(request, baseline); this morning's gate sketch is async decide(...). Derives (a session's list, "what may I create") can only use the synchronous one.
  7. p2's session lock is the single-user version of "resources on sessions". The owner picks MCP servers, instructions and two capabilities; the worker mirrors the lock into Durable; tools and server objects check it at every call.
  8. The UI is decided at the level of plugins and items. Views are plugins, a plugin owns its items' data, panes come from ViewKinds, listable items from ArtifactKinds (2026-11-12). Layouts as apps, placements, the "+", and several sessions in one layout are proposals.
  9. The worker is built in p2 and mostly settled. One process per session, the Durable harness, extensions from a registry, a guard on every tool, code-mode namespaces declared by extensions (Durable, 2026-11-12). Extensions keyed by resource exist only on paper.
  10. About ten rules would settle most of it. They are on the last page, followed by the owner's open decisions in the order they unblock the most.

Words used throughout

BUILT, DECIDED and PROPOSED label every code block (see the cover note). A principal is who a call is from, stamped by the link it arrives on ({ kind: "user", id }). A factory is the function that makes a Chord object; it runs synchronously and only declares. A per-principal object is a Chord remote object: one per params and principal, choosing one variant (a set of members) when it is made. A store is a local object with empty params: one per host, it may persist data and contribute to registries. A registry collects contributions from plugins and composes one value. A resource is something a session can use (an MCP server, a tool, a model provider); its owner is a user or the instance. Bringing puts a resource on a session's list. The policy answers "may this user do this". A lock is p2's per-session pick of resources. A view is a pane on screen showing an item (an artifact, a file, a terminal) of a view kind; a layout arranges views; a placement is one view in a layout. A worker is the process running one session; its harness is pi-durable's Harness; an extension is a Durable bundle of tools and prompt sections; a namespace groups an extension's tools for code mode.

I

The Rule Under Everything

Part 1 starts with Chord, because every question about users, resources and locks ends at the same rule: what a factory may know when it runs.

Every access question in p3 becomes, in code, one of three questions: may this caller get this object at all, which variant does it get, and may it make this call now. Chord answers the first two in one place, the factory, and the factory runs under a hard rule.

The rule

Design §1, principle 3: "Factories declare, Chord activates. A factory is synchronous and only declares; Chord performs activation. Handles a factory gets are valid for the object's whole life." Design §6 adds: "Synchronous and declarative: no awaits, no side effects; async work happens in activation (opens), in calls, in routines and jobs."

The types say the same:

// BUILT · packages/chord/src/host/attempt.ts (excerpt)
export type Factory<C extends Contract, P extends Principal = Principal> = ShapeOf<C>["kind"] extends "local"
	? (params: ParamsOf<C>, self: keyof ParamsOf<C> extends never ? StoreSelf<P> : Self<P>) => Implementation<C, Ctx<P>>
	: (params: ParamsOf<C>, principal: P, self: Self<P>) => Implementation<C, Ctx<P>>;

Three consequences matter for everything that follows:

  1. A factory can decide only from its params and its principal. It may declare self.get(Other, {}), but the reference becomes live after the factory returned. It cannot read another object's state, a table or the policy while it runs. So it cannot refuse a caller or pick a variant because of data stored somewhere.
  2. Only stores and facets touch tables and registries. self.table, self.query and self.contribute exist only on StoreSelf, the self of a local type with empty params (one per host). A per-principal object cannot own a table and cannot contribute to a registry (design §17, R21).
  3. Params are flat. A record of str(), int(), bool() or oneOf(...) fields, nothing nested (design §5). A resource reference { kind, owner, id } cannot be one param.

Design §7 states where checks therefore live: "Authority checks live in the per-principal view's methods (and in route.authorize before a host starts); there is no async activation guard." route.authorize is synchronous too: authorize(principal, address): boolean.

// BUILT · apps/p2/src/hosts/session-workers.ts (excerpt): the route to session workers

Where Runs Can read Example

And where the answer depends on data that changes (is the session locked, is it shared), p2 declares the stores in the factory and checks their followed state inside each method:

// BUILT · apps/p2/plugins/telemetry/server.ts (excerpt)
host.serve(Traces, (_params, principal, self) => {
	// …
	if (isOwner(principal)) return { variant: "owner", members: reads(store, async () => {}) };
	if (isWorker(principal)) {
		const { session } = principal;
		const shares = self.get(Shares, {});
		const locks = self.get(SessionLocks, {});
		// What the agent finds lands in the transcript: anyone the session is shared with (viewers too) would read it.
		const check = async (_ctx: Ctx) => {
			if (locks.locks.value[session] !== undefined)
				throw forbidden("Telemetry is the owner's: this session is locked.");
			const shared =
				shares.links.value.some((link) => link.session === session) ||
				shares.people.value.some((person) => person.session === session);
			if (shared) throw forbidden("Telemetry is the owner's: this session is shared.");
		};
		return { variant: "agent", members: reads(store, check) };
	}
	throw forbidden("Telemetry is the owner's.");
});

These two shapes, "decide from the principal in the factory" and "declare in the factory, check followed state per call", are the only two Chord offers. Every mechanism in this rundown has to be one of them.

II

Users

Who a person is in p3: what is decided, what the kit and p2 have, and three generations of proposals.

Decided

  • Principals are server, worker, user, guest (decisions.md, 2026-11-06). The guest is reserved until sharing is designed. The owner is the first user; the kit's owner link signs in as that user (Chord decision "The kit's owner is a principal the app chooses").
// DECIDED · decisions.md "Principals are server, worker, user, guest" (2026-11-06), written as a type
type P3Principal =
	| { readonly kind: "server" }
	| { readonly kind: "worker"; readonly session: string }
	| { readonly kind: "user"; readonly id: string }
	| { readonly kind: "guest" };              // reserved until sharing is designed
  • Instance resources, not an instance user (decisions.md, 2026-11-13, refines "Resource model direction"): a resource's owner is a user or the instance. No pretend user appears in lists, presence or audit.
// DECIDED · decisions.md "Instance resources, not an instance user" (2026-11-13), written as a type
type ResourceOwner = { readonly kind: "user"; readonly user: string } | { readonly kind: "instance" };

Built

Chord's app kit has the pieces p3 is meant to start from: defineUsers(profile) (profiles by id, packages/chord/src/node/app/users.ts), Sessions (sign-in sessions), owner links and device pairing, and a fixed principal.owner in its options (app.ts: principal: { server: P; worker?: …; owner: P }).

p2 has one owner and guests. The owner's principal says how they reached the server; a guest's carries every session shared with them and a revision:

// BUILT · apps/p2/src/runtime/principals.ts (excerpt)
export type GuestPrincipal = {
	readonly kind: "guest";
	readonly id: string;
	readonly name: string;
	readonly email?: string;
	readonly home: string;
	readonly sessions: Readonly<Record<string, "view" | "full">>;
	readonly revision: number;
};

/** May read the session: the owner, or a guest it was shared with. */
export const canView = (principal: P2Principal | undefined, session: string): boolean =>
	isOwner(principal) || (isGuest(principal) && Object.hasOwn(principal.sessions, session));

/** May send, stop and upload in the session: the owner, or a guest it was shared with read/write. */
export const canSend = (principal: P2Principal | undefined, session: string): boolean =>
	isOwner(principal) || (isGuest(principal) && principal.sessions[session] === "full");

Contradictions and gaps

Review: the instance user is still in two books

/tmp/users-chapter.md and resource-model/book.md (chapter II, "Admins and the instance user") define INSTANCE: UserId, "owns company resources and everything plugins bring". The 2026-11-13 decision replaces it with an owner { kind: "instance" }. users-sketch.md already drops it ("INSTANCE is not part of users"). The two books are stale on this point.

Review: account grants versus "one resource, one login"

accounts/book.md stores per-session grants (p3.account-grants) so a session may use a user's account. The resource-model book's third edition says "no grants" and "the owner of the resource decides its login, forever"; users-sketch.md agrees ("the per-call MCP account envelope is not needed: one resource, one login"). The accounts book's grant table is superseded; its AccountProviders (how an integration refreshes credentials) has no successor yet.

  • The kit's owner. The 2026-11-06 decision makes the owner the first user; users-sketch.md wants the kit's principal.owner removed in favour of an admin check registry. Not decided (its open point 1).
  • Who is admin. The users chapter keeps an admin flag in the users plugin; users-sketch.md moves it into the active directory. Not decided.
  • What a guest is. p3 reserves { kind: "guest" } with no fields; p2's guest carries sessions and a revision; sharing.md (owner direction, 2026-11-10) says someone you share an app with is a user, not a guest. Nobody has written p3's guest. See chapter V for why its shape decides how every factory checks.
  • A user's data when they leave. Each plugin keys its own per-user data by user id; nothing tells them a user was deleted (users-sketch.md open point 5).
III

Resources and Bringing

What a session may use: the decided direction, the single-user version p2 runs today, and two proposals that disagree on where the list lives.

The decided core is short: what a session may use is a list of resources, people bring their own resources onto it, and everyone who may send in the session uses all of it. Everything else, where the list is kept, how it is computed, who checks it, is open, and the two proposals answer differently.

Decided

  • No per-run authority (decisions.md, 2026-11-08: "there is no point in trying to prevent prompt injections. that's why one should be able to define what is brought into a session"). Everyone who may send in a session uses every resource in its selection, whoever started the run.
  • Resource model direction (decisions.md, 2026-11-08, voice walkthrough; "to be specified and reviewed against p2's features"). In short:
    • each resource has one owner and its own login or none, and never changes whose login it uses;
    • users create resources only for themselves; plugins' built-in resources (tools, prompt sections) exist when the plugin is installed; one Durable extension = one resource;
    • groupings (recent, folders, projects, Discord channels) only show things; a grouping "with resources" keeps a list in its own plugin;
    • a session has exactly one resource source: its own list, its owner's defaults ("everything I own plus every instance resource I may use, so new tools appear by themselves"), or one grouping with resources;
    • one replaceable policy plugin guards create, bring, add-member "through one guarded step in core";
    • workers follow their session's list live; the harness lets in only extensions whose resource is on it "(and belongs to the contributing plugin)"; resource plugins' per-session server views check the list.
  • Instance resources, not an instance user (2026-11-13): owner { kind: "user", user } or { kind: "instance" }; plugin-installed and company resources are instance resources; the policy decides who may create or bring them.
  • Session data on the server as host-keyed documents (2026-11-09): a plugin keeps per-session server data in its own server object, keyed by the session's host address (defineState(…, { keyed: Session }), host(Session) columns), so export, import and delete carry it. A session's list, wherever it lives, follows this rule.

Built: p2's lock

p2 has no users and no resources, but it has the single-user version of "what is brought into a session": the lock. A locked session (one listening to a Discord channel, say) uses only what the owner picked.

It is kept the Chord way: one store on the server, one per-principal object for the owner and for each worker. The worker's variant is a derive picking its own session out of the store, chosen from the worker principal alone:

// BUILT · apps/p2/plugins/sessions/locks.ts (excerpt)
host.serve(SessionLock, (_params, principal, self) => {
	const locks = self.get(SessionLocks, {});
	if (isWorker(principal)) {
		const session = principal.session;
		return {
			variant: "worker",
			members: { lock: deriveTyped(self, [locks.locks], ([all]) => all[session] ?? null) },
		};
	}
	if (!isOwner(principal)) throw forbidden("session locks are the owner's");
	return { variant: "owner", members: { locks: locks.locks, set: (args, ctx) => locks.set(args, ctx) } };
});

Proposed: two models of the list

The resource-model book (resource-model/book.md, third edition, 2026-11-08, p3 session, after the owner's code review). A resource is one row in the resources plugin's index (defineResource("mcp.server") names the kind); brought resources come from a registry while their plugin is installed; a session's effective list is a derive on the server, recomputed when anything it depends on changes:

// PROPOSED · apps/p3/docs/resource-model/book.md, chapter "One List" (2026-11-08), excerpt
host.serve(SessionList, ({ session }, self) => {
	const row = self.get(SessionCatalog, {}).rows.at(session);      // live: owner, source
	const resources = self.get(Resources, {});
	const own = resources.ownLists.at(session);                      // live: this session's own list
	const groupings = self.registry(Groupings);
	const policy = self.registry(Policies);
	// …
	const list = self.derive(
		[row, own, resources.index, resources.exclusions, fromGrouping, policy, clock],
		([r, ownEntries, index, excluded, grouping, current, time]) => {
			const entries =
				r.source.kind === "defaults" ? defaultsOf(r.owner, index, excluded[r.owner] ?? [])
				: r.source.kind === "own" ? ownEntries
				: grouping.entries;
			// …
			return { kind: "ready", entries: entries.flatMap((entry) => usable(entry, r, index, current, time.now)) };
		},
	);
	return { list };
});

This respects the factory rule: everything is declared, the key comes from params, the policy runs inside the derive (so it must be synchronous; chapter IV).

Contradictions and gaps

Review: defaults are a rule, not a copy

The 2026-11-08 decision says a session's owner-defaults are a rule, "so new tools appear by themselves", and the resource-model book computes them live. The walkthrough copies "my resources" into the session's rows at creation and asks in its open point 3 whether later resources should join. The decision already answers it; the walkthrough contradicts it.

Review: one source per session

The decision makes the source one field ("own list, owner's defaults, or one grouping with resources: the invariant is structural"). The walkthrough has no source field and no grouping with resources: each session owns rows. A project or a Discord channel that equips its sessions has no place in it.

Review: "belongs to the contributing plugin"

The decision says the harness admits an extension only if its resource is on the list "and belongs to the contributing plugin". The resource-model book's third edition dropped that check ("no plugin-name check: installed plugins are trusted code"). One of them should be corrected.

Review: shelved or alive

sharing.md §4 (owner direction, 2026-11-10) says "No per-user environments … the resource-model plugin stays shelved" and "no access-control lists in the base". The 2026-11-13 decision ("the policy plugin decides who may create or bring them") and both proposals from this week assume it is alive. Newest wins, but sharing.md still says shelved.

  • Central index or per-plugin lists. The book keeps one index of every resource (owner, label, revision) so a derive can compute lists; the walkthrough asks each plugin's list() at the moment of use, "in owner's scope", which needs a way to run plugin code as a user that Chord does not have (its open point 1).
  • Withdrawal. The book raises a revision so lists drop withdrawn entries; the walkthrough deletes the row. Both work; the book's also handles "Colin left the company" without touching every session.
  • Expiry. The book has until per entry (the Discord case: an hour of access); the walkthrough has none.
  • What is a resource in p2 terms. The lock picks MCP servers, instructions, and the capabilities ports and conversations; bash and file tools are not in it (a sandboxed location limits them). Whether p3's bash is a resource (the book: yes, coding-tools.bash) or a property of the location is not decided.
IV

Who May

One replaceable policy is decided; its shape is not, and the two shapes on the table cannot both be true.

Decided

The 2026-11-08 "Resource model direction": "One replaceable policy plugin (a registry with one provider; built-in default: the single user may do everything) guards create, bring, add-member and similar typed operations through one guarded step in core; plugins never know about ACL, SAML or Radius; the UI only renders server views (e.g. a per-user list of creatable kinds computed with the policy)." The 2026-11-13 decision adds that the policy decides who may create or bring instance resources.

Built

Contradictions and gaps

Review: synchronous or async

The resource-model book calls policy.decide(...) inside a derive (usable, which drops denied entries from a session's list) and inside MyResources.creatable. Derives are synchronous and pure (design §12). The gate sketch's company policy is async and awaits the directory. An async policy can gate a method call; it cannot compute a list or tell a page what it may create. If p3 wants both, the policy plugin must follow what it needs (groups, rules) as state and answer synchronously; the await directory.groupsOf moves into the policy plugin's own routine.

Review: "one guarded step in core" versus "a gate in Chord's dispatch"

The decision puts the guarded step in p3's core (a method plugins call). The sketch puts it in Chord's dispatch, which has no such hook. Chord's design argues against the hook: principle 2 ("The owner holds the data, enforces its rules in its methods"), §17 ("Registries add behaviour … they never replace an owner's checks") and §7 ("there is no async activation guard"). Chapter VI shows how to get the sketch's effect without touching Chord.

  • Closed or open vocabulary. The book's Request is a closed union in core: a third-party plugin's operation is only reachable through its call variant with match(op). The sketch is open: every plugin declares operations and facts, and a shared fact vocabulary (kind, runsCode, reaches, audience, right, resourceKind) lets a policy decide without knowing the plugin. Who owns that vocabulary is the sketch's own open point 6.
  • Conflicts. The book composes zero, two or a failed policy to deny-all; the users sketch does the same for directories; the gate sketch does not say.
  • Baselines. The book passes the asking code's own answer (the owner rule, the admin flag) as a baseline the policy may override; the sketch has no baseline. With a baseline the default policy is one line ((_request, baseline) => baseline); without, the default policy re-implements the hard rules.

Sharing and Locks

Read-only sharing is decided and built in p2 for guests; for p3's users the question is where 'may Ada send here' lives, and the factory rule decides that.

Decided

  • Read-only sharing (decisions.md, 2026-11-11: "we obv want read-only sharing"): a session can be shared with a viewer who reads everything and sends nothing, besides full participation.
  • No per-run authority (2026-11-08): a full participant's messages drive the same agent with the same list.
  • The agent writes plugins (2026-11-11): the trust boundary is access to the server; "a guest who may send can already have the agent run bash there".
  • Superseded: "A view's frame is a Chord client with a view principal" (2026-11-10), replaced by "Artifacts and views" (2026-11-12). There are no view principals.

Built in p2

p2's sharing plugin (apps/p2/plugins/sharing, p2-notes "Sharing") keeps links and grants in server tables keyed by host(Session), issues a guest principal per person with the sessions shared with them and their modes, and bumps the guest's revision on any change (share, join, removal, link reset, archive). The revision is part of the principal key, so the old principal's objects end (invalidatePrincipal) and the guest's page re-holds as the new one. Every factory then decides synchronously with canView and canSend (chapter I). A read-only guest gets the viewer or reader variant; an html artifact's bridge tells the page readOnly, and its changes are not saved.

The lock (chapter III) is the other half: what the session's agent may reach, whoever talks to it.

Proposed

  • sharing.md (2026-11-10, synthesis of three designers by the p3 session; nothing decided): Watch (read-only, default for links) and Join (talks to the agent; named, signed-in people only); approvals are never a guest's; links expire by default; freeze the scope, not the layout; whole-app sharing deferred. Its §4 records the owner's direction of the same day: views know who is there (presence); sharing an app with someone makes them a user, not a guest; which of an app's sessions they see is the app's decision, enforced in its own objects' variants; no access-control lists in the base; no per-user environments.
  • multiuser-walkthrough.md (2026-11-13): a sessions.people table (user, right: owner | send | view) and a sessions.links table per session, SessionPeopleView with share, unshare, link, revokeLink.

The gap: where does "may Ada send here" live?

In p2 the answer is in the guest's principal. p3's decided user principal is { kind: "user", id }. If Ada's rights live in the walkthrough's sessions.people table, a factory on the session's worker cannot read them: it runs synchronously and the table's value arrives after it returns. So the chat cannot choose viewer or editor for Ada. There are three ways out, all possible with today's Chord.

(a) Rights in the principal, as p2. { kind: "user", id, sessions: { S1: "view" }, revision }. Factories stay one line. Cost: every share or unshare anywhere bumps Ada's revision and ends all her objects on every device, which p2 accepts for guests with one or two sessions and a user with hundreds of sessions would feel all day.

(b) One variant for people; the right is followed state, checked per call. The worker's route admits only members (synchronous, against a value the server keeps current); the object exposes the right as state for the UI and checks it in each method; removing someone revokes their objects once. p2's worker route already admits by a synchronous check (canView, chapter I); here the check reads a followed membership map instead of the principal.

SessionPeople, Chat and Conversation below stand for p3 contracts that do not exist yet; every Chord call in it (host.serve, self.get, self.derive, forbidden, a route's authorize, host.revoke) exists today.

Review: the walkthrough's sessions core assumes (b) without saying so

SessionPeopleView has variants owner and member, picked in its factory, while the rights are rows of sessions.people. That factory cannot read the rows. Either the variant comes from the principal (a or c) or the object has one variant and checks per call (b).

Locks in p3

p2's lock is "the owner picks what this session uses". The 2026-11-08 decision turns it into "a session's own list" (one of the three sources). Nothing p3-specific about locks is decided beyond that. What p2's lock covers and p3's list must also cover: MCP servers by name, project MCP servers, global instructions and skills, and the capabilities ports and conversations. What p2's lock deliberately does not cover: bash and file tools, which a sandboxed location limits instead.

Open questions

  1. Guests in p3: a principal kind of their own (p2's shape), or a link admission into a user-like principal (users-sketch.md open point 4)?
  2. Which of (a), (b), (c) carries "may view, may send" for users?
  3. Approvals: may a send participant approve the agent's risky calls in someone else's session? sharing.md: never; the walkthrough leaves it open.
  4. Expiry of links and of named shares.
  5. Whole-app sharing: the owner's direction makes the other person a user; the app then decides which sessions they see. With which mechanism (the app's own objects' variants need the same answer as question 2).
VI

Three Edges in Real Chord

Today's proposal, checked against the factory rule: where each of its three mechanisms breaks, and how each would have to be written with Chord as it is.

Another session proposed this today (not decided), summarizing multiuser-walkthrough.md, operation-gates-sketch.md and users-sketch.md:

"Plugins never check anything themselves; the platform does it at three edges. (1) User scopes: a plugin declares some state is per user (e.g. my MCP servers) and writes code as if there were one user; the platform keeps a copy per user and hands the plugin the caller's copy (like browser profiles). (2) Operation gates: every contract method is a named operation; dispatch asks the policy before the call reaches the plugin (default allows everything; a company plugin restricts). (3) Resources on sessions: a plugin declares a kind of resource; the platform keeps which resources are on a session and who brought them, only lets you bring your own; before a call it checks the resource is on that session. p2's session lock is the single-user version."

The goal is right: a third-party plugin (the walkthrough's @someone/p3-todos) should not have to know about users, groups or policies. The mechanism assumes something Chord does not do: that the platform can look something up before the plugin's object exists and hand it in. In Chord the factory is synchronous and runs first; whatever it needs that is not in its params or principal arrives after it returned. The walkthrough's own list of "Guessed APIs" (scopes, gates, dispatch hooks, resource kinds) is exactly the set of places where it needs an async step before or around the factory.

Edge 1: user scopes

What it assumes. A table or document declared scope: "user"; a remote contract declared scope: "user"; a ctx.scope in methods; the platform adding the user to every key and query.

Where it breaks. The walkthrough's MCP plugin, as written:

// PROPOSED · apps/p3/docs/multiuser-walkthrough.md, A2 (2026-11-13), excerpt
host.serve(McpServers, (_params, _principal, self) => {
	const configs = self.table(Configs);                // rows of this object's scope only (u1 here)
	const all = self.query(configs, query(Configs), 1000);
	return {
		variant: "user",
		members: {
			servers: self.derive([all], ([rows]) => rows.map(toInfo)),
			create: async ({ label, config }, ctx) => {
				// …
				return { kind: "mcp.server", owner: ctx.scope, id };   // ctx.scope: guessed, the platform's user id
			},
		},
	};
});
  1. McpServers is a remote contract, so its factory gets Self, not StoreSelf: self.table and self.query do not exist there (chapter I). Tables belong to stores, one per host.
  2. scope: "user" on defineTable, defineState and remote, and ctx.scope, do not exist. Adding them is a Chord change against design §4 ("Objects persist a projection with its own schema, never the principal").
  3. Background work for one user (refreshing that user's tokens) would need "run as u1", which the walkthrough itself lists as unsolved (its open point 1).

What Chord already gives. Half of "a copy per user" is free: a remote object's identity is (type, params, principal key), so McpServers {} held by Mario and by Colin are already two objects. Only persisted data needs a key, and Chord has keyed documents (design §5 "Keyed state members", example test/examples/24-keyed-members.ts). The factory pins the caller's key synchronously, because the key comes from the principal; Chord loads it during activation:

A p3 API helper can hide the read side (refuse non-users, pin at(principal.id), hand the plugin mine). It cannot hide the write side completely: a store method takes data, never a function (design §5, "No callbacks as arguments"), so writes stay store methods with the user as an argument, and the store's own routines do background work for all users at once. The plugin author writes two small objects instead of one, and never sees another user's data from a per-principal object.

Edge 2: operation gates

What it assumes. A hook in Chord's remote method dispatch that runs await gate.decide(...) before the handler.

Where it breaks.

  1. Chord has no such hook, and its design rejects one: principle 2 (the owner enforces its rules in its methods), §7 (authority checks live in the per-principal view's methods), §17 (registries never replace an owner's checks). This is a design change to Chord, not a missing helper.
  2. The sketch's company policy is async and awaits directory.groupsOf. The same policy must also answer inside derives: the book's effective list drops denied entries in a derive, and a page's "what may I create" list is a derive. Derives are synchronous.

How to write it with today's Chord. Gating is a property of the methods an object returns, and a factory returns plain functions. p3's API can serve a plugin's factory through a wrapper that wraps the named methods; the wrapper declares the policy registry like any dependency. The plugin's handlers still contain no checks:

// PROPOSED · this rundown: a gate without a Chord hook (types simplified). Every Chord call here exists today.
export function serveGated<C extends Contract>(
	host: FacetHost<P3Principal>,
	Type: C,
	operations: readonly Operation[],                    // operation(McpServers, "create", { facts }) values
	factory: Factory<C, P3Principal>,
): void {
	host.serve(Type, (params, principal, self) => {
		const policy = self.registry(Policies);            // a declared dependency: the object parks until there is one
		const made = factory(params, principal, self);     // the plugin's own factory, still synchronous
		const members: Record<string, unknown> = { ...made.members };
		for (const op of operations) {
			const handler = members[op.method] as ((args: unknown, ctx: Ctx) => Promise<unknown>) | undefined;
			if (handler === undefined) continue;              // not in this variant
			members[op.method] = async (args: unknown, ctx: Ctx) => {
				const decision = policy.value.decide({ principal, operation: op.name, object: { contract: Type.name, params }, args, facts: op.facts(args) });
				if (decision.kind === "deny") throw forbidden(decision.reason);
				return handler(args, ctx);
			};
		}
		return { variant: made.variant, members };
	});
}

// The plugin, unchanged except for the serve call:
serveGated(host, McpServers, [CreateMcp, RemoveMcp], (_params, principal, self) => { /* as in edge 1 */ });

If p3's API hands plugins a facet host whose serve does this for every contract that declares operations, plugins do not even call serveGated. Calls between trusted code on the server (a store's methods) are not gated, which is correct: stores have no caller principal. The open choice is the policy's shape (chapter IV): with a synchronous decide over followed state, the same policy serves gates and derives.

Edge 3: resources on sessions

What it assumes. That the platform checks a resource reference against the session's list before the plugin's object for it is made, and sets the scope to the resource's owner.

Where it breaks. The walkthrough's third-party plugin:

	version: 1,

  1. Params are flat strings, integers, booleans or literals. { resource: ResourceRefParam } (an object) is refused at declaration.
  2. No check before the factory. The list lives in a server table or derive; reading it is async; Chord has no async activation guard. A worker's hold of a server object goes over its parent link, where the server sees only the worker principal ("Upward is a boundary", design §4), and there is no authorize in that direction.
  3. A check at hold time would not be enough anyway. Colin withdraws Linear while the worker holds the reference; the object lives on. The resource-model book already says "check again at every call".
  4. Tools get a Durable Context, not a Chord ctx (design §24). Durable's execute is (args, api, context); a tool reaches Chord objects through a root (chord(fn, context) in the design, worker().root(fn, context) in p2).
  5. inner.table in a remote factory: as in edge 1.

How to write it with today's Chord. The resource's identity is the params (flat); the factory declares the session's list, chosen by the worker principal; every method checks the list, and the state members hide the data when the resource leaves the list. This is the telemetry pattern from chapter I:

		variant: "worker",

				return store.add({ list: `${owner}/${id}`, text }, ctx);
			},
		},

The p3 version swaps view.servers for the session's list and builds defineExtension({ name, namespace, tools }) per entry; each tool's execute(args, api, context) opens worker().root(...) and calls the server object above. If core should enforce the list without trusting each plugin's filter, the resource-model book's shape is the one that fits Chord: contributions are pairs [resource, extension] and the harness drops pairs whose resource is not on the list (chapter XII).

Is p2's lock the single-user version?

Mostly, yes. The lock is a per-session list the owner picks, kept on the server, followed by the worker, mirrored into Durable, checked by the tool guard and by server objects at each call (chapter III). Two differences: it names capabilities (ports, conversations) and instructions, which p3 would have to make resources; and it leaves bash and file tools to the location's sandbox, while the resource-model book makes bash a resource.

What a Session's Worker Runs

Part 3. One process per session, the Durable harness inside it, and extensions from a registry: built in p2, designed in Chord §24, barely touched by p3's decisions.

Built in p2

Each session runs in its own worker process, started by the server through Chord's workers component and reached over a route whose links stamp { kind: "worker", session, generation }. The worker is a Chord host that loads every plugin's worker facet. Its core opens pi-durable's Harness on the session's store, and the harness reads its extensions from a Chord registry that host-lifetime objects and facets contribute to:

What else runs in a p2 worker, each a plugin's worker facet: the chat objects (one per conversation and principal), the models (WorkerModels), the execution environments (local, SSH, gondolin sandboxes), code mode's sandbox (CodemodeRuntime, one per worker), the MCP plugin's extensions (one per server; the processes and credentials stay on the server), subagents, views, artifacts' tools, the lock mirror, drafts, files.

Designed in Chord (§24)

Design §24 describes the same thing as p3's target: the harness is a store in the core facet (host lifetime) that opens Durable paused with self.open, reads models, environments and extensions from registries at each use, and is resumed after host.load. Tools, hooks and sections get Durable's ToolExecutionApi and a Durable Context, never a Chord ctx; they reach Chord through chord(async (ctx) => …, context), a root acting as the host. "Tools, sections, hooks, wraps and tasks reach the harness as one Durable Extension per plugin contributed to p3's core registry" (§17).

Decided for p3

  • No per-run authority (2026-11-08): no "who started this turn" anywhere in the worker.
  • Resource model direction (2026-11-08): "one Durable extension = one resource"; workers follow their session's list live; the harness lets in only extensions whose resource is on the list.
  • Artifacts and views (2026-11-12): plugin tools are code-mode only, grouped by the namespace their extension declares; the prompt lists namespaces from configuration, so it stays stable when servers connect.
  • The agent writes plugins (2026-11-11): plugin tools are ordinary tools in the session's selection; "a locked-down session does not get them, as it does not get bash".

p3 decided nothing about subagents, locations or code mode beyond this; they are p2's.

The Filters

Seven places decide whether the model sees a tool and whether a call goes through; p3 must keep or replace each.

Between "a plugin is installed" and "a tool call does something", p2 has seven filters. They run in this order.

1–3: into Durable's registry

An extension is there while its contributor is live (design §17). ExtensionSwitches leaves switched-off extensions out (code mode's setting). durableRegistry wraps every tool that declares requirements with guardTool.

4–6: per conversation (Durable)

Durable's AgentState holds each conversation's choices. Subagents use them to get a tool selection of their own:

A tool's callers (["model"], ["tools"] or both) and deferred decide whether the model is offered it directly, through code mode, or through tool_search when code mode is off.

7: the guard, and the server

// BUILT · apps/p2/src/runtime/tool-access.ts (excerpt)
export type ToolAccess = {
	/**
	 * Where it works: anywhere; only in the session's top-level conversations (`main`: the main conversation and its
	 * `/tree` branches, never a subagent or one-shot agent, for tools acting on the session itself); or offered only to
	 * subagents, which get it without choosing.
	 */
	readonly scope?: "any" | "main" | "subagent";
	/**
	 * In a locked session (`SessionLock`): `pass` (the default: what it reaches is limited by the lock elsewhere, MCP
	 * servers by their leases, location tools by the sandbox), `never`, or only when the owner picked the capability.
	 */
	readonly locked?: "pass" | "never" | LockCapability;
};

export function guardTool(tool: P2Tool): P2Tool {
	const rule = tool.locked ?? "pass";
	if (rule === "pass" && tool.scope !== "main") return tool;
	return {
		...tool,
		execute: async (args, api, context: Context): Promise<ToolExecutionResult | ToolPark> => {
			if (tool.scope === "main" && !(await isTopLevel(api, api.conversationId, context)))
				return refusal(`${tool.name} works only in the session's main conversation.`);
			if (rule !== "pass") {
				const lock = await sessionLock(api, context);
				if (lock && rule === "never") return refusal(`${tool.name} is not available in a locked session.`);
				if (lock && rule !== "never" && !lock.capabilities.includes(rule))
					return refusal(`${tool.name} is not among the resources the owner picked for this session.`);
			}
			return tool.execute(args, api, context);
		},
	};
}

The proposed harness, and whether it fits Chord

The resource-model book's harness respects the factory rule: it declares the extensions registry and the session's list in the factory, opens Durable as a native, and checks the list at compose time and at each call:

// PROPOSED · apps/p3/docs/resource-model/book.md, chapter "On the Worker" (2026-11-08), excerpt
export type HarnessExtension = readonly [resource: ResourceRef, extension: Extension];
export const Extensions = defineRegistry<
	readonly HarnessExtension[] | Watchable<readonly HarnessExtension[]>, ExtensionTable
>("harness.extensions", { version: 1 });

host.serve(HarnessHost, (_params, self) => {
	const extensions = self.registry(Extensions);
	const resources = self.get(SessionResources, {});

	/** Whether `resource` may be used now: the server link live, the list ready, the entry there and not expired. */
	const allowed = (resource: ResourceRef): boolean => {
		if (resources.state.value.kind !== "live") return false;              // a lost link keeps last values, not permission
		const list = resources.list.value;
		if (list.kind !== "ready") return false;
		const now = Date.now();
		return list.entries.some((e) => sameResource(e.resource, resource) && (e.until === null || e.until > now));
	};

	// Durable's registry, built as p2's durableRegistry (apps/p2/src/runtime/durable.ts) with `allowed` in place of
	// switches: rebuilt when the extensions or the list change, and every tool's execute wrapped so a call is refused
	// when `allowed` turns false mid-phase (captured code-mode tools, nested calls included).
	const registry = self.open((ctx) => durableRegistry(extensions, resources.list, allowed, ctx), closeRegistry);
	return {};
});

It is p2's durableRegistry with the lock replaced by the list: the same three moves (follow, compose, wrap). One detail does not fit design §24 as written: there the harness is base code in the core facet, here a plugin (plugins/harness) owns the registry. Either is possible; the 2026-11-06 "Reloads first" decision ("every behaviour … is a plugin") favours the plugin.

The walkthrough's version (ResourceExtensions with an extension(resource, label) factory per kind) has the tools call ctx.get(...) inside execute(args, ctx); with Durable that is execute(args, api, context) and a Chord root (chapter VI, edge 3).

Locks become the list

p2's lock answers "what may this session's agent use" for one owner. In p3 the decided answer is the session's list, with three sources (own, defaults, a grouping). The p2 lock is then exactly a session whose source is "own". What has no p3 home yet: the lock's instructions flag (global AGENTS.md, skills, prompt templates) and the capabilities ports and conversations; in the book's terms they would be instance resources brought by their plugins.

Ten Rules and the Decisions Left

One page: ten rules that would settle most of the above (proposed by this rundown), and the owner's open decisions in the order they unblock the most.

Ten rules (proposed)

  1. A factory decides only from params and the principal. Everything else is checked in methods and shown as derived state. (Chord as it is; no async activation guard.)
  2. Per-user data lives in a store keyed by user id. The per-user object pins at(principal.id) in its factory. No scope option in Chord.
  3. A resource's owner is a user or the instance. You create and bring only your own; who may create or bring instance resources is the policy's call. (Decided 2026-11-13.)
  4. A session has one list, from one source. Everyone who may send uses all of it. No per-run authority. (Decided 2026-11-08.)
  5. The list is computed on the server and followed by the worker. The policy is applied when the list is computed; the worker never asks the policy.
  6. Every server object a worker calls for a resource checks the list at each call and hides the resource's data in its derived state once it is withdrawn.
  7. The policy is one synchronous function over state its plugin follows, with the asking code's baseline. Hard rules (you bring only your own) come first and no policy changes them.
  8. Guarded methods are wrapped when served, by p3's API from the operations a contract declares, never by a hook in Chord's dispatch.
  9. A view shows an item a plugin owns. The plugin decides where the item's data lives and who sees it, through its per-principal objects; the layout only places.
  10. A guest sees exactly what the objects give their principal. A layout or a hidden pane never protects anything.

Decisions for the owner, in the order they unblock the most

  1. Where "may view, may send" lives for users: in the principal (p2), as followed state checked per call, or a principal per session (chapter V, a/b/c).
  2. Policy shape: synchronous over followed state, or async (chapter IV).
  3. Per-user data: the store-plus-pin pattern of edge 1, or Chord-level scopes.
  4. Resource index: one central index (resource-model book) or per-plugin list() (walkthrough).
  5. Defaults are a live rule (decision of 2026-11-08): confirm, and drop the walkthrough's copy at creation.
  6. Guarded operations: core's typed request union, or plugins' operations with shared facts; who keeps the fact vocabulary.
  7. Who enforces on the worker: core (extensions keyed by resource) or each resource plugin; and whether "belongs to the contributing plugin" stays.
  8. Retire stale texts: INSTANCE in two books, account grants, sharing.md's "resource model shelved", views.md's typed params and two tiers.
  9. Guests in p3: their own principal kind (p2's shape) or a link admission into a user-like principal.
  10. Placements: session data (p2) or layout data, and who hosts layouts (per user and device class, or per device).
  11. The "+" registry: ViewKinds gains title, icon and needsItem; where recently closed is kept.
  12. Terminals and files as view kinds, and which guests get them.
  13. Environments: instance-wide (sharing.md) or resources owned by users (book).
  14. Lock capabilities and instructions as instance resources.
  15. Plugin tools in a locked session: mark reload_plugins locked: "never" in p2, or change the decision's wording.
  16. Layouts as apps: record it in decisions.md or not.
