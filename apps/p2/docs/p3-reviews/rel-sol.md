# rel-sol — focused adversarial reload and rollout review

Scope: `target-design.md` §15 and `plugin-loading.md` §§4.1, 7.4, 7.5, on pi-private `6559589bd`; read-only review against real p2 plugins and runtime. Assumes §§7–14 as given. This records review conclusions and recommendations, not implemented behavior. References to an "owner decision" below mean the decision is stated as decided in the target design; the proposed fixes and open questions are **not** known to have been decided by the owner.

## Verdict

**§15 is not sound enough to build as written.** The clean rollout path is plausible, but the start barrier, registry admission, removal, and overlapping-install rules need tighter definitions. These are design findings, not claims about the current loader.

## Findings (ordered by severity)

1. **Durable work can remain blocked after removal or a failed first load.** A subagent reporter can commit its `report` checkpoint, then `subagents` is removed and the worker restarts. The next phase has no `p2.subagent-reporter` definition, so its answer is never delivered. A pinned snapshot protects a phase already running, not one resumed after a crash. The start barrier also permits an “optional” facet to fail before Durable resumes. See target-design.md §15 (lines 446–452), `plugins/subagents/tools.ts:118–164`, and `packages/durable/src/harness/scheduler.ts:1229,1366–1381`. **Fix:** treat definitions needed by unsettled Durable tasks as required; block removal or retain their definitions until the tasks settle, and check this before `resume()`. **Status:** Open. The decision to allow optional-facet failure and to remove types in place is stated in §15; this necessary Durable-specific exception is not resolved there.

2. **The start barrier can deadlock against its own worker admission.** The subagents host-lifetime contributor holds the server’s `Subagents` object (`plugins/subagents/worker.ts:35–39`). Today the worker admits its IPC link with `control.ready()` *before* awaiting `host.ready()` (`src/hosts/worker.ts:98–105`). If “wait until every contributor is live” and “route nothing until it reports” also delay that link admission, the hold cannot complete, so the worker cannot report. This applies to a worker spawned mid-rollout too. See target-design.md §§14–15 (lines 417–418, 446–457). **Fix:** specify an early transport/control admission distinct from application routing; gate external calls, not the link needed for bootstrap holds. **Status:** Open. The §14 start barrier and §15 install-before-routing policy are stated design decisions; their ordering needs to be reconciled.

3. **Publishing registry entries before their resources are ready bypasses the object gate.** Radius registers a request resolver that immediately reads `connection.value` (`plugins/radius/server.ts:46–48`); HTTP invokes resolvers directly from the registry (`src/hosts/server.ts:493–500`). Between publish and resource replacement/open, a request can invoke a new resolver against an unready resource. Retaining the old resolver is not necessarily safe either if its resource has been replaced and its handle is stale. See target-design.md §15 (lines 434–440). **Fix:** make registry invocation readiness-aware, or keep the old contributor *and its usable resources* until the replacement is ready, then switch exposure together. **Status:** Open. The publish/after division and no-entry-gap goal are stated decisions; direct registry calls need a rule that actually enforces them.

4. **A rejected facet can break a same-host registry contract without a binding failure.** For example, change chat’s `SendRouters` interface while changing `chat-mode`; if `chat-mode` setup throws, its old router remains, while new chat can read and invoke it directly (`plugins/chat/worker.ts:588–596`; `plugins/chat-mode/worker.ts:131–169`). The object-type bind rule does not protect that function call. Section 13 describes adapting old entries, but §15 does not say that an incompatible retained entry refuses the *new registry owner’s* publication. See target-design.md §§13, 15 (lines 395–401, 429–438). **Fix:** validate the complete proposed table, including retained entries, against its owner version; reject the dependent publication unless an adapter covers each old entry. Report the resulting mixed-version state, not just the facet that threw. **Status:** Open. Per-facet setup rejection and mixed versions within one host are expressly accepted in §15, but the claim that the same contracts protect every cross-plugin interaction needs this validation, including old registry readers as well as old entries.

5. **Removal contradicts the promise that running work finishes.** A chat shell is launched after its method returns; ending its object closes `shells` and aborts the command (`plugins/chat/worker.ts:185–195, 320–347`). If chat is removed while it runs, the command may already have changed files, while its subsequent state write or transcript entry can fail (`:270–315`). A retry can repeat the external effect without the original result being recorded. See target-design.md §15 (lines 449–452). **Fix:** either refuse removal while such work is active, or define removal as cancellation with a durable, visible terminal result. Do not apply the ordinary “running work finishes” claim to removal. **Status:** Open. In-place removal and non-draining reload are stated decisions, but their interaction for already-running work is unspecified.

6. **Successive installs need explicit per-host serialization.** Nothing in §15 or plugin-loading.md §7.5 orders R2 against an R1 whose asynchronous *after* phase is still reopening resources. R2 can publish and open its gate; an R1 completion can then replace a resource or report after R2, leaving the host’s advertised revision different from its live code. A server restart during a rollout makes late reports particularly important to discard. See target-design.md §15 (lines 429–440, 455–467); plugin-loading.md §7.5. **Fix:** serialize publish/after per host, retain only the latest desired complete code set, and fence every completion and report by revision *and incarnation*. **Status:** Open. Complete-code-set revisions with server incarnation are stated decisions; install ordering and stale-completion handling are not.

7. **`installed` at an older revision has no mismatch rule.** The stated cases cover a provider ahead, behind *and installing*, rejected, or at the same revision (`target-design.md:468–476`). In rapid rollouts, a client at R2 can meet a worker still reporting `installed` R1 before its R2 install starts. This is neither “behind and installing” nor final; parking without a known target relies only on the deadline. **Fix:** responses must include the provider’s desired/pending revision as well as its installed revision. Define a behind-but-not-installing state: initiate reconciliation if reachable, otherwise fail or time out with a specific reason. **Status:** Open. Parked calls, mismatch status and deadlines are stated decisions; this state is missing from the comparison table.

8. **The readiness gate opens before eager singleton migration.** Section 15 orders “then the readiness gate opens” before migrating exposed singleton documents (`target-design.md:439–444`). A newly admitted call or subscription can therefore reach a v2 member while its stored value is still v1, despite the stated rule that v2 operations never run on v1 state. **Fix:** migrate eager singletons before opening that object’s gate; if one migration fails, expose its specified per-member error when the gate opens. **Status:** Open. Lazy migration of unloaded/keyed documents and per-member failure for exposed singletons are stated decisions; the eager migration/gate order needs correction.

## Additional review points, open questions and boundary cases

- **Clean reconnects, new workers and late clients.** The revision/incarnation scheme and install-before-routing rule address ordinary reconnects and late clients **if** enforced for every new worker, web page and TUI host. Current `src/runtime/server.ts:380–389` chooses a worker's init plugins at spawn, and `src/hosts/web/main.tsx` and `src/hosts/tui-client.ts` use their own client connection/bundle lifecycle. A worker spawned during rollout must be tagged with the complete desired revision, admit its bootstrap link as in finding 2, reconcile it, and withhold application routing until it has reported. A client that was disconnected, hidden, or installed late must reconcile the current complete set on reconnect; a server restart must force reinstallation across incomparable incarnations. **Status:** Intended by §15 (owner-design decision), but the admission/progress ordering in findings 2, 6 and 7 remains open. No separate defect is claimed for an ordinary successful reconnect.
- **Partial rollout and rejected facets.** A server *load* error is specified to stop the rollout before publishing; a setup rejection *after* load can leave that server on mixed facet versions while workers and clients advance. Likewise a worker rejecting a facet is not necessarily a reason to stop the whole rollout. These are deliberate no-cross-host-transaction choices. The provider's reported revision must not pretend to name the complete code set when it retained an old facet, and the rejection status and plugin-specific reason must travel to affected bindings. Validate retained registry entries, shared document assumptions and old readers before treating this as contract-safe (finding 4). **Status:** Mixed versions/no votes decided in §15; safe detection/reporting of same-host incompatibility open.
- **Project installs and base rollouts.** Project revisions install per worker, outside the base rollout (`plugin-loading.md` §7.4), while the worker also receives base facets from the server (`§4.1`, `src/runtime/server.ts:380–389`). An overlapping project install and base R1/R2 install needs a single per-host publication order and an explicit representation of both desired sets; comparing only the base revision must not mistake a project facet's state for a fully reconciled worker. **Status:** Separate project revision is stated in §7.4; combined ordering/identity is open. No concrete project-plugin failure was established in this review.
- **Routines and parked calls.** §11 allows a routine's old handler to finish, with a deadline before starting its replacement. A worker routine waiting on a server call that is parked for the worker's pending install can delay that install itself. The deadline makes the wait finite, but an old handler that later resumes may duplicate a new routine's reconciliation unless the operation has its own idempotency key. The subagents reporter uses submission request IDs (`plugins/subagents/tools.ts:127–133,155–163`), an example of the required protection. **Status:** The routine deadline and reconciliation rule are stated decisions; ensure the install path does not wait on a handler blocked on that same install, and document per-operation deduplication where appropriate. This is a review question, not a separately established finding.
- **Resources and old code.** §12 expressly allows a replaced native to error for old running work and says old handles become stale. This limits §15's broad “running calls and jobs finish with their old code” language: they finish execution under old code, but need not succeed or preserve an external operation after resource replacement. Code mode's running scripts depend on a sandbox resource (`plugins/codemode/worker.ts:22–40`); removing code mode has an explicit cancellation implementation (`plugins/codemode/calls.ts`). **Status:** Resource replacement semantics decided in §12. Open recommendation: state the limitation and require a terminal result or a refusal for effects that cannot safely be interrupted, especially removal (finding 5); do not promise uninterrupted work solely from code pinning.
- **Preparation versus publication.** Explicit reload, never on save; no factory trial, migration dry run or live-consumer check at prepare; install means code published rather than every object live; per-object failed/backoff/retry are stated owner-design decisions (§15). These are not themselves defects in this review. They make clear post-publish failure states, per-member migration errors, validated registry tables and readiness gates necessary rather than optional preflight complexity. **Status:** Decisions stated in §15; concrete gaps above remain open.

Read-only review: no implementation changes or tests were made.
