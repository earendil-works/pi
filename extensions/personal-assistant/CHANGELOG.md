# Changelog

## [Unreleased]

### Breaking Changes
- **Client-side recall re-ranking removed — server is the sole ranking authority**: `recallAtomsSingleSegment` no longer computes a `score` formula (no more `cosine × (1 + 0.3×strength + 0.2×importance) + 0.10×tagOverlap + 0.05×freshness`), no longer applies per-type top-3 cap, no longer round-robin interleaves. The bge-m3 FastAPI service runs the dual-channel (dense + learned sparse) RRF fusion server-side and returns the pre-sorted top-K; the client propagates `rrf` / `cosine` / `sparseScore` verbatim. `formatMemoryContext` re-sorts by `rrf` DESC (server's RRF order) before injecting into the LLM prompt. `RecallResult` drops the `score`, `tagOverlap`, `freshness`, `distance` fields and gains `rrf` + `sparseScore`. `scoring.ts` (computeScore / computeTagOverlap / computeFreshness) is deleted.
- **`DEFAULT_DENSE_COSINE_FLOOR` reverted 0.60 → 0.55**. The 0.60 setting (shipped in the previous "trust server" refactor) was wrong: for short queries like `之前修复的脚本是哪个` where max cosine is 0.59, the dense channel collapses to 0 hits and RRF degenerates to "sparse rank-0 for everyone" — all candidates end up at RRF ≈ 0.0167 with no gap to the actual relevant atom. At 0.55 the top-2 hits clear the dense channel and reach rrf=0.0328 (rank-0 in BOTH channels), giving a clean gap to the tail (0.0164). The 0.60 value's stated rationale ("sparse carries keyword rescue so we can tighten dense") was correct in isolation but missed the second-order effect: RRF needs BOTH channels to differentiate, and 0.60 was tightening past the point where the dense channel contributed anything. The empirical evidence from the original refactor still holds: sparse rescue works for short keyword queries (`MGM` → 1 hit, `mgm 项目还记得吗` → 1 hit, `BLAST 验证引物` → 2 hits).
- **`PersonalAssistantConfig.memory.{tagOverlapWeight, freshnessWeight, tagAliases}` removed**. These were the runtime-tunable scoring knobs for the deleted `score` formula. Settings that still include them are silently ignored. (The PATCH `/api/memory/:id` route no longer reads `tagAliases` for write-time tag folding either — passes `undefined` to `mergePatchBody`.)
- **Webui `POST /api/memory/search` response shape change**: drops `score` and `distance` fields, adds `sparseScore` and `rrf`. Frontend consumers reading `r.score` need to switch to `r.rrf`.
- **Decay formula re-parameterized from `baseDecay` to `halfLifeDays`**: `runDecay` now takes a half-life in days (default **33**) instead of a per-day decay rate. Formula: `new_strength = strength × exp(-ln(2) × deltaDays / (halfLifeDays × importance))` — at `importance=1` a reference atom reaches 0.5 strength after 33 days without access; effective half-life scales linearly with importance (e.g. `importance=2` → 66-day half-life, `importance=0.5` → 16.5-day half-life). `PersonalAssistantConfig.memory.decay.baseDecay` is removed; the config key is now `halfLifeDays` (camelCase) or `half_life_days` (snake_case). Settings that still include `baseDecay` are silently ignored.
- **Decay cadence changed from hourly throttled to daily throttled**: `DECAY_INTERVAL_MS` 1h → 24h. `session_start` now runs `runDecay` at most once per 24h per process — appropriate for a 33-day half-life (a user who opens pi once a day sees one batch of forgetting applied per session_start; multiple session_starts on the same day are no-ops).
- **`RunMemoryExtractionResult.superseded` → `updated`**: the LLM-driven update via `oldId` collapses what used to be two buckets (cosine gate's `supersede` for "mark old + create new" + LLM 二次确认's `update` for in-place rewrite) into a single `updated: Array<{oldId, newAtom}>` bucket (in-place rewrite keeps id; `oldId` field reports the parent for true supersedes). External callers reading `result.superseded.length` must switch to `result.updated.length`. In-tree callers already updated: `memory.ts` (`runCompactExtraction` completion notify), `packages/webui/server/routes/sessions.ts:316` (DELETE session extraction summary), `packages/webui/server/routes/memory.ts` (`POST /api/memory/extract` response).
- **LLM-driven update via `oldId` (replaces cosine gate + Phase-2 LLM 二次确认)**: `extractionPlanSchema.items[*].oldId?: uuid` is the only update reference; presence means "merge into atom with this id", omission means "create fresh". The corpus section in `buildExtractionPrompt` now renders each recalled atom with id + summary + content preview (300 chars) + .md path so the LLM can target a precise merge. Removed: programmatic `findMostSimilarEmbedding(0.65)` cosine gate in `executeItem`, Phase-2 `confirmDedupAction` second-pass LLM call (single LLM call per /compact cycle now), `persistSupersede` helper, the `supersedeIfSimilar` extraction-side path, and the `extraction-dedup-confirm.ts` + `extraction-dedup-confirm.test.ts` files entirely. `supersedeIfSimilar` and `dedup.ts` remain for the webui PATCH path. **Known trade-off** (see Known Limitations): paraphrase duplicates the LLM missed by recall will not be corrected at write time and may slowly bloat the corpus until a future drive-time sweep.
- **API surface for `POST /api/memory/extract`**: response `superseded` field renamed → `updated`, `supersededPairs` → `updatedPairs`. Same rename applies in `RunMemoryExtractionResult` callers across the codebase.

### Added
- **LLM 二次确认 dedup on cosine ≥ 0.65 hit (Task 3.7)**: `executeItem` no longer auto-supersedes when a cosine hit fires. When the caller supplies a `callLlm` closure, the hit is forwarded to `confirmDedupAction` which asks the LLM to disambiguate four actions — `update` (in-place rewrite of the hit atom with merged content), `supersede` (mark old + create new), `create` (cosine hit was coincidence, keep both), `skip` (drop the new item). LLM failures (timeout, non-JSON, schema mismatch) collapse to a conservative "supersede" fallback so a transient LLM outage never silently absorbs an unconfirmed duplicate. Without `callLlm` the legacy "auto-supersede" path via `supersedeIfSimilar` is preserved. New `updated` bucket in `executePlan` / `executeParsedPlan` / `extractMemoriesWithCallLlm` / `RunMemoryExtractionResult` return shapes for the LLM-chosen merge case.
- **Tag normalization + concept-tag presence warn in `executeItem`**: every item's `tags` array is run through `normalizeTag` (trim, case-fold, dictionary match) before `buildAtomFromItem`; if the normalized tag list contains no `concept/*` tag, a `[extract] item "..." lacks concept tag` warning is logged so missing cross-cutting properties are visible in the run log without blocking the write.
- **`reindexOneOrWarn` bge-m3 reindex after every write path**: `executeItem` now calls `reindexOne(atomId)` after every successful insert / update / supersede (create, update, supersede actions all converge on this final step). The call is non-fatal — `reindexOne` already collapses every failure to `{ok: false, error}`, and `reindexOneOrWarn` just logs a warning on `!ok` so a bge-m3 service blip never aborts the extract pipeline (one stale vector until the next reindex is the documented trade-off).
- **Migration script `extensions/personal-assistant/scripts/migrate-legacy-atoms.mts` (Task 2.3)**: one-shot program-driven dedup for legacy atoms. Reads the active corpus, sorts by `access_count DESC, last_access DESC NULLS LAST, created_at DESC` so the most-used atom in each cluster wins, then for each atom calls `findMostSimilarEmbedding(embedding, threshold)` (default 0.65, CLI override via `--threshold=N`) and `markSupersededNoInsert(hit.id, atom.id, now)` to archive the loser. Pre-migration backup `memory.db.bak.YYYYMMDD` is created first; on backup failure the script aborts without touching the db. Writes a `migrate-report.json` summary (active/archived/unchanged counts + threshold + backup path). Idempotent by design — re-run finds no cosine-≥-0.65 pairs and produces 0 changes.
- **`markSupersededNoInsert(oldId, parentId, now)` helper on `MemoryIndex` (Task 2.1)**: UPDATE-only migration primitive. Marks an existing atom as superseded (sets `is_latest=0, parent_id=<winner>, superseded_at=now`) **without** inserting a new row and **without** rewriting the loser's `memory_vectors` row. The `parent_id` direction is intentionally inverted vs `markSupersededTx` (loser points to winner) so the migration sweep can archive losers without touching the winner. Returns the updated atom.
- **`getEmbedding(id)` helper on `MemoryIndex` (Task 2.4)**: reads the cached bge-m3 embedding for an atom from `memory_vectors` and returns it as a plain `number[]` (or `null` if the row is missing). Reconstructs the `Float32Array` view via the `buffer + byteOffset + byteLength / 4` defensive idiom, matching the rest of the storage code's tolerance for Node Buffer pooling.
- **`findMostSimilarEmbedding` / `vectorSearch` now accept `excludeId?` (Task 2.5 fix)**: the previous behavior returned the query atom itself as the closest match (cosine 1.0) when present in the index, blocking the migration loop from ever reaching the real neighbor. The new optional 4th arg lets the migration script (and any future caller that needs to skip self) pass an id to exclude — applied as a SQL `v.id != ?` clause AND an in-loop guard for belt-and-suspenders. Without `excludeId` the legacy behavior is preserved exactly, so `dedup.ts` and `extraction.ts` self-match guards remain valid for write flows where the new id is freshly minted.
- **`tag-vocab.ts` (Task 3.1)**: tag dictionary + normalization helpers. `loadTagVocabulary(index, topK=50)` scans active atoms and returns the top-K most-frequent tags (with deterministic alphabetical tiebreak) so the extraction LLM can prefer existing tags over inventing near-synonyms. `normalizeTag(input, dictionary?)` trims + dictionary-exact-match (priority) + ASCII case-fold (Chinese kept verbatim via Unicode-range detection). `conceptTagCount(tags)` counts entries under the `concept/*` namespace so callers can warn when an atom has no cross-cutting action/category tag.
- **`EXTRACT_PROMPT_V2` active-update section (Task 3.3)**: new `## 主动更新,非扩张` block instructs the LLM to update an existing atom's `content` (with date-stamped appended paragraph) when new information belongs to the same topic/object, instead of creating a new atom. Reduces the future-atom-creation rate without requiring program-side force-merging.
- **`buildExtractionPrompt(messages, opts?)` now accepts `tagVocabulary` (Task 3.4)**: when a non-empty vocabulary is supplied, the prompt gets a `## 现有 tag 字典 (优先复用, 不要发明新近义 tag)` section with the comma-joined entries injected between `EXTRACT_PROMPT_V2` and the user tone hint. Backward-compatible — `buildExtractionPrompt(messages)` without opts is byte-identical to before.
- **`extractMemoriesWithCallLlm` + `RunMemoryExtractionOptions` carry `tagVocabulary?` (Task 3.6)** and `memory.ts` lazily computes it once per corpus-size change (Task 3.5): module-level cache keyed by `getActiveAtoms().length` avoids re-scanning 1000+ atom corpora on every `session_before_compact`. Cache invalidates automatically when the corpus size changes (manual add/remove).
- **`extraction-dedup-confirm.ts` (Task 3.8)**: LLM 二次确认 decision helper. Builds a `DEDUP_CONFIRM_PROMPT` from hit.atom + newItem + cosine, calls `callLlm(prompt)`, then zod-validates the JSON response against `{action: update|supersede|create|skip, merged?: {...}}`. Throws on non-JSON or schema failure — the caller (`executeItem`) handles the conservative "supersede" fallback. 5-second timeout lives in the caller's `callLlm` (memory.ts:402-441), not stacked here.
- **`bge-reindex.ts` (Task 3.9)**: thin `reindexOne(atomId, baseUrl?)` HTTP client for the bge-m3 `/api/atoms/{atomId}/reindex` endpoint. 5s `AbortController` timeout, never throws — returns `{ok: false, error}` on any failure. Used by `executeItem`'s `reindexOneOrWarn` helper after every successful write.
- **`memory_save` tool (capability `agent-memory-write-tool`)**: single agent-facing write tool exposing three outcomes via the `MemorySaveResult.details.action` field — `created` (fingerprint miss + no id → fresh atom), `skipped` (fingerprint hit on an active atom → no-op with `existing_id`), `updated` (caller-supplied `id` matching an existing atom → in-place rewrite with `version + 1`), and `error` (caller-supplied `id` not in DB → `error: "id_not_found"`). TypeBox schema (`MemorySaveParams`) validates `type ∈ {rule, fact, process}`, `title ≤ 200 chars`, `content ≥ 10 chars`, `importance ∈ [0, 1]`, `tags ≤ 10 entries × 50 chars` before dispatch; validation failures return `{action: "error", error: "invalid_type" | "content_too_short" | ...}` rather than throwing. The bge-m3 `embedText` call uses an explicit 15s timeout and gracefully falls back to a 1024-dim zero vector (`embedding: "skipped"`) when the embed service is down — the DB row and .md sidecar still land so a later reindex trigger catches up.
- **`recallPipeline(index, opts)` shared helper (capability `tui-webui-recall-parity`)**: single recall entry point that both the TUI `before_agent_start` hook (`memory.ts:871`) and the webui `POST /api/memory/search` route (`routes/memory.ts:932`) call. Encapsulates `rewriteQueries → recallAtoms (parallel) → rerankAndFilter → mergeByRerankScore` with sticky-priority status aggregation (an earlier `fallback` rerank status is never overwritten by a later `ok`), 1-100 `topK` clamping with default 20, optional bge-m3 `/api/health` probe that surfaces `status.embeddingServiceStatus: "up" | "down"` without blocking the main pipeline, and per-stage timing metadata (`status.recallMs` / `rewriteMs` / `rerankMs`). Returns `{results: RecallResult[], status: RecallStatus}` — the webui adapts this to its `{hits, recallTimeMs, ...}` response shape while the TUI pipes `results` straight into `formatMemoryContext`.
- **`tool_call` hook blocks direct file writes to memory atoms (`extensions/personal-assistant/tools.ts:1046-1085`)**: agents can no longer bypass `memory_save` by calling `write` / `edit` with `path: "~/.pi/agent/memory/atoms/**"` or `bash` with redirect / heredoc / tee targeting the atoms directory. Block returns `{block: true, reason: "..."}` and the tool's `execute` is never invoked. `read` and `bash {command: 'cat <atoms-path>'}` pass through unchanged — only the write-side surface is gated.
- **`before_agent_start` injects `## Memory` system prompt section (`tools.ts:920+`)**: every agent turn sees the canonical `memory_save({type, title, content, summary?, importance?, tags?, id?})` contract, the three outcomes + the `id_not_found` error envelope, and the rule "do not write/edit/bash to `~/.pi/agent/memory/atoms/**` — use `memory_save`". The TUI footer still surfaces the recall status from the previous turn.
- **Segment save counter (`segmentMemorySaveCount`) module-level state**: zero-cost integer that ticks up by 1 inside `memory_save.execute` after any successful outcome (created / skipped / updated) and is the signal the `session_before_compact` safety net reads. Exposed via `getSegmentMemorySaveCount` / `incrementSegmentMemorySaveCount` / `resetSegmentMemorySaveCount` for testability.

### Changed
- `supersedeIfSimilar` default cosine dedup threshold 0.92 → 0.65 (Task 1.1). The 0.92 value was effectively inert — it sat so far above the recall floor (0.55) that almost no real cluster pair ever crossed it, leaving the corpus free to accumulate near-duplicate atoms. At 0.65 the threshold sits 0.10 above the recall floor (a buffer for bge-m3 cosine noise) and catches the real cluster pairs (90-atom sweep: 35 hits, 0 false positives). Migration script and live extract path both use the new default. Callers that want the old value can still pass `threshold` explicitly.
- `EXTRACT_PROMPT_V2` no longer advertises 0.92 (Tasks 1.3, 3.3) — the `## Dedup 策略` bullet and `executeItem` JSDoc now read "≥ 0.65" so the LLM and future maintainers see the same number the runtime actually uses.
- `executePlan` / `executeParsedPlan` / `extractMemoriesWithCallLlm` signatures extended with an optional `callLlm?` parameter (Task 3.7, 3.11). When provided, the same LLM callback is used twice: once for the initial extraction JSON and once per cosine hit to disambiguate the dedup action. When omitted, the legacy `supersedeIfSimilar` auto-supersede path is preserved.
- `RunMemoryExtractionResult` and `extractMemoriesWithCallLlm` return shape add a new `updated: Array<{oldId, newAtom}>` bucket (Task 3.7) for the LLM-chosen "update existing atom in place" case so callers can distinguish a rewrite from a supersede/create.
- `RunMemoryExtractionOptions` extends with optional `tagVocabulary?: string[]` (Task 3.6); the webui entry point passes it through to `extractMemoriesWithCallLlm` unchanged.
- **`session_before_compact` safety-net semantics**: when `segmentMemorySaveCount >= 1` (the agent already wrote an atom this segment) the safety net short-circuits — it returns `undefined` and does NOT invoke `runCompactExtraction`. Replaces the legacy hard-gate `{cancel: true}` which blocked compaction outright. When the count is 0 the legacy `runCompactExtraction` flow is preserved. Extraction failure inside the safety net is graceful — `notifySafely({type: "warn", message: "safety net skipped: ..."})` is emitted and the hook still returns `undefined`, so a transient `runCompactExtraction` throw can never abort compaction.
- **`segmentMemorySaveCount` reset boundary changed**: counter resets at `session_start` and `session_compact` only — NOT at every `before_agent_start` turn boundary. The per-turn reset was a draft proposal that was rejected after the planner caught the S22 / R5 contradiction: turning back on after a long compacted-back-in session would cause the safety net to fire even when the agent had saved earlier in the same logical segment.
- **`before_agent_start` TUI hook refactored**: the inline `rewriteQueries` + `recallAtoms` + `rerankAndFilter` + `mergeByRerankScore` chain was replaced with a single `recallPipeline(index, {query, recent, topK: 20, embeddingServiceUrlProbe: false})` call. Both the rewrite / recall / rerank / merge ordering and the final `formatMemoryContext` shaping are unchanged; the only externally observable difference is that the recall result now includes a `status` object with timing + embedding-service metadata (TUI ignores it; webui propagates it through the response body).

### Fixed
- `findMostSimilarEmbedding` returned the query atom itself (cosine 1.0) as the closest match when the query id was present in the vector index (Task 2.5). The migration loop's `hit.atom.id !== atom.id` guard then short-circuited the candidate, so the actual neighbor (cosine 0.75) was never seen and no dedup ever fired. New optional `excludeId?` parameter (4th arg) lets the migration script pass the query id explicitly, applied as both a SQL `v.id != ?` clause and an in-loop guard. Without `excludeId` the legacy "self-as-closest" behavior is preserved for `dedup.ts` and `extraction.ts` write flows where the new id is freshly minted.

### Fixed
- Hash mismatch between DB content_fingerprint and file contentHash (both now use normalizeContent before sha256)
- Express route shadowing: /api/memory/stats, /search, /extract now register before /:id
- **`session_before_compact` extraction wired up**: the hook previously read `event.messages` (a non-existent field) and used a hardcoded `callLlm` stub returning `'{"items":[]}'`, so compact fired the hook but never produced atoms. The handler now reads `event.preparation.messagesToSummarize`, calls `completeSimple` with the session's `ctx.model`, and resolves the API key via `getEnvApiKey` (env first) then `ctx.modelRegistry.getApiKeyForProvider` (auth-storage fallback). Compact now grows memory automatically on every summary — no more manual `POST /api/memory/extract` workaround.
- **Memory directory self-heals on missing parent**: `MemoryIndex` constructor now runs `mkdirSync(dirname(dbPath), { recursive: true })` before opening the better-sqlite3 handle. better-sqlite3 itself refuses to create parent dirs — without this, deleting `~/.pi/agent/memory/` (or installing onto a fresh machine) made every compact / session_start / before_agent_start fail with SQLITE_CANTOPEN. The runtime's `extensionRunner.emit()` caught the throw and logged it via the extension error channel, so compact completed but extraction silently no-op'd. Now extraction self-heals and the next compact recreates the directory.
- **Compact extraction is now config-driven**: previously the session_before_compact hook used `ctx.model` (the session's main model) for the extraction LLM call. That was wrong — settings.json has its own `personalAssistant.memory.extraction.{provider,model}` setting (e.g. `minimax/MiniMax-M3`) which lets users run a cheap local model for extraction while keeping a strong cloud model for the agent loop. The hook now reads `loadConfig()`, looks up the configured model via `ctx.modelRegistry.find()`, and resolves auth via `ctx.modelRegistry.getApiKeyAndHeaders()` (the same path pi's own agent loop uses). If the config is missing, the model is not in the registry, or auth fails, the hook surfaces the error via `ctx.ui.notify(message, "error")` and **cancels compact** by returning `{cancel: true}`. The rationale: compact discards messages — discarding without preserving the learnings in memory would silently degrade the memory subsystem. Failing loudly is better than silently dropping; the user fixes the config and retries `/compact`. Empty `messagesToSummarize` (nothing to extract) does NOT cancel — it returns undefined so compact proceeds normally.
- **Extraction report's `modelUsed` is now the chat model, not the embedding model**: previously the hook passed `config.memory.embedding.model` (e.g. `bge-m3:latest`) as the `model` field to `extractMemoriesWithCallLlm`, which is then written to the report as `modelUsed`. That made the audit log show the wrong model — the chat completion model (e.g. `minimax/MiniMax-M3`) is the one that actually produced the extraction, not the embedding model. The report now names the chat model as `provider/model`, e.g. `minimax/MiniMax-M3`. No functional change; just fixes the audit label so `/compact` traces show the real model.
- **Compact hook now reads both `messagesToSummarize` and `turnPrefixMessages`**: previously the hook only looked at `event.preparation.messagesToSummarize`. For split-turn compactions (the common case for `/compact` and `auto-compact` mid-turn), the actual conversation content lives in `event.preparation.turnPrefixMessages` — `messagesToSummarize` is empty (just an old compaction summary) and the hook early-returned with zero atoms, silently dropping the only conversation content of the session. The fix concatenates both fields; the extraction LLM now sees the full pre-compact content regardless of where the cut landed. Regression test added: `reads BOTH messagesToSummarize and turnPrefixMessages (split-turn fix)`.
- **`recallAtoms` RRF threshold reverted to industry-standard rank-only (`1/(rrfK+1)`) + cosine floor is the noise filter**: the previous "strict" `DEFAULT_RECALL_THRESHOLD = 1 / DEFAULT_RRF_K` (≈ 0.01667) filtered single-channel rank=0 hits, breaking the user's keyword-only rescue path ("MGM" / "mgm 项目还记得吗" returning 0 hits even though the MGM atom is in the corpus and dense+BM25 return it). RRF rank-only is the industry standard (Elasticsearch / OpenSearch / Qdrant / Milvus all filter on rank, not absolute score). The threshold is now `1 / (DEFAULT_RRF_K + 1)` (≈ 0.01639 with rrfK=60) — single-channel rank=0 contribution EQUALS the threshold and passes (`>=`), rank≥1 single-channel contributions are filtered. The user's `lefse` dense-noise case (cosine 0.55, BM25 0 hit) is still correctly filtered, but by the COSINE FLOOR (`DEFAULT_DENSE_COSINE_FLOOR = 0.65`), not the recall gate — the floor removes the 0.55 cosine atom from the dense channel BEFORE RRF fusion. For users who want strict "宁可漏召不可误召" single-channel rank=0 filtering, the config knob `recallThreshold: 1 / rrfK` (≈ 0.01667) is now documented as the opt-in strict mode. `recallThreshold: 0` remains the test/dev escape hatch. Regression test rewritten: `lefse-regression.test.ts` now pins the production-pipeline contract (cosine floor catches lefse), the strict-mode contract (`recallThreshold: 1/rrfK` + `threshold: 0` filters single-channel rank=0), and the MGM-style keyword rescue contract (single-channel BM25 rank=0 passes the default gate).
- **`recallAtoms` query splitting for mixed ASCII+CJK queries (OR-semantics across heterogeneous tokens) — capped at 3 segments**: the user's mixed query `mgm工时计算` previously returned only the MGM atom (1 hit) — the joint embedding of `mgm工时计算` is dominated by the MGM project signal, and dense cosine with work-hour atoms (`工时估算-...`) falls below the 0.65 floor (`0.55-0.60` range). Stripping CJK from the BM25 query helps ASCII matching (`mgm` → MGM atom via the `MGM` tag token) but does not surface the CJK-content work-hour atoms. The fix splits the query into homogeneous segments at ASCII↔CJK boundaries AND whitespace (`mgm工时计算` → `["mgm", "工时计算"]`, `mgm 工时计算` → `["mgm", "工时计算"]`) and OR-merges the per-segment results: dedup by `atom.id` keeping the highest `rrfScore`, re-apply per-type cap (3), round-robin interleave by type. Each segment gets its own dense embedding so the `工时计算` sub-query's dense channel matches the work-hour atoms (cosine 0.66-0.73) without the MGM bias. **The split ONLY fires when the segment count is ≤ 3 (`MAX_SPLIT_SEGMENTS`)** — longer mixed queries (typical for the agent's `before_agent_start` hook passing a full user message: file path + project ID + description + commands) explode into 15-30 segments after `splitQuery`, and OR-merging that many dilutes specificity because recall probability scales as `1-(1-p)ᴺ`. For long queries the whole string is treated as a single segment so dense embedding of the full message can hit semantic neighbors via subword-level matching and BM25 can match the escape-preserved ASCII tokens (project ID, file path) directly. The pure-query case (webui search and focused `before_agent_start` queries) is unaffected — short mixed queries like `mgm工时计算` (2 segments, under cap) still split and benefit from per-segment dense + BM25. The split ALSO only fires when segments have BOTH ASCII and CJK kinds — pure ASCII multi-word (`"omicron signal unique"`) and pure CJK multi-word (`"工时估算 项目"`) are passed as a single query because the dense embedding of the full phrase is more precise than per-word embeddings for non-mixed queries. After this change: `mgm工时计算` returns 3 hits (MGM atom via `mgm` BM25 + 2 work-hour atoms via `工时计算` dense), up from 1; the user's 212-char DNA-virus message returns the correct `X101SC26063351-Z01-J001 从 rnaVirus 修正为 dnaVirus` atom (cos 0.6593, single-segment dense + BM25) instead of over-recalling 6 unrelated atoms via 32-segment OR-merge.
- **`escapeFtsQuery` strips `-` and `.` (FTS5 query-parser column-filter trap)**: previously a long query containing file paths or sample IDs (e.g. `X101SC260410257-Z01-F001.metagenomics.20260617`) raised `SqliteError: no such column: Z01` from `bm25Search` because FTS5's query parser interprets `IDENT-IDENT` as `IDENT : IDENT` (the `-` becomes an implicit column-filter separator) and the second IDENT is treated as a column name. The dot character raised `fts5: syntax error near '.'`. The fix extends the strip set with `-` and `.` so the query is converted to space-separated tokens; the corpus's unicode61 tokenizer already splits on `-` and `.` at INSERT time, so stripping them in the query doesn't change matchability — it just avoids the parse error. New regression test: `long mixed query does NOT split into segments; BM25 strips - and . cleanly` exercises the full long-prompt path through `recallAtoms` + `escapeFtsQuery` + FTS5.
- **`escapeFtsQuery` rewritten as whitelist (keep `[a-zA-Z0-9_\s]`, strip everything else)**: the previous version enumerated the FTS5-special char set (`"`, `(`, `)`, `*`, `:`, `[`, `]`, `,`, `/`, `-`, `.`) — but FTS5 also raises syntax errors on `;`, `!`, `?`, `&`, `|`, `~`, `@`, `#`, `$`, `%`, `=`, `<`, `>`, `'`, `\`, `{`, `}` (each with a different error message). The user's monthly-workload query `等位基因差异性表达（ASE）分析;分子分型分析;...` crashed every `before_agent_start` recall with `fts5: syntax error near ";"`. Enumerating bad chars is an endless whack-a-mole as user queries surface new ones. The fix inverts the regex to keep ONLY the corpus's unicode61 token alphabet (ASCII letters, digits, underscore, whitespace). Fullwidth punctuation `（）` `；` etc. is also stripped (FTS5 errors on those too). After the rewrite: the user's monthly-workload query reaches FTS5 without throwing (returns 0 results, since the corpus has no atoms about ASE / molecular typing / Salmon / Kallisto — that's a separate recall-coverage gap, not a crash). New regression tests cover each previously-breaking char class and the full user query.
- **`buildEmbeddableText` drops `content` — embeddings use only title + summary + tags (`CURRENT_EMBEDDABLE_TEXT_VERSION = 2`)**: recall is discovery-only (results carry `atom.id`; full content is fetched by `memory_get` on demand), so embedding the long, verbose `content` field was redundant — it just dilutes the curated title/summary/tags signal with incidental token mentions. Concrete effect: a work-hour atom that mentions "MGM" once in its long content would previously have its embedding direction pulled toward the "MGM" cluster, causing cross-concept false positives during recall. After this change the embedding reflects only the curated "index card" (title + summary + tags), so a focused query like `mgm工时计算` no longer gets diluted by the long content. The drop also cuts embedding input size by ~5-10x on average (content is typically 80% of the text), giving a measurable latency win on the embed call. Schema migration: added `embed_text_version` column to `memory_index` (ALTER TABLE in `init()`, idempotent) + `listStaleEmbedVersionIds` / `setEmbedTextVersion` storage methods + a migration step in the `session_start` hook that re-embeds any atom whose stored version is below current. The migration is incremental and self-terminating: once every atom has been re-embedded, subsequent `session_start` events no-op on this step. Existing user DBs are migrated automatically on the next `session_start` after the upgrade; for the current user the 19 active atoms completed in ~2.5s. Also fixed `upsertVector`: `INSERT OR REPLACE` does not work against sqlite-vec's `vec0` virtual table (the unique constraint fires instead of deleting the prior row), so the method now does explicit `DELETE` + `INSERT` to remain idempotent at call sites.
- **`init()` repairs broken `memory_fts` left over from earlier schema (NULL `id` rows)**: previously `init()`'s "memory_fts exists → skip" idempotency path was too aggressive — it didn't detect when an existing `memory_fts` was structurally broken. The user's real `~/.pi/agent/memory/memory.db` had `memory_fts` with 7 rows but ALL `id` columns were NULL (leftover from an earlier parallel session that created the table in contentless mode `content=''`, which doesn't populate the UNINDEXED `id` column on INSERT). Every `bm25Search` JOIN silently returned zero hits because `v.id IS NULL` never matches `i.id`. The init path now detects NULL-id rows (`SELECT COUNT(*) FROM memory_fts WHERE id IS NULL > 0`) and atomically `DROP + CREATE + backfill` in a single transaction; healthy `memory_fts` is left untouched. The trade-off: a brief startup-time rebuild of a broken table is better than a silent BM25 outage — principle "宁可漏召不可误召" + "FTS5 行同步在 storage 层原子化". Regression tests added: `init repairs broken memory_fts (NULL ids)` and `init does not touch valid memory_fts (no false repair)`.

### Known Limitations
- **TUI memory status indicator**: the `ctx.ui.setStatus` API for footer status has existed since `7b902612 feat(coding-agent): add FooterDataProvider for git branch and extension statuses`, but neither v1 nor v2 memory ever called it. Recall results were only ever injected into the LLM prompt — invisible to the user. Now fixed via the `before_agent_start` hook firing `setStatus("memory", …)` on every turn.
- **Paraphrase-duplicate atom growth with new oldId-only dedup** (extract-oldid-merge): the removal of the cosine ≥ 0.65 write-time gate means the LLM is the sole decision-maker for update-vs-create. When the LLM misses a paraphrase duplicate of an existing atom (e.g. recall top-K didn't bring it back, or the LLM paraphrased and didn't recognize it), the atom will be created as a sibling. The corpus may grow incrementally over time until a future drive-time sweep re-introduces a cosing gate (the migration script `migrate-legacy-atoms.mts` is a one-shot template for this; not yet ported to recurring). Pre-existing concern deepened by the rename. Tracking separately.
- **TOCTOU window in `executeItem` update path (extract-oldid-merge)**: `index.getAtom(oldId)` → `index.updateAtom(merged)` has a race against concurrent PATCH / parallel extraction / drift-sweep. The webui PATCH path closes this with `updateAtomIfVersion` (storage.ts:228, optimistic CAS on `version`); `executeItem` uses the plain `updateAtom`. Pre-existing in v1 cosine path; the new oldId path elevates merge correctness. Fix would be a 1-file change reusing the `version` field on `read`/`write`. Out of scope for this quickfix.
- **`recalledAtoms` corpus may serve stale DB content** (extract-oldid-merge): `collectRecalledAtoms` calls `recallAtoms` without passing `atomsDir`, so `RecallResult.atom.content` is read from the DB row, not the on-disk `.md`. If the user or agent edited the .md body directly via the write/edit tool (or via bash), the LLM sees stale text when deciding what to merge via oldId — and then writes its merged content on top of the stale view. Pre-existing behavior (v1 also did not read .md for recall); the oldId path makes it more impactful because the LLM now relies on body content to choose a merge target. `f9ac3423d feat(memory): recall reads .md body for content` adds the option to pass `atomsDir`; calling `collectRecalledAtoms` should forward `config.atomsDir` to unlock it. Out of scope for this quickfix.

### Added (webui-memory-page)

### Added

- **Public API surface** for the memory subsystem: `MemoryIndex`, `MemoryAtom`, `MemoryAtomType`, `QueryRewriteResult` are now exported from `@earendil-works/pi-personal-assistant` (previously module-private), enabling the webui server to read/write atoms without re-implementing the index or the file store.
- **Server-friendly helpers** that take an injected `callLlm` callback instead of `ExtensionContext.modelRegistry`, so the webui server can run the recall pipeline without constructing a fake agent context:
  - `getAllAtoms(index)` — module-level function returning all atoms (including archived).
  - `MemoryIndex.invalidateEmbedding(id)` — public method that removes the cached embedding row (PATCH callers invoke this to defer recompute).
  - `rewriteQueryWithCallLlm(callLlm, query, config)` — runs the query rewrite path against an injected LLM callback; falls back to `simpleKeywordExtraction` on error or unparseable JSON.
  - `searchAtomsWithScores(index, query, topK, config?)` — same hybrid FTS5 + embedding search as `searchAtoms`, but returns per-result `{fts_score, cosine_score, hybrid_score}` plus an `embedding_available` flag for the recall tester; accepts an optional `config` override so the server's settings (not the developer's `~/.pi/agent/settings.json`) drive embedding search.
- `MemoryAtomType` union now includes `"bug"` as an 8th type alongside the documented 7 (production data contained 1 atom of this type).
- `QueryRewriteResult.fallback: boolean` — `true` when the rewrite degraded to `simpleKeywordExtraction` (LLM threw, returned empty, or returned unparseable JSON), `false` when a structured LLM response was parsed.

### Fixed

- `writeAtomToFile(atom, baseDir)` previously emitted a `tmp → rename` overwrite that could collide with another atom sharing the same slugified title, silently orphaning the older file. (Documented as v1 limitation R14; not fixed — needs ID-stamped paths.)
- Query rewriter now drops redundant keywords before they reach FTS5:
  - `dedupeRedundantKeywords`: drops any keyword that can be formed by concatenating a subsequence of the other keywords (catches the common LLM behavior of returning BOTH the broken-down tokens AND the original phrase as one of the keywords, e.g. `["PDF","图片","提取","图片提取"]` for query `pdf中图片提取`).
  - `dedupeAgainstQuery`: drops any keyword that equals the normalized user query (case-insensitive, whitespace-folded).
  Both helpers run inside `parseRewriteJson` / `rewriteQueryWithCallLlm` / `rewriteQuery` / `callOllamaRewrite` so every code path that hands a `QueryRewriteResult` to `searchAtoms` benefits.
- `searchAtomsWithScores.embedding_available` now reflects the **embedding service's reachability**, not whether FTS candidates happened to have stored embeddings. Previously it was `(embeddingResults.size > 0)`, which conflated two unrelated facts and caused the webui Search Tester to display "embedding unavailable" in the common case where the LLM returned empty keywords or the FTS `target_types` filter excluded the matching atom. Fixed by adding `isEmbeddingServiceAvailable(queryText, config)` (probes the embedding service for the query vector) and calling it at the top of `searchAtomsWithScores`, independent of the FTS path. `searchEmbeddings` now also returns `{ scores, serviceAvailable }` so the scoring layer can keep using per-atom cosine scores without re-probing.
