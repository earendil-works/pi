# Changelog

## [Unreleased]

### Breaking Changes
- Memory module v2: complete rewrite using pure vector retrieval (sqlite-vec + bge-m3)
- Atom type union: 8 types → 3 types: `rule | fact | process` (replaces constraint/preference/knowledge/event/bug/workflow/solution/insight)
- File path: `<slug>.md` → `<type>/<atom.id>.md` (id-based, no slug collision)
- Content fingerprint now includes normalization (whitespace collapse + lowercase) before hashing
- Storage: `bun:sqlite`/`node:sqlite` wrapper → better-sqlite3 + sqlite-vec
- Removed: FTS5, query rewriting, CJK keyword expansion, isEmbeddingServiceAvailable fallback

### Added
- MemoryIndex class with KNN search, fingerprint-based dedup, supersede transactions, audit log
- executePlan with fingerprint + cosine (>= 0.92) two-tier dedup
- runDecay with exp decay formula, rule type never archived
- formatMemoryContext with L0/L1 tiering and token budget (default 4000)
- Lifecycle hooks: session_before_compact (extraction), session_start (throttled decay), before_agent_start + context (memory injection with 8s timeout)
- Extraction report JSON to ~/.pi/agent/logs/
- Recall quality validation: 14 atoms / 9 queries labeled dataset, char n-gram mock embed
- New `memory_get` tool — sole programmatic strength-feedback entry. Bumps `access_count` and `last_access` on successful lookup.
- New `scoreUserTone` 5-tier user-tone scorer (STRONG/HABIT/WEAK/RARE/NEUTRAL) + `<user_tone>` hint injection in `buildExtractionPrompt`. Extraction LLM uses it to calibrate importance (±0.15 deviation allowed).
- TUI footer status indicator for memory recall. The `before_agent_start` hook now surfaces the most recent recall result via `ctx.ui.setStatus("memory", …)` so the user sees `"📦 N atoms · rule=X fact=Y process=Z · top=0.XXX"` (hits), `"🔍 no memory match"` (empty), or `"⚠ memory recall failed"` (error) below the mode chip. Status reflects the most recent recall; older states are not retained.
- `supersedeIfSimilar(index, atomsDir, newAtom, embedding, threshold?)` extracted to `dedup.ts` for reuse by webui PATCH and extraction flows
- `normalizeTags(input, aliases?)` in `tag-alias.ts` for dual-side alias folding (write + query)
- `computeTagOverlap` and `computeFreshness` scoring helpers in `scoring.ts`
- `PersonalAssistantConfig.memory.{tagAliases, tagOverlapWeight, freshnessWeight}` — runtime-configurable scoring weights
- Score formula extended with additive `tagOverlap` and `freshness` terms (RecallResult exposes both as debug fields)

### Changed
- memory.ts reduced from 1649 → 290 lines (v2 is entry-point-only)
- All v1 search/extract/decay logic moved to specialized modules (storage, search, format, extraction, decay)
- Schema: new tables (memory_index, memory_vectors vec0 FLOAT[1024], memory_audit) with 5 indexes
- Embedding: full text (title+summary+content+tags) instead of title-only
- Search is discovery-only: `recallAtoms` returns summary + `id` for every result (no L0/L1 tier hydration). The agent calls `memory_get(id)` to fetch full content — that call is the sole programmatic strength-feedback signal.
- Search response now returns `score` instead of `file_path`. Score = cosine × (1 + 0.3 × strength + 0.2 × importance), per-type top-3 with round-robin interleaving. `formatMemoryContext` re-sorts by `distance` ASC (cosine DESC) before injecting into LLM prompt — `score` is metadata, not visible to the LLM. Extraction prompt now accepts `<user_tone>` hint to calibrate importance.
- Webui `GET /api/memory/:id` is preview-only — does NOT bump `access_count`. Strength feedback is recorded exclusively by the agent's `memory_get` tool.
- Recall pipeline from hybrid (BM25+dense+RRF) to pure dense + cosine floor 0.7

### Fixed
- Hash mismatch between DB content_fingerprint and file contentHash (both now use normalizeContent before sha256)
- Express route shadowing: /api/memory/stats, /search, /extract now register before /:id
- **`session_before_compact` extraction wired up**: the hook previously read `event.messages` (a non-existent field) and used a hardcoded `callLlm` stub returning `'{"items":[]}'`, so compact fired the hook but never produced atoms. The handler now reads `event.preparation.messagesToSummarize`, calls `completeSimple` with the session's `ctx.model`, and resolves the API key via `getEnvApiKey` (env first) then `ctx.modelRegistry.getApiKeyForProvider` (auth-storage fallback). Compact now grows memory automatically on every summary — no more manual `POST /api/memory/extract` workaround.
- **Memory directory self-heals on missing parent**: `MemoryIndex` constructor now runs `mkdirSync(dirname(dbPath), { recursive: true })` before opening the better-sqlite3 handle. better-sqlite3 itself refuses to create parent dirs — without this, deleting `~/.pi/agent/memory/` (or installing onto a fresh machine) made every compact / session_start / before_agent_start fail with SQLITE_CANTOPEN. The runtime's `extensionRunner.emit()` caught the throw and logged it via the extension error channel, so compact completed but extraction silently no-op'd. Now extraction self-heals and the next compact recreates the directory.
- **Compact extraction is now config-driven**: previously the session_before_compact hook used `ctx.model` (the session's main model) for the extraction LLM call. That was wrong — settings.json has its own `personalAssistant.memory.extraction.{provider,model}` setting (e.g. `minimax/MiniMax-M3`) which lets users run a cheap local model for extraction while keeping a strong cloud model for the agent loop. The hook now reads `loadConfig()`, looks up the configured model via `ctx.modelRegistry.find()`, and resolves auth via `ctx.modelRegistry.getApiKeyAndHeaders()` (the same path pi's own agent loop uses). If the config is missing, the model is not in the registry, or auth fails, the hook surfaces the error via `ctx.ui.notify(message, "error")` and **cancels compact** by returning `{cancel: true}`. The rationale: compact discards messages — discarding without preserving the learnings in memory would silently degrade the memory subsystem. Failing loudly is better than silently dropping; the user fixes the config and retries `/compact`. Empty `messagesToSummarize` (nothing to extract) does NOT cancel — it returns undefined so compact proceeds normally.
- **Extraction report's `modelUsed` is now the chat model, not the embedding model**: previously the hook passed `config.memory.embedding.model` (e.g. `bge-m3:latest`) as the `model` field to `extractMemoriesWithCallLlm`, which is then written to the report as `modelUsed`. That made the audit log show the wrong model — the chat completion model (e.g. `minimax/MiniMax-M3`) is the one that actually produced the extraction, not the embedding model. The report now names the chat model as `provider/model`, e.g. `minimax/MiniMax-M3`. No functional change; just fixes the audit label so `/compact` traces show the real model.
- **Compact hook now reads both `messagesToSummarize` and `turnPrefixMessages`**: previously the hook only looked at `event.preparation.messagesToSummarize`. For split-turn compactions (the common case for `/compact` and `auto-compact` mid-turn), the actual conversation content lives in `event.preparation.turnPrefixMessages` — `messagesToSummarize` is empty (just an old compaction summary) and the hook early-returned with zero atoms, silently dropping the only conversation content of the session. The fix concatenates both fields; the extraction LLM now sees the full pre-compact content regardless of where the cut landed. Regression test added: `reads BOTH messagesToSummarize and turnPrefixMessages (split-turn fix)`.
- **`recallAtoms` RRF threshold reverted to industry-standard rank-only (`1/(rrfK+1)`) + cosine floor is the noise filter**: the previous "strict" `DEFAULT_RECALL_THRESHOLD = 1 / DEFAULT_RRF_K` (≈ 0.01667) filtered single-channel rank=0 hits, breaking the user's keyword-only rescue path ("MGM" / "mgm 项目还记得吗" returning 0 hits even though the MGM atom is in the corpus and dense+BM25 return it). RRF rank-only is the industry standard (Elasticsearch / OpenSearch / Qdrant / Milvus all filter on rank, not absolute score). The threshold is now `1 / (DEFAULT_RRF_K + 1)` (≈ 0.01639 with rrfK=60) — single-channel rank=0 contribution EQUALS the threshold and passes (`>=`), rank≥1 single-channel contributions are filtered. The user's `lefse` dense-noise case (cosine 0.55, BM25 0 hit) is still correctly filtered, but by the COSINE FLOOR (`DEFAULT_DENSE_COSINE_FLOOR = 0.65`), not the recall gate — the floor removes the 0.55 cosine atom from the dense channel BEFORE RRF fusion. For users who want strict "宁可漏召不可误召" single-channel rank=0 filtering, the config knob `recallThreshold: 1 / rrfK` (≈ 0.01667) is now documented as the opt-in strict mode. `recallThreshold: 0` remains the test/dev escape hatch. Regression test rewritten: `lefse-regression.test.ts` now pins the production-pipeline contract (cosine floor catches lefse), the strict-mode contract (`recallThreshold: 1/rrfK` + `threshold: 0` filters single-channel rank=0), and the MGM-style keyword rescue contract (single-channel BM25 rank=0 passes the default gate).
- **`recallAtoms` query splitting for mixed ASCII+CJK queries (OR-semantics across heterogeneous tokens) — capped at 3 segments**: the user's mixed query `mgm工时计算` previously returned only the MGM atom (1 hit) — the joint embedding of `mgm工时计算` is dominated by the MGM project signal, and dense cosine with work-hour atoms (`工时估算-...`) falls below the 0.65 floor (`0.55-0.60` range). Stripping CJK from the BM25 query helps ASCII matching (`mgm` → MGM atom via the `MGM` tag token) but does not surface the CJK-content work-hour atoms. The fix splits the query into homogeneous segments at ASCII↔CJK boundaries AND whitespace (`mgm工时计算` → `["mgm", "工时计算"]`, `mgm 工时计算` → `["mgm", "工时计算"]`) and OR-merges the per-segment results: dedup by `atom.id` keeping the highest `rrfScore`, re-apply per-type cap (3), round-robin interleave by type. Each segment gets its own dense embedding so the `工时计算` sub-query's dense channel matches the work-hour atoms (cosine 0.66-0.73) without the MGM bias. **The split ONLY fires when the segment count is ≤ 3 (`MAX_SPLIT_SEGMENTS`)** — longer mixed queries (typical for the agent's `before_agent_start` hook passing a full user message: file path + project ID + description + commands) explode into 15-30 segments after `splitQuery`, and OR-merging that many dilutes specificity because recall probability scales as `1-(1-p)ᴺ`. For long queries the whole string is treated as a single segment so dense embedding of the full message can hit semantic neighbors via subword-level matching and BM25 can match the escape-preserved ASCII tokens (project ID, file path) directly. The pure-query case (webui search and focused `before_agent_start` queries) is unaffected — short mixed queries like `mgm工时计算` (2 segments, under cap) still split and benefit from per-segment dense + BM25. The split ALSO only fires when segments have BOTH ASCII and CJK kinds — pure ASCII multi-word (`"omicron signal unique"`) and pure CJK multi-word (`"工时估算 项目"`) are passed as a single query because the dense embedding of the full phrase is more precise than per-word embeddings for non-mixed queries. After this change: `mgm工时计算` returns 3 hits (MGM atom via `mgm` BM25 + 2 work-hour atoms via `工时计算` dense), up from 1; the user's 212-char DNA-virus message returns the correct `X101SC26063351-Z01-J001 从 rnaVirus 修正为 dnaVirus` atom (cos 0.6593, single-segment dense + BM25) instead of over-recalling 6 unrelated atoms via 32-segment OR-merge.
- **`escapeFtsQuery` strips `-` and `.` (FTS5 query-parser column-filter trap)**: previously a long query containing file paths or sample IDs (e.g. `X101SC260410257-Z01-F001.metagenomics.20260617`) raised `SqliteError: no such column: Z01` from `bm25Search` because FTS5's query parser interprets `IDENT-IDENT` as `IDENT : IDENT` (the `-` becomes an implicit column-filter separator) and the second IDENT is treated as a column name. The dot character raised `fts5: syntax error near '.'`. The fix extends the strip set with `-` and `.` so the query is converted to space-separated tokens; the corpus's unicode61 tokenizer already splits on `-` and `.` at INSERT time, so stripping them in the query doesn't change matchability — it just avoids the parse error. New regression test: `long mixed query does NOT split into segments; BM25 strips - and . cleanly` exercises the full long-prompt path through `recallAtoms` + `escapeFtsQuery` + FTS5.
- **`escapeFtsQuery` rewritten as whitelist (keep `[a-zA-Z0-9_\s]`, strip everything else)**: the previous version enumerated the FTS5-special char set (`"`, `(`, `)`, `*`, `:`, `[`, `]`, `,`, `/`, `-`, `.`) — but FTS5 also raises syntax errors on `;`, `!`, `?`, `&`, `|`, `~`, `@`, `#`, `$`, `%`, `=`, `<`, `>`, `'`, `\`, `{`, `}` (each with a different error message). The user's monthly-workload query `等位基因差异性表达（ASE）分析;分子分型分析;...` crashed every `before_agent_start` recall with `fts5: syntax error near ";"`. Enumerating bad chars is an endless whack-a-mole as user queries surface new ones. The fix inverts the regex to keep ONLY the corpus's unicode61 token alphabet (ASCII letters, digits, underscore, whitespace). Fullwidth punctuation `（）` `；` etc. is also stripped (FTS5 errors on those too). After the rewrite: the user's monthly-workload query reaches FTS5 without throwing (returns 0 results, since the corpus has no atoms about ASE / molecular typing / Salmon / Kallisto — that's a separate recall-coverage gap, not a crash). New regression tests cover each previously-breaking char class and the full user query.
- **`buildEmbeddableText` drops `content` — embeddings use only title + summary + tags (`CURRENT_EMBEDDABLE_TEXT_VERSION = 2`)**: recall is discovery-only (results carry `atom.id`; full content is fetched by `memory_get` on demand), so embedding the long, verbose `content` field was redundant — it just dilutes the curated title/summary/tags signal with incidental token mentions. Concrete effect: a work-hour atom that mentions "MGM" once in its long content would previously have its embedding direction pulled toward the "MGM" cluster, causing cross-concept false positives during recall. After this change the embedding reflects only the curated "index card" (title + summary + tags), so a focused query like `mgm工时计算` no longer gets diluted by the long content. The drop also cuts embedding input size by ~5-10x on average (content is typically 80% of the text), giving a measurable latency win on the embed call. Schema migration: added `embed_text_version` column to `memory_index` (ALTER TABLE in `init()`, idempotent) + `listStaleEmbedVersionIds` / `setEmbedTextVersion` storage methods + a migration step in the `session_start` hook that re-embeds any atom whose stored version is below current. The migration is incremental and self-terminating: once every atom has been re-embedded, subsequent `session_start` events no-op on this step. Existing user DBs are migrated automatically on the next `session_start` after the upgrade; for the current user the 19 active atoms completed in ~2.5s. Also fixed `upsertVector`: `INSERT OR REPLACE` does not work against sqlite-vec's `vec0` virtual table (the unique constraint fires instead of deleting the prior row), so the method now does explicit `DELETE` + `INSERT` to remain idempotent at call sites.
- **`init()` repairs broken `memory_fts` left over from earlier schema (NULL `id` rows)**: previously `init()`'s "memory_fts exists → skip" idempotency path was too aggressive — it didn't detect when an existing `memory_fts` was structurally broken. The user's real `~/.pi/agent/memory/memory.db` had `memory_fts` with 7 rows but ALL `id` columns were NULL (leftover from an earlier parallel session that created the table in contentless mode `content=''`, which doesn't populate the UNINDEXED `id` column on INSERT). Every `bm25Search` JOIN silently returned zero hits because `v.id IS NULL` never matches `i.id`. The init path now detects NULL-id rows (`SELECT COUNT(*) FROM memory_fts WHERE id IS NULL > 0`) and atomically `DROP + CREATE + backfill` in a single transaction; healthy `memory_fts` is left untouched. The trade-off: a brief startup-time rebuild of a broken table is better than a silent BM25 outage — principle "宁可漏召不可误召" + "FTS5 行同步在 storage 层原子化". Regression tests added: `init repairs broken memory_fts (NULL ids)` and `init does not touch valid memory_fts (no false repair)`.

### Known Limitations
- **TUI memory status indicator**: the `ctx.ui.setStatus` API for footer status has existed since `7b902612 feat(coding-agent): add FooterDataProvider for git branch and extension statuses`, but neither v1 nor v2 memory ever called it. Recall results were only ever injected into the LLM prompt — invisible to the user. Now fixed via the `before_agent_start` hook firing `setStatus("memory", …)` on every turn.

### Added (webui-memory-page)

### Added

- **Public API surface** for the memory subsystem: `MemoryIndex`, `MemoryAtom`, `MemoryAtomType`, `QueryRewriteResult` are now exported from `@earendil-works/pi-personal-assistant` (previously module-private), enabling the webui server to read/write atoms without re-implementing the index or the file store.
- **Server-friendly helpers** that take an injected `callLlm` callback instead of `ExtensionContext.modelRegistry`, so the webui server can run the recall pipeline without constructing a fake agent context:
  - `getAllAtoms(index)` — module-level function returning all atoms (including archived).
  - `MemoryIndex.invalidateEmbedding(id)` — public method that removes the cached embedding row (PATCH callers invoke this to defer recompute).
  - `rewriteQueryWithCallLlm(callLlm, query, config)` — runs the query rewrite path against an injected LLM callback; falls back to `simpleKeywordExtraction` on error or unparseable JSON.
  - `searchAtomsWithScores(index, query, topK, config?)` — same hybrid FTS5 + embedding search as `searchAtoms`, but returns per-result `{fts_score, cosine_score, hybrid_score}` plus an `embedding_available` flag for the recall tester; accepts an optional `config` override so the server's settings (not the developer's `~/.pi/agent/settings.json`) drive embedding search.
- `MemoryAtomType` union now includes `"bug"` as an 8th type alongside the documented 7 (production data contained 1 atom of this type).
- `QueryRewriteResult.fallback: boolean` — `true` when the rewrite degraded to `simpleKeywordExtraction` (LLM threw, returned empty, or returned unparseable JSON), `false` when a structured LLM response was parsed.

### Fixed

- `writeAtomToFile(atom, baseDir)` previously emitted a `tmp → rename` overwrite that could collide with another atom sharing the same slugified title, silently orphaning the older file. (Documented as v1 limitation R14; not fixed — needs ID-stamped paths.)
- Query rewriter now drops redundant keywords before they reach FTS5:
  - `dedupeRedundantKeywords`: drops any keyword that can be formed by concatenating a subsequence of the other keywords (catches the common LLM behavior of returning BOTH the broken-down tokens AND the original phrase as one of the keywords, e.g. `["PDF","图片","提取","图片提取"]` for query `pdf中图片提取`).
  - `dedupeAgainstQuery`: drops any keyword that equals the normalized user query (case-insensitive, whitespace-folded).
  Both helpers run inside `parseRewriteJson` / `rewriteQueryWithCallLlm` / `rewriteQuery` / `callOllamaRewrite` so every code path that hands a `QueryRewriteResult` to `searchAtoms` benefits.
- `searchAtomsWithScores.embedding_available` now reflects the **embedding service's reachability**, not whether FTS candidates happened to have stored embeddings. Previously it was `(embeddingResults.size > 0)`, which conflated two unrelated facts and caused the webui Search Tester to display "embedding unavailable" in the common case where the LLM returned empty keywords or the FTS `target_types` filter excluded the matching atom. Fixed by adding `isEmbeddingServiceAvailable(queryText, config)` (probes the embedding service for the query vector) and calling it at the top of `searchAtomsWithScores`, independent of the FTS path. `searchEmbeddings` now also returns `{ scores, serviceAvailable }` so the scoring layer can keep using per-atom cosine scores without re-probing.
